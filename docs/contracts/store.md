# store contract

## Responsibility

The only module that opens the database. `store.SessionDayWriter` upserts and `store.SessionDayReader` reads `master.session_day r1` rows; `sessionday.Open` returns both with `Close` as a `store.SessionDayStore`. `internal/store/migrate` applies goose SQL migrations from an `fs.FS` the caller supplies; it embeds none.

`internal/store/snapshot` holds the Reader and the Writer of two append-only datasets, `obs.option_eod r1` (one option contract on one session day, in-session daily chain snapshot, any number of captures a day) and `obs.quote_snapshot r1` (a planned time slot of quotes). Neither can be obtained again once the day has gone, so both tables are permanent. `snapshot.OpenOptionEod` returns a `store.OptionEodStore` and `snapshot.OpenQuoteSnapshot` a `store.QuoteSnapshotStore`, each with `Close`.

`internal/store/instrument` holds the instrument tables' store: `master.instrument` (one row per instrument, `instrument_id` generated by the database) and `master.instrument_identifier` (the names of an instrument: schemes `ibkr_conid`, `osi`, `ticker_exchange`, `jpx_option_code`, `isin`; key `(scheme, value, valid_from)`; `valid_to` NULL while valid), made by migration `0008`. `instrument.Open` returns a `store.InstrumentStore`: the resolver `ResolveInstrument` and the reader `Instruments`, with `Close`.

`master.option_terms` (migration `0009`) holds one row per version of the terms of one option, and the view `rd.option_terms_r1` shows the current version of each. `instrument.OpenOptionTerms` returns a `store.OptionTermsStore`: the reader `OptionTerms`, with `Close`. `store.OptionEodCatalog` (`OptionEodLatest`) lists the underlyings that have rows of `obs.option_eod` and the greatest `session_day` of each, read from `rd.option_eod_r1`; it is declared in `internal/store/api.go` and implemented by its own entry.

`internal/store/reading` holds the Reader and the Writer of stored figure values, `readings.reading` r1 (with the children `reading_input`, `reading_input_key` and `reading_parameter`). `reading.Open` returns a `store.ReadingStore` (`InsertReadings`, `LatestReadings`, `Close`) that also has the optional method `UpsertReadings` of `readingkey.ReadingUpserter` (callers assert it), from the line `store.DSNEnvReadings` (`OT_PG_DSN_READINGS`) of the role `ot_w_readings`.

`internal/store/bar` declares, in `api.go` only (no implementation in the package), the store of two datasets: `obs.price_bar r1` (daily bars upserted by key, `trades` and `adjusted_last`) and `obs.fx_rate r1` (the daily USD.JPY rate, upserted by key). `bar.BarStore` is `PriceBarWriter`, `PriceBarReader`, `FxRateWriter`, `FxRateReader` and `Close`; `bar.OpenBarFunc` opens it from the line `bar.DSNEnvBar` (`OT_PG_DSN_BAR`) of the role `ot_w_bar`. The implementation is `internal/store/barpg`.
`internal/store/ownerset` declares, in `api.go` only, the owner's settings store: `ownerset.Reader` (`Params`, `Exclusions`, `History`, `Version`, `Close`, all read as of a time), `ownerset.Writer` (`Apply` of a `Change`, one transaction, unchanged fields insert nothing), `ownerset.Store` (both) and `ownerset.OpenFunc`, from the line `ownerset.DSNEnvSettings` (`OT_PG_DSN_SETTINGS`). Design: `docs/design/settings-form.md#Interface`.

`internal/store/underlying` declares, in `api.go` only, the store of the names the owner follows (`docs/design/underlyings.md#Interface`): `underlying.Reader` (`Current`, `History`), `underlying.Writer` (`Apply` of a `Change`, one transaction, an `InvalidError` names the refused field), `underlying.Settler` (`Pending`, `Settle`: inserts only if the newest row of the key still has id `AfterID` and status `pending` or `unresolved`, else `written` false and no error), `underlying.Store` (all three) and `underlying.OpenFunc`, with `underlying.DSNEnvResolve` (`OT_PG_DSN_UNDERLYING_RESOLVE`); `InvalidError` is an interface (`error`, `Field() string`, `Why() string`) read with `errors.As`, so the package holds no function body; `underlyingpg` defines its own type. Migration `0033_underlying.sql` adds the insert-only versioned table `settings.underlying` (the newest row per `name_key` wins, ties by id) and the view `rd.underlying_r1`. Two roles write it: `ot_w_settings` (page route and import) and `ot_w_underlying_resolve` (the resolve job; made by `setup.Setup`, twenty roles in all, line `OT_PG_DSN_UNDERLYING_RESOLVE`, which `store/setup` writes as a literal because it may not import `store/underlying`); each has INSERT and SELECT on `settings.underlying`, SELECT on `rd.underlying_r1` and USAGE on the schemas `settings` and `rd`; `ot_w_underlying_resolve` holds nothing on `settings.rule_param` or `settings.option_exclusion`. `ot_ro_pages` and `ot_runner` have SELECT on the view and no grant on the table. No role but the owner has UPDATE, DELETE or TRUNCATE. The implementation is `internal/store/underlyingpg` (a later issue).

`internal/store/mark` declares, in `api.go` only, the store of position marks, `account.position_mark r1` (insert-only, one row per position of a capture, key `(capture_id, con_id, attempt)`). `mark.Writer.WriteMarks` writes the rows in one transaction and leaves a row whose key exists as it is (a correction is a row with a higher `Attempt`); `mark.Reader.Marks(alias, day)` returns the rows of the newest capture of that day that has marks, the highest `Attempt` of each `ConID`, sorted by `ConID`, an empty slice when none. `mark.Store` is both with `Close`; `mark.OpenFunc` opens it from the line `mark.DSNEnvPositionMark` (`OT_PG_DSN_POSMARK`) of the role `ot_w_posmark`. The implementation is `internal/store/markpg`: `markpg.Open` (a `mark.OpenFunc`) writes the table `account.position_mark` (migration `0026_position_mark.sql`; primary key `(capture_id, con_id, attempt)`, `basis` one of `mid`, `last`, `close`, `none`) with `ON CONFLICT DO NOTHING` in one transaction and reads the view `rd.account_position_mark_r1` only. The role `ot_w_posmark` (made by `setup.Setup`, eighteen roles in all) has INSERT and SELECT on the table, SELECT on the view and USAGE on the schemas `account` and `rd`; `ot_ro_pages` has SELECT on the view and nothing on the table; no role but the owner has UPDATE, DELETE or TRUNCATE. `store/setup` writes the literal `OT_PG_DSN_POSMARK` because it may not import `store/mark`.

`internal/store/openquote` declares, in `api.go` only, the stores of the option open pull (`docs/design/option-open-pull.md`): `OptionOpenWriter` (`InsertOptionOpen`: one transaction, `ON CONFLICT DO NOTHING` on `(session_day, capture_id, slot, instrument_id)`, -1, NaN and infinity stored as null, a row of slot `SlotRefresh` refused as a Permanent error: a refresh row is never stored) and `OptionOpenReader` (`OptionOpen(day)`: the newest row of each instrument, by `received_at`, from the view `rd.option_open_r1`), `OptionOpenPlanStore` (`PutPlan`; `Plan(day, slot, underlyingIDs...)`: the items of the latest plan, by `planned_at`, of each underlying, from the view `rd.option_open_item_r1`), `OptionNotListedStore` (`AddNotListed` replaces a mark of the same key; `NotListed(now)` lists the marks whose `retry_at` is after `now`; `RemoveNotListed`, `RemoveNotListedByUnderlying`, `RemoveNotListedExpired`), `OptionContractStore` (`PutOption` and `ListOptions` over `master.option_contract`, the one lookup from a contract identity: underlying id, currency, exchange, trading class, multiplier, expiry, strike text and right, to its instrument id) and `Stores`, all of them with `Close`; `SlotRefresh` is the one declaration of the refresh marker and `DSNEnvOptionOpen` (`OT_PG_DSN_OPTION_OPEN`) names the line of the role `ot_w_option_open`. The implementation is `internal/store/optionopenpg` (`Open`, an `openquote.OpenFunc`), over migrations `0029_option_open.sql` (`obs.option_open`, a hypertable on `session_day`, and `rd.option_open_r1`), `0030_option_open_plan.sql` (`plan.option_open_item` and `rd.option_open_item_r1`), `0031_option_not_listed.sql` and `0032_option_contract.sql`. The role `ot_w_option_open` (made by `setup.Setup`, nineteen roles in all) has INSERT on `obs.option_open` and `plan.option_open_item`, SELECT on the two views, INSERT, UPDATE, DELETE and SELECT on `master.option_not_listed`, INSERT, UPDATE and SELECT on `master.option_contract`, and USAGE on the schemas `obs`, `plan`, `master` and `rd`; it has no SELECT on `obs.option_open` or `plan.option_open_item`. `ot_ro_pages` has SELECT on the two views and no grant on a base table (`ot serve` reads both views, with the pages line, and calls only the readers). No role but the owner has UPDATE, DELETE or TRUNCATE on `obs.option_open` and `plan.option_open_item`. `store/setup` writes the literal `OT_PG_DSN_OPTION_OPEN` because it may not import `store/openquote`.

`internal/store/hoursnotice` declares, in `api.go` only, the store of calendar-hours notices (`docs/design/calendar-ibkr-hours.md`, entry 5, Decisions 6, 7 and 9): `hoursnotice.Notice` (`Market`, `Day`, `Ours`, `IBKR`), `hoursnotice.Reader` (`Notices`, all rows ordered by market and day, an empty slice when none; `Close`) and `hoursnotice.Store` (the Reader and `Replace(ctx, market, rows)`). `Replace` deletes the market's rows and inserts `rows` in one transaction, so a day that no longer differs vanishes, a repeat with the same rows changes nothing, an empty `rows` clears the market, rows of other markets stay, and a row of another market fails the call before any statement. The implementation is `internal/store/hoursnoticepg` (`Open(ctx, dsn)`, for the line of the role `ot_w_master`; it writes the table and reads the view only). Migration `0040_session_hours_notice.sql` (0039 was taken by `0039_fx_rate_repair.sql` when this entry was written) adds `master.session_hours_notice` (`market`, `day`, `ours`, `ibkr`, `seen_at`; key `(market, day)`; no `cleared_at`) and the view `rd.session_hours_notice_r1`; `ot_w_master` has INSERT, DELETE and SELECT on the table, `ot_ro_pages` has SELECT on the view and nothing on the table. Tests: `TestReplaceContract` and `TestReaderIsASubsetOfStore` (the contract with a fake), `TestReplaceRunsDeleteAndInsertsInOneTransaction`, `TestReplaceRollsBackWhenAnInsertFails` and `TestMigrationGrants` (no database), and under the build tag `pg` `TestReplaceInsertsAndReadsInOrder`, `TestReplaceTwiceWithSameRowsChangesNothing`, `TestReplaceWithFewerRowsDropsTheMissingDays` and `TestReplaceOfOneMarketLeavesTheOtherAlone`.

`internal/store/strategyresult` declares, in `api.go` only, the store of the generic result table `strategy.result r1` (`docs/design/strategy-framework.md`, Interface and Decisions 4 and 5): `strategyresult.Row` (`SessionDay`, `RunID`, `Strategy`, `RuleVersion`, `ParamHash`, `Key`, `UnderlyingID`, `Status`, `Rank` and `RankInUnderlying` as `*int`, `Legs`, `Checks` and `Facts` as JSON text, `ComputedAt`, `SettingsVersion` as `*int64`; a nil rank stays nil), `strategyresult.Writer` (`InsertResults`: insert-only, key `(session_day, run_id, strategy, key)`, the same key again inserts nothing and is no error, it returns the count inserted), `strategyresult.Reader` (`Results(day, strategy)`: the rows of that strategy and day written by the newest run of the day, ranked rows first), `strategyresult.Store` (both and `Close`) and `strategyresult.OpenFunc`. The table is `strategy.result` and the view is `rd.strategy_result_r1`; the role `ot_w_candidate` (line `OT_PG_DSN_CANDIDATE`) writes and reads, `ot_ro_pages` reads the view only; no new role and no new line. The package imports nothing of `internal/strategy`. The implementation, the migration and the contracts record are later issues. Test: `TestResultStoreFromBothSides` (the contract with a fake).

`internal/store/jobrequest` declares, in `api.go` only, the queue of job requests of the job console (`docs/design/job-console.md#Interface`), split by role: `jobrequest.Reader` (`Recent`, `Get`, `Close`) is reached by the pages role `ot_ro_pages`; `jobrequest.Poster` (`Reader` and `Enqueue`, which answers `EnqueueCreated`, `EnqueueExisting`, `EnqueueWithdrawing` or `EnqueueBusy`, and `Withdraw`) by the web role `ot_w_settings`; `jobrequest.Consumer` (`Queued` oldest first, `Claim`, `Hold`, `Finish`, `FailRunning`, `Close`) by the runner role `ot_runner`. `State` has seven values: `queued`, `running`, `done`, `refused`, `failed`, `interrupted`, `withdrawn`. The openers are `jobrequest.OpenReaderFunc`, `OpenPosterFunc` and `OpenConsumerFunc`, each `func(ctx, dsn) (T, error)`. The package imports neither `internal/runner` nor a driver; the implementation, the tables and the grants are later issues.

## Inputs

- `master.session_day r1` rows (`contracts.SessionDay`: `calendar_id`, `session_day`, `is_session`, `open_at`, `close_at`, `early_close`) to `UpsertSessionDays`.
- A calendar id and two `contracts.Day` values (`YYYY-MM-DD`, market zone) to `SessionDays`.
- A connection string to `sessionday.Open`; a `*sql.DB` and an `fs.FS` of SQL files to `migrate`.
- The administrative DSN and an `fs.FS` of SQL files to `setup.MigrateUp`, which applies them as `ot_owner`; the administrative DSN to `setup.OwnerDSN`, which returns the DSN of the database `optdesk` whose login sets the role `ot_owner`, for `sessionday.Open`.
- `setup.ReadEnv` reads a `$OT_HOME/.env` file; `store.DSNEnvLoader` (`OT_PG_DSN_LOADER`) names the line that holds the DSN of `ot_loader`.
- `contracts.OptionEod` rows to `InsertOptionEod` (key `session_day`, `capture_id`, `instrument_id`); `contracts.QuoteSnapshot` rows to `InsertQuoteSnapshots` (key `session_day`, `capture_id`, `slot`, `instrument_id`).
- An underlying id and two `contracts.Day` values to `OptionEod`; an instrument id and two `contracts.Day` values to `QuoteSnapshots`.
- A connection string to `snapshot.OpenOptionEod` and to `snapshot.OpenQuoteSnapshot`; `store.DSNEnvOptionEod` (`OT_PG_DSN_OPTION_EOD`) and `store.DSNEnvQuoteSnapshot` (`OT_PG_DSN_QUOTE_SNAPSHOT`) name the lines that hold the DSNs of `ot_w_option_eod` and `ot_w_quote_snapshot`.

- An identifier `key`, an `InstrumentSpec` (`Type` stock, index or option; `Currency` three upper-case letters; `PriceIncrement` and `LotSize` decimal text; `Status` defaults to `active`) and extra identifiers to `ResolveInstrument`; instrument ids to `Instruments`; a connection string to `instrument.Open`, from the line `store.DSNEnvMaster` (`OT_PG_DSN_MASTER`) of the role `ot_w_master`.

- Instrument ids (at most 500) to `OptionTerms`; a connection string to `instrument.OpenOptionTerms`, from the line `store.DSNEnvPages` (`OT_PG_DSN_PAGES`) of the role `ot_ro_pages`. A `since` day (`YYYY-MM-DD`, or empty for no lower bound) to `OptionEodLatest`.

## Outputs

- `SessionDays` returns the rows of the calendar with `session_day` between the two days, both ends inclusive, ordered by `session_day`; instants are in UTC; no rows gives an empty slice.
- `OptionEod` returns the rows of the underlying with `session_day` between the two days, both ends inclusive, ordered by `session_day`, `instrument_id` and `capture_id`, and only the picked row of each `session_day` and `instrument_id`: the rows of status ok of one capture, among those whose `snapshot_kind` is `session` (a legacy `eod` row ranks as `session`) if any, else among the `off_session` ones, the one with the greatest `received_at`, then `capture_id`; a key with no ok row returns one row, the newest by `received_at`, then `capture_id`, of its non-ok rows (each key is decided alone), so a later off-session run never hides an earlier in-session row; `QuoteSnapshots` returns the rows of the instrument in the same range ordered by `session_day`, `slot` and `capture_id`; instants are in UTC; no rows gives an empty slice. The views pass every row through; the pick is made by the reader, and `OptionEodLatest` is unchanged.
- The views `rd.option_eod_r1` and `rd.quote_snapshot_r1` name every column of their table and return every row; `ot_runner` and `ot_ro_pages` have SELECT on them, and `ot_ro_pages` has no grant on a base table.
- `ResolveInstrument` returns the id of the instrument that `key` names now (the identifier row with `valid_to IS NULL`), creating it when none exists; the same key always gives the same id. `Instruments` returns the instruments of the ids with the identifiers valid now, ordered by id; an unknown id is absent; `PriceIncrement` and `LotSize` come back as the text the database holds, so a decimal round-trips as given.
- `OptionTerms` returns the version with `valid_to IS NULL` of each id, ordered by `InstrumentID`; an id without a current version is absent; an empty list gives an empty answer and no database call. `Strike` and `Multiplier` are the text the database prints for the numeric (`100` and `100.00` are equal values); `ExpirationDate` is `YYYY-MM-DD`; `ValidFrom` is in UTC. More than 500 ids and an id of 0 are `Permanent`; a database failure is `Retryable`.
- `OptionEodLatest` returns one entry per `underlying_id` with a row of `session_day` on or after `since`, ordered by `UnderlyingID`, with the greatest `session_day` of it; no row gives an empty list; a `since` that is neither empty nor `YYYY-MM-DD` is `Permanent`.
- `InstrumentNames` (`store.InstrumentNameReader`) returns the `InstrumentID`, `Type` and `Name` of each id from the view `rd.instrument_r1` (columns `instrument_id`, `instrument_type`, `name`, `currency`; owner `ot_owner`; `SELECT` granted to `ot_ro_pages` only, nothing in schema `master`; migration `0010`), ordered by `InstrumentID`; an unknown id is absent; an empty list gives an empty answer and no database call; more than 500 ids and an id of 0 are `Permanent`. `instrument.OpenInstrumentNames` takes the line `store.DSNEnvPages`; it is a stub until its own entry fills it.
- `IndexIDs` (`instrument.OpenIndexIDs` returns `*instrument.IndexIDs`: methods `IndexIDs` and `Close`; the line `store.DSNEnvPages`, role `ot_ro_pages`, no migration) returns the `InstrumentID`, `Type` and `Name` of the rows of `rd.instrument_r1` with `instrument_type = 'index'` and a name in the list, ordered by `InstrumentID`; an unknown name is absent, and a name held by two rows gives two rows; an empty list gives an empty answer and no database call; more than 500 names and a name of empty text are `Permanent`. It is declared in `internal/store/instrument`, not in `internal/store/api.go`.
- `LatestReadings` returns the newest rev of each day with `day` between the two days, both ends inclusive, for one `name`, `subject_kind` and `subject`, in any state, ascending by day; no rows gives an empty slice. `InsertReadings` returns the number of readings inserted; a key `(name, version, subject_kind, subject, day)` that exists adds none. `UpsertReadings` (`readingkey.ReadingUpserter`, migration `0045`) runs in one transaction one `INSERT ... ON CONFLICT (name, version, subject_kind, subject, day) DO UPDATE ... WHERE (value, unit, currency, state, reason_code, origin, cutoff, rows_sha256, rev) IS DISTINCT FROM (the new ones) AND NOT (stored state = 'ok' AND new state = 'missing_input') RETURNING 1` per reading: a returned row is written and its inputs, input keys and parameters are deleted and written again, any other is skipped (equal, or a `missing_input` that yields to a stored `ok`); `recorded_at` and `job_run_id` are not compared; the call returns written and skipped counts, makes no call for an empty list, and a key twice in one call is a `Permanent` error before any statement.
- `PriceBars` returns the winner rows: for each day the row of the highest epoch (`AdjustEpoch`) of the instrument and basis, ascending by day, both ends inclusive; no rows gives an empty slice. `FxRates` returns the rates in the range ascending by day. `LatestFxRate` returns the rate of the newest day on or before `asOf`; when none exists it answers not found (`found` false, no error): there is no fallback to a default or a later day.
- Errors are `contracts.TypedError`: `Retryable` when the database fails, `Permanent` for a malformed day.

## Invariants

- `obs.price_bar` is upserted by `barpg.Store.UpsertPriceBars` (`bar.PriceBarUpserter`; migration `0041_price_bar_repair.sql`, `docs/design/data-repair-bars.md` Decisions 1 to 6): the key is `(instrument_id, basis, session_day)` with no epoch (`adjust_epoch` stays as a column, `DEFAULT 1`, written by no code), one transaction per call, one `INSERT ... ON CONFLICT (instrument_id, basis, session_day) DO UPDATE` per row that sets the prices, `volume`, `currency`, `source`, `status = 'ok'`, `updated_at` and `written_by` only when the stored values (numeric equality, so `100.50` equals `100.5`) or status differ, and returns written (rows inserted or replaced) and unchanged (rows given minus written); a row stored `void` or `no_value` and answered with a value is replaced; `received_at` and the key are never changed and no old value is kept. The prices and volume are `numeric`, the four prices are checked positive unless `status = 'no_value'` and may be NULL; the table has `status`, `updated_at` and `written_by`; the view `rd.price_bar_r1` keeps its twelve columns (numbers as text) and shows only `status = 'ok'`, one row per key. `ot_w_bar` has table-level INSERT, UPDATE on the columns `open`, `high`, `low`, `close`, `volume`, `currency`, `source`, `status`, `updated_at` and `written_by`, and SELECT on the columns `instrument_id`, `basis`, `session_day`, `open`, `high`, `low`, `close`, `volume`, `currency`, `source` and `status`; it has no DELETE, no TRUNCATE and no UPDATE of the key, `received_at` or `adjust_epoch`. `InsertPriceBars` stays (one transaction per call, a key that exists is left as it is). `obs.fx_rate` is upserted by `barpg.Store.UpsertFxRates` (`bar.FxRateUpserter`; migration `0039_fx_rate_repair.sql`, `docs/design/data-repair-fx.md`): one transaction per call, one `INSERT ... ON CONFLICT (pair, rate_day) DO UPDATE` per row that sets `rate`, `source`, `status = 'ok'`, `updated_at` and `written_by` only when the stored rate (numeric equality, so `153.425` equals `153.4250`), source or status differs, and returns written (rows inserted or replaced) and unchanged (rows given minus written); a row stored `void` or `no_value` and answered with a rate is replaced; `received_at` and the key are never changed and no old value is kept. The table has `status` (`ok`, `no_value`, `void`), `updated_at` and `written_by` and a numeric `rate`; the view `rd.fx_rate_r1` keeps its five columns and shows only `status = 'ok'`. `ot_w_bar` has table-level INSERT, UPDATE on the columns `rate`, `source`, `status`, `updated_at` and `written_by`, and SELECT on the columns `pair`, `rate_day`, `rate`, `source` and `status`; it has no DELETE, no TRUNCATE and no UPDATE of the key or `received_at`.
- `obs.series_point` is keyed `(series_id, observation_date)` (migration `0043_series_registry.sql`, `docs/design/series-registry.md` Decisions 1 to 5, 10, 11). `seriesStore.UpsertSeriesPoints` (`seriesdef.SeriesUpserter`) runs one `INSERT ... ON CONFLICT (series_id, observation_date) DO UPDATE` per row in one transaction, after the sentinel screen (`-1`, NaN and infinities are stored as NULL with `sentinel_rejected`): a stored row is replaced only when its value, status, unit, currency or source differs, a `no_value` row never replaces a `present` one, and the call returns written and unchanged counts and does nothing for an empty list; `updated_at` and `written_by` follow the replaced row and no old value is kept. `FillSeriesPoints` (`seriesdef.SeriesFiller`) is the same statement that replaces only a stored `no_value` or `void` row, so a backup source never overwrites a `present` value. `InsertSeriesPoints` stays insert-only (a date that exists is left as it is). `ActiveSeries` (`seriesdef.SeriesRegistry`) reads `obs.series_definition WHERE active`. The migration keeps only the newest `realtime_start` of each date and adds `updated_at` and `written_by` to the points, and to `obs.series_definition` the registry columns `title`, `category`, `frequency`, `source`, `source_series_id`, `secondary_source`, `seasonal_adjustment`, `first_observation` and `active` (it fills the 12 series of the job and adds `BAMLC0A0CM`, `BAA10Y`, `SOFR` and `WRESBAL`). The view `rd.series_point_r1` keeps its eleven columns, its owner and its grants and hides `status = 'void'`. `ot_w_series_fred` keeps INSERT on both tables and has UPDATE on the columns `value`, `status`, `unit`, `currency`, `realtime_start`, `realtime_end`, `published_at`, `source`, `source_revision`, `updated_at` and `written_by` of `obs.series_point`, SELECT on its columns `series_id`, `observation_date`, `value`, `status`, `unit`, `currency`, `realtime_start`, `realtime_end`, `published_at`, `source` and `source_revision`, and SELECT on `obs.series_definition`; it has no DELETE, no TRUNCATE and no UPDATE of the key.
- `UpsertSessionDays` is `ON CONFLICT (calendar_id, session_day) DO UPDATE`, runs in one transaction (all rows or none), and does nothing for an empty input.
- The caller's context is passed to every database call.
- The SQL names the six columns of the table and never uses `SELECT *`.
- `obs.option_eod` and `obs.quote_snapshot` are append-only: the insert is `ON CONFLICT DO NOTHING` in one transaction per call, no database call is made for an empty input, and no role but the owner may UPDATE, DELETE or TRUNCATE. A retry of the same capture (same `capture_id` and instrument) adds no row and keeps the first one; a better observation is a new capture with a new `capture_id`, a different key that the first never blocks.
- Sentinel rule, per column: the writer stores NULL for -1, NaN or an infinity in any numeric column, `delta` and `theta_per_calendar_day` included (a real -1.0 is lost), keeps the `status` the caller set and the other columns of the row, and never rejects a row as a whole. The migration's CHECKs repeat the rule: no NaN or infinity anywhere, no -1 in IV, gamma and vega, and prices, sizes, volume, open interest and underlying price at least 0; `delta` and `theta_per_calendar_day` allow -1 in the CHECK.
- `ot_w_option_eod` and `ot_w_quote_snapshot` (LOGIN, made by `setup.Setup`) each have `USAGE` on schemas `obs` and `ops`, `INSERT` on their own table only and `SELECT, REFERENCES` on `ops.capture_run` (`migrations/0006_option_eod.sql`, `migrations/0007_quote_snapshot.sql`), plus CONNECT on the database. They have no SELECT on their table and no write on `ops`: no UPDATE, DELETE or TRUNCATE anywhere.
- `ops.dataset_window` needs no row of its own for the two datasets: `PutWindow` writes it for a dataset as soon as a job plans a key with its `DatasetID`, and no migration seeds it.
- `capture_id` is a uuid with no foreign key yet; `underlying_id`, `instrument_id` and `terms_version_id` are `bigint`; since `0008` the first two (and `instrument_id` of `obs.quote_snapshot`) point at `master.instrument`, `terms_version_id` has no key.
- On a database made before `0006`, `ot setup pg` must run before `ot migrate`: `0006` and `0007` fail when the role `ot_w_option_eod` or `ot_w_quote_snapshot` is missing. Both tables are hypertables and need the timescaledb extension that `Setup` creates.
- `session_day` is the market-zone date, not a UTC date.
- Only files under `internal/store/` import pgx.

Its errors for a parse, connect, role or schema step are of fixed text and hold no DSN.

- The view `rd.session_day_r1` (migration `0028_session_day_view.sql`; the six columns of `master.session_day`, owner `ot_owner`) is what `sessionday.Reader` reads for its three readers: `ot_ro_pages`, `ot_runner` and `ot_loader` have `SELECT` on it. `ot_ro_pages` has no `USAGE` on schema `master` and no grant on the table. `0028` gives `ot_loader` `GRANT USAGE ON SCHEMA rd TO ot_loader;` (the other two have it from `0002`); Down drops the view and revokes that `USAGE` only. No key column is updatable, and there is no DELETE, TRUNCATE or grant on another schema than `master` and `rd`.

- `Setup` sends a SCRAM-SHA-256 verifier to the server and never a plain password; the plain password is only in `.env`.
- The verifier is built with 16 random bytes of salt, 4096 iterations and no SASLprep (passwords are ASCII and made by `Setup`).
- `setup.MigrateUp` logs migration names only, never the DSN, a password, a verifier or a pgx error.
- On a database made before `0005`, `ot setup pg` must run before `ot migrate`: `0005` fails when the role `ot_loader` is missing.
- Migration naming and order: a design entry names its migration `migrations/NNNN_<name>.sql` with NNNN the next free number at cut time; acceptance greps use the glob `migrations/*_<name>.sql`. `setup.MigrateUp` applies out of order (`goose.WithAllowOutofOrder(true)`): a lower version that lands after a higher one is applied on a database that already has the higher ones, because each module's migration is its own schema, tables, views and grants and the shared prerequisites are `0002` to `0006`. A duplicate version is caught by the pg job (goose refuses two files with one version) and the worker renames the file.

- `ResolveInstrument` runs in one transaction that first takes `pg_advisory_xact_lock(hashtext(scheme || ':' || value))` over the key, then looks the key up, and on a miss inserts the instrument (`recorded_at` and `valid_from` are the database's `now()`) and the identifiers `key` and `extra`. It never closes an identifier. For a new `option` whose `extra` holds an `osi` identifier of 21 characters (symbol padded to 6, `yymmdd` in 2000 to 2099, `C` or `P`, strike times 1000 in 8 digits) it also inserts the current row of `master.option_terms` in the same transaction: `right`, `strike` and `expiration_date` from the `osi`, `strike_currency` from `Currency`, `multiplier` from `LotSize`, and the text `unknown` for `exercise_style` and `settlement_type`. The insert runs between `SAVEPOINT option_terms` and `RELEASE SAVEPOINT option_terms` with `ON CONFLICT (instrument_id) WHERE valid_to IS NULL DO NOTHING`; on any error the transaction does `ROLLBACK TO SAVEPOINT option_terms` and commits, so the call still returns the id and a nil error and the option has no terms row. After the transaction has committed, that rollback writes one `WARN` line through the store's logger (`slog.Default()` unless a test sets one): message `option terms insert rolled back`, attributes `component=store`, `status=rolled_back`, `instrument_id=<n>` and `err=<class>`, where `err` is the SQLSTATE of the error (for example `42501`) or `other` when it has none, never an error text, because a database message can carry values. A terms insert skipped by `ON CONFLICT DO NOTHING` is not a failure and is not logged; nor is a call whose transaction fails. The same holds for an `osi` that does not parse, a type other than `option`, an option with no `osi` and an existing key: no terms statement, no error. An `osi` that already names another instrument (an SPX and an SPXW option, or an adjusted one, give the same `osi`) is a `Permanent` error as before. The table is versioned and the code never updates it: a later correction of the `unknown` defaults closes the row by setting `valid_to` and inserts a new version. Options that exist before the writer has no row (no backfill). An `extra` identifier that already names an instrument is a `Permanent` error and nothing is written; so is an unknown scheme, an empty value, a `Type` outside the three, a `Currency` that is not three upper-case letters or a decimal that does not parse, all before any statement.

A row is written at run start as `not_finished` for a name with no row; `Expected` is set once (a non-empty value is never replaced); a re-run writes a reason only when `Listed` is below `Expected`.
- A watched US stock with no run row is a gap: the run did not reach it or died before writing.
- Tests: `internal/store/openquote/api_test.go`: `TestOptionListPutAndReadBack`.
- `ListRecord` also carries the confirmed band (`docs/design/option-open-gap-jp.md`, entry 1): `BandLo` and `BandHi` (decimal text; empty means none stored), `Sigma`, `SigmaSource` (`iv`, `rv20` or `default`) and `InBand` (int); `ListedAt` is as before. Tests: `TestListRecordBandRoundTrip`, `TestListRecordBandEmptyIsNone`.

## Instrument, stock and company

Migration `0044_instrument_company.sql` (docs/design/instrument-company.md, entry 2; it holds the auto-deploy: rebuild `ot`, `ot setup pg`, migrate, `ot setup pg` again). The old binary keeps working on the migrated tables: `symbol` has a default and the old insert is unchanged.

- Tables: `master.instrument` gains `symbol text NOT NULL DEFAULT ''` (a check: a JPY instrument's symbol has no dot) and its `issuer_id` a foreign key to `master.issuer`; `master.stock (instrument_id, name, market US|JP|EU or NULL, primary_exchange, issuer_id, sector_fund)`, one row per stock, etf or index; `master.issuer (issuer_id, name, country, cik, edinet_code)`, one of the two codes set, each unique where set. The `issuer_id` of the instrument and of the stock are one value.
- Schemes of `master.instrument_identifier`: `ibkr_conid`, `osi`, `ticker_exchange`, `jpx_option_code`, `isin`, `cusip`, `figi`, `sym_fred`, `sym_alphavantage`, `sym_jquants`, `sym_sec`, `sym_eodhd`; a unique index allows one current row (`valid_to IS NULL`) per instrument and scheme. A missing row means the source does not have the value.
- Views, read by `ot_ro_pages` and `ot_runner`: `rd.stock (instrument_id, symbol, name, market, primary_exchange, currency, mic, sector_fund, issuer_id, issuer_name)` and `rd.option (instrument_id, symbol, currency, underlying_id, underlying_symbol, expiry, strike, "right", multiplier, trading_class, exchange)`; an option without a `master.option_contract` row has NULL underlying columns.
- Grants: `ot_w_master` has SELECT, INSERT and UPDATE on `master.stock` and `master.issuer` and UPDATE on `master.instrument` (`symbol`, `issuer_id`); no DELETE, no TRUNCATE, and no close of an identifier row.
- Backfill (Decision 7): symbol from the name (the osi identifier for an option); a stock row per stock, etf or index with the market from the currency (NULL for a currency other than USD, JPY or EUR) and the name, exchange and issuer of the newest `settings.underlying` row whose con_id is the instrument's `ibkr_conid` (the smaller `name_key` when two match). The migration stops on a duplicate current identifier or a JPY symbol with a dot.
- Writers: `internal/store/instrument` `ResolveInstrument` sets `symbol` and inserts the stock row of a new stock or index and repairs an empty symbol once on a hit (its signature is unchanged; a JPY symbol with a dot is Permanent); `RegisterStock` (`stockreg.StockRegistrar`) writes the stock side and the issuer, finds the issuer by `cik` or `edinet_code`, refuses a registration whose two codes name two issuer rows (Permanent, nothing written), and writes nothing for equal input; `LookupStock` and `Identifier` (`stockreg.StockDirectory`) read by symbol and market (an empty market is never found; two stocks are a Permanent error naming both ids) and by scheme.

## Run view

`internal/store/runview/api.go` declares, in a package of its own (`internal/store/api.go` is at its ceiling), `Row` (session day, dataset, key, status, finished at, returned and usable counts, error code, reason code), `Reason` (day, dataset, subject, scope, code, detail, at), `Reader` and `ReasonWriter`. `Reader.RunsOn(ctx, day)` and `ReasonsOn(ctx, day)` return the rows of a session day ascending, never nil; `NotWired(ctx)` returns the reasons stored under the constant `NotWiredDay` (the date `1970-01-01`) and the dataset `ops.not_wired` (`NotWiredDataset`), ascending by scope, never nil. `ReasonWriter.ReplaceReasons(ctx, day, dataset, subject, reasons)` replaces the whole set of that day, dataset and subject in one transaction, so a clean run (no reasons) clears an earlier reason and another subject is untouched. Declarations only: no migration and no Postgres code yet. Tests: `internal/store/runview/api_test.go`: `TestRunviewContractBothSides`, `TestReasonsOnNeverNil`, `TestReplaceReasonsClearsOld`.
