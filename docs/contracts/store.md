# store contract

## Responsibility

The only module that opens the database. `store.SessionDayWriter` upserts and `store.SessionDayReader` reads `master.session_day r1` rows; `sessionday.Open` returns both with `Close` as a `store.SessionDayStore`. `internal/store/migrate` applies goose SQL migrations from an `fs.FS` the caller supplies; it embeds none.

`internal/store/snapshot` holds the Reader and the Writer of two append-only datasets, `obs.option_eod r1` (one option contract on one session day, frozen after the close) and `obs.quote_snapshot r1` (a planned time slot of quotes). Neither can be obtained again once the day has gone, so both tables are permanent. `snapshot.OpenOptionEod` returns a `store.OptionEodStore` and `snapshot.OpenQuoteSnapshot` a `store.QuoteSnapshotStore`, each with `Close`.

`internal/store/instrument` holds the instrument tables' store: `master.instrument` (one row per instrument, `instrument_id` generated by the database) and `master.instrument_identifier` (the names of an instrument: schemes `ibkr_conid`, `osi`, `ticker_exchange`, `jpx_option_code`, `isin`; key `(scheme, value, valid_from)`; `valid_to` NULL while valid), made by migration `0008`. `instrument.Open` returns a `store.InstrumentStore`: the resolver `ResolveInstrument` and the reader `Instruments`, with `Close`.

`master.option_terms` (migration `0009`) holds one row per version of the terms of one option, and the view `rd.option_terms_r1` shows the current version of each. `instrument.OpenOptionTerms` returns a `store.OptionTermsStore`: the reader `OptionTerms`, with `Close`. `store.OptionEodCatalog` (`OptionEodLatest`) lists the underlyings that have rows of `obs.option_eod` and the greatest `session_day` of each, read from `rd.option_eod_r1`; it is declared in `internal/store/api.go` and implemented by its own entry.

`internal/store/reading` holds the Reader and the Writer of stored figure values, `readings.reading` r1 (with the children `reading_input`, `reading_input_key` and `reading_parameter`). `reading.Open` returns a `store.ReadingStore` (`InsertReadings`, `LatestReadings`, `Close`) from the line `store.DSNEnvReadings` (`OT_PG_DSN_READINGS`) of the role `ot_w_readings`.

`internal/store/bar` declares, in `api.go` only (no implementation in the package), the store of two append-only datasets: `obs.price_bar r1` (daily bars, `trades` and `adjusted_last`) and `obs.fx_rate r1` (the daily USD.JPY rate). `bar.BarStore` is `PriceBarWriter`, `PriceBarReader`, `FxRateWriter`, `FxRateReader` and `Close`; `bar.OpenBarFunc` opens it from the line `bar.DSNEnvBar` (`OT_PG_DSN_BAR`) of the role `ot_w_bar`. The implementation is `internal/store/barpg`.
`internal/store/ownerset` declares, in `api.go` only, the owner's settings store: `ownerset.Reader` (`Params`, `Exclusions`, `History`, `Version`, `Close`, all read as of a time), `ownerset.Writer` (`Apply` of a `Change`, one transaction, unchanged fields insert nothing), `ownerset.Store` (both) and `ownerset.OpenFunc`, from the line `ownerset.DSNEnvSettings` (`OT_PG_DSN_SETTINGS`). Design: `docs/design/settings-form.md#Interface`.

`internal/store/mark` declares, in `api.go` only, the store of position marks, `account.position_mark r1` (insert-only, one row per position of a capture, key `(capture_id, con_id, attempt)`). `mark.Writer.WriteMarks` writes the rows in one transaction and leaves a row whose key exists as it is (a correction is a row with a higher `Attempt`); `mark.Reader.Marks(alias, day)` returns the rows of the newest capture of that day that has marks, the highest `Attempt` of each `ConID`, sorted by `ConID`, an empty slice when none. `mark.Store` is both with `Close`; `mark.OpenFunc` opens it from the line `mark.DSNEnvPositionMark` (`OT_PG_DSN_POSMARK`) of the role `ot_w_posmark`. The implementation is `internal/store/markpg`: `markpg.Open` (a `mark.OpenFunc`) writes the table `account.position_mark` (migration `0026_position_mark.sql`; primary key `(capture_id, con_id, attempt)`, `basis` one of `mid`, `last`, `close`, `none`) with `ON CONFLICT DO NOTHING` in one transaction and reads the view `rd.account_position_mark_r1` only. The role `ot_w_posmark` (made by `setup.Setup`, eighteen roles in all) has INSERT and SELECT on the table, SELECT on the view and USAGE on the schemas `account` and `rd`; `ot_ro_pages` has SELECT on the view and nothing on the table; no role but the owner has UPDATE, DELETE or TRUNCATE. `store/setup` writes the literal `OT_PG_DSN_POSMARK` because it may not import `store/mark`.

`internal/store/openquote` declares, in `api.go` only, the stores of the option open pull (`docs/design/option-open-pull.md`): `OptionOpenWriter` (`InsertOptionOpen`: one transaction, `ON CONFLICT DO NOTHING` on `(session_day, capture_id, slot, instrument_id)`, -1, NaN and infinity stored as null, a row of slot `SlotRefresh` refused as a Permanent error: a refresh row is never stored) and `OptionOpenReader` (`OptionOpen(day)`: the newest row of each instrument, by `received_at`, from the view `rd.option_open_r1`), `OptionOpenPlanStore` (`PutPlan`; `Plan(day, slot, underlyingIDs...)`: the items of the latest plan, by `planned_at`, of each underlying, from the view `rd.option_open_item_r1`), `OptionNotListedStore` (`AddNotListed` replaces a mark of the same key; `NotListed(now)` lists the marks whose `retry_at` is after `now`; `RemoveNotListed`, `RemoveNotListedByUnderlying`, `RemoveNotListedExpired`), `OptionContractStore` (`PutOption` and `ListOptions` over `master.option_contract`, the one lookup from a contract identity: underlying id, currency, exchange, trading class, multiplier, expiry, strike text and right, to its instrument id) and `Stores`, all of them with `Close`; `SlotRefresh` is the one declaration of the refresh marker and `DSNEnvOptionOpen` (`OT_PG_DSN_OPTION_OPEN`) names the line of the role `ot_w_option_open`. The implementation is `internal/store/optionopenpg` (`Open`, an `openquote.OpenFunc`), over migrations `0029_option_open.sql` (`obs.option_open`, a hypertable on `session_day`, and `rd.option_open_r1`), `0030_option_open_plan.sql` (`plan.option_open_item` and `rd.option_open_item_r1`), `0031_option_not_listed.sql` and `0032_option_contract.sql`. The role `ot_w_option_open` (made by `setup.Setup`, nineteen roles in all) has INSERT on `obs.option_open` and `plan.option_open_item`, SELECT on the two views, INSERT, UPDATE, DELETE and SELECT on `master.option_not_listed`, INSERT, UPDATE and SELECT on `master.option_contract`, and USAGE on the schemas `obs`, `plan`, `master` and `rd`; it has no SELECT on `obs.option_open` or `plan.option_open_item`. `ot_ro_pages` has SELECT on the two views and no grant on a base table (`ot serve` reads both views, with the pages line, and calls only the readers). No role but the owner has UPDATE, DELETE or TRUNCATE on `obs.option_open` and `plan.option_open_item`. `store/setup` writes the literal `OT_PG_DSN_OPTION_OPEN` because it may not import `store/openquote`.

## Inputs

- `master.session_day r1` rows (`contracts.SessionDay`: `calendar_id`, `session_day`, `is_session`, `open_at`, `close_at`, `early_close`) to `UpsertSessionDays`.
- A calendar id and two `contracts.Day` values (`YYYY-MM-DD`, market zone) to `SessionDays`.
- A connection string to `sessionday.Open`; a `*sql.DB` and an `fs.FS` of SQL files to `migrate`.
- The administrative DSN and an `fs.FS` of SQL files to `setup.MigrateUp`, which applies them as `ot_owner`; the administrative DSN to `setup.OwnerDSN`, which returns the DSN of the database `optdesk` whose login sets the role `ot_owner`, for `sessionday.Open`.
- `setup.ReadEnv` reads a `$OT_HOME/.env` file; `store.DSNEnvLoader` (`OT_PG_DSN_LOADER`) names the line that holds the DSN of `ot_loader`.
- `contracts.OptionEod` rows to `InsertOptionEod` (key `session_day`, `capture_id`, `instrument_id`); `contracts.QuoteSnapshot` rows to `InsertQuoteSnapshots` (key `session_day`, `capture_id`, `slot`, `instrument_id`).
- An underlying id and two `contracts.Day` values to `OptionEod`; an instrument id and two `contracts.Day` values to `QuoteSnapshots`.
- A connection string to `snapshot.OpenOptionEod` and to `snapshot.OpenQuoteSnapshot`; `store.DSNEnvOptionEod` (`OT_PG_DSN_OPTION_EOD`) and `store.DSNEnvQuoteSnapshot` (`OT_PG_DSN_QUOTE_SNAPSHOT`) name the lines that hold the DSNs of `ot_w_option_eod` and `ot_w_quote_snapshot`.

- An identifier `key`, an `InstrumentSpec` (`Type` stock, index or option; `Currency` three upper-case letters; `PriceIncrement` and `LotSize` decimal text; `Status` defaults to `active`) and extra identifiers to `ResolveInstrument`; instrument ids to `Instruments`; a connection string to `instrument.Open`, from the line `store.DSNEnvMaster` (`OT_PG_DSN_MASTER`) of the role `ot_w_master`.

- Instrument ids (at most 500) to `OptionTerms`; a connection string to `instrument.OpenOptionTerms`, from the line `store.DSNEnvPages` (`OT_PG_DSN_PAGES`) of the role `ot_ro_pages`. A `since` day (`YYYY-MM-DD`, or empty for no lower bound) to `OptionEodLatest`.

## Outputs

- `SessionDays` returns the rows of the calendar with `session_day` between the two days, both ends inclusive, ordered by `session_day`; instants are in UTC; no rows gives an empty slice.
- `OptionEod` returns the rows of the underlying with `session_day` between the two days, both ends inclusive, ordered by `session_day`, `instrument_id` and `capture_id`; `QuoteSnapshots` returns the rows of the instrument in the same range ordered by `session_day`, `slot` and `capture_id`; instants are in UTC; no rows gives an empty slice. Every capture of a key is returned, because the views pass every row through.
- The views `rd.option_eod_r1` and `rd.quote_snapshot_r1` name every column of their table and return every row; `ot_runner` and `ot_ro_pages` have SELECT on them, and `ot_ro_pages` has no grant on a base table.
- `ResolveInstrument` returns the id of the instrument that `key` names now (the identifier row with `valid_to IS NULL`), creating it when none exists; the same key always gives the same id. `Instruments` returns the instruments of the ids with the identifiers valid now, ordered by id; an unknown id is absent; `PriceIncrement` and `LotSize` come back as the text the database holds, so a decimal round-trips as given.
- `OptionTerms` returns the version with `valid_to IS NULL` of each id, ordered by `InstrumentID`; an id without a current version is absent; an empty list gives an empty answer and no database call. `Strike` and `Multiplier` are the text the database prints for the numeric (`100` and `100.00` are equal values); `ExpirationDate` is `YYYY-MM-DD`; `ValidFrom` is in UTC. More than 500 ids and an id of 0 are `Permanent`; a database failure is `Retryable`.
- `OptionEodLatest` returns one entry per `underlying_id` with a row of `session_day` on or after `since`, ordered by `UnderlyingID`, with the greatest `session_day` of it; no row gives an empty list; a `since` that is neither empty nor `YYYY-MM-DD` is `Permanent`.
- `InstrumentNames` (`store.InstrumentNameReader`) returns the `InstrumentID`, `Type` and `Name` of each id from the view `rd.instrument_r1` (columns `instrument_id`, `instrument_type`, `name`, `currency`; owner `ot_owner`; `SELECT` granted to `ot_ro_pages` only, nothing in schema `master`; migration `0010`), ordered by `InstrumentID`; an unknown id is absent; an empty list gives an empty answer and no database call; more than 500 ids and an id of 0 are `Permanent`. `instrument.OpenInstrumentNames` takes the line `store.DSNEnvPages`; it is a stub until its own entry fills it.
- `LatestReadings` returns the newest rev of each day with `day` between the two days, both ends inclusive, for one `name`, `subject_kind` and `subject`, in any state, ascending by day; no rows gives an empty slice. `InsertReadings` returns the number of readings inserted; a key that exists adds none.
- `PriceBars` returns the winner rows: for each day the row of the highest epoch (`AdjustEpoch`) of the instrument and basis, ascending by day, both ends inclusive; no rows gives an empty slice. `FxRates` returns the rates in the range ascending by day. `LatestFxRate` returns the rate of the newest day on or before `asOf`; when none exists it answers not found (`found` false, no error): there is no fallback to a default or a later day.
- Errors are `contracts.TypedError`: `Retryable` when the database fails, `Permanent` for a malformed day.

## Invariants

- `obs.price_bar` and `obs.fx_rate` are insert-only: `InsertPriceBars` and `InsertFxRates` are one transaction per call, a key that exists is left as it is, and a restated day is a new row under the next epoch.
- `UpsertSessionDays` is `ON CONFLICT (calendar_id, session_day) DO UPDATE`, runs in one transaction (all rows or none), and does nothing for an empty input.
- The caller's context is passed to every database call.
- The SQL names the six columns of the table and never uses `SELECT *`.
- `obs.option_eod` and `obs.quote_snapshot` are append-only: the insert is `ON CONFLICT DO NOTHING` in one transaction per call, no database call is made for an empty input, and no role but the owner may UPDATE, DELETE or TRUNCATE. A retry of the same capture (same `capture_id` and instrument) adds no row and keeps the first one; a better observation is a new capture with a new `capture_id`, a different key that the first never blocks.
- Sentinel rule, per column: the writer stores NULL for -1, NaN or an infinity in any numeric column, `delta` and `theta_per_calendar_day` included (a real -1.0 is lost), keeps the `status` the caller set and the other columns of the row, and never rejects a row as a whole. The migration's CHECKs repeat the rule: no NaN or infinity anywhere, no -1 in IV, gamma and vega, and prices, sizes, volume, open interest and underlying price at least 0; `delta` and `theta_per_calendar_day` allow -1 in the CHECK.
- `ot_w_option_eod` and `ot_w_quote_snapshot` (LOGIN, made by `setup.Setup`) each have `USAGE` on schemas `obs` and `ops`, `INSERT` on their own table only and `SELECT, REFERENCES` on `ops.capture_run` (`migrations/0006_option_eod.sql`, `migrations/0007_quote_snapshot.sql`), plus CONNECT on the database. They have no SELECT on their table and no write on `ops`: no UPDATE, DELETE or TRUNCATE anywhere.
- `ops.dataset_window` needs no row of its own for the two datasets: `PutWindow` writes it for a dataset as soon as a job plans a key with its `DatasetID`, and no migration seeds it.
- `capture_id` is a uuid with no foreign key yet; `underlying_id`, `instrument_id` and `terms_version_id` are `bigint`; since `0008` the first two (and `instrument_id` of `obs.quote_snapshot`) point at `master.instrument`, `terms_version_id` has no key.
- On a database made before `0006`, `ot setup pg` must run before `ot migrate`: `0006` and `0007` fail when the role `ot_w_option_eod` or `ot_w_quote_snapshot` is missing. Both tables are hypertables and need the timescaledb extension that `Setup` creates.
- `session_day` is the market-zone date, not a UTC date.
- Only files under `internal/store/` import pgx.
- `setup.MigrateUp` runs `SET ROLE ot_owner` as the first statement of its one connection, then `SET search_path TO meta` and `CREATE SCHEMA IF NOT EXISTS meta`; the goose version table is `meta.goose_db_version`, owned by `ot_owner`. Its errors for a parse, connect, role or schema step are of fixed text and hold no DSN.
- `ot_runner` has SELECT on `master.session_day` and nothing else there (`migrations/0004_session_day_grant.sql`).
- The view `rd.session_day_r1` (migration `0028_session_day_view.sql`; the six columns of `master.session_day`, owner `ot_owner`) is what `sessionday.Reader` reads for its three readers: `ot_ro_pages`, `ot_runner` and `ot_loader` have `SELECT` on it. `ot_ro_pages` has no `USAGE` on schema `master` and no grant on the table. `0028` gives `ot_loader` `GRANT USAGE ON SCHEMA rd TO ot_loader;` (the other two have it from `0002`); Down drops the view and revokes that `USAGE` only. The writer keeps the table.
- `ot_loader` (LOGIN, no other attribute) is made by `setup.Setup`; its grants are exactly `GRANT USAGE ON SCHEMA master TO ot_loader;`, `GRANT SELECT, INSERT ON master.session_day TO ot_loader;` and `GRANT UPDATE (is_session, open_at, close_at, early_close) ON master.session_day TO ot_loader;` (`migrations/0005_session_day_loader.sql`), `GRANT USAGE ON SCHEMA rd TO ot_loader;` and `GRANT SELECT ON rd.session_day_r1 TO ot_loader;` (`migrations/0028_session_day_view.sql`), plus CONNECT on the database. No key column is updatable, and there is no DELETE, TRUNCATE or grant on another schema than `master` and `rd`.
- The Down part of `0005` only REVOKEs; no migration drops the role.
- `Setup` sends a SCRAM-SHA-256 verifier to the server and never a plain password; the plain password is only in `.env`.
- The verifier is built with 16 random bytes of salt, 4096 iterations and no SASLprep (passwords are ASCII and made by `Setup`).
- `setup.MigrateUp` logs migration names only, never the DSN, a password, a verifier or a pgx error.
- On a database made before `0005`, `ot setup pg` must run before `ot migrate`: `0005` fails when the role `ot_loader` is missing.
- Migration naming and order: a design entry names its migration `migrations/NNNN_<name>.sql` with NNNN the next free number at cut time; acceptance greps use the glob `migrations/*_<name>.sql`. `setup.MigrateUp` applies out of order (`goose.WithAllowOutofOrder(true)`): a lower version that lands after a higher one is applied on a database that already has the higher ones, because each module's migration is its own schema, tables, views and grants and the shared prerequisites are `0002` to `0006`. A duplicate version is caught by the pg job (goose refuses two files with one version) and the worker renames the file.

- `ResolveInstrument` runs in one transaction that first takes `pg_advisory_xact_lock(hashtext(scheme || ':' || value))` over the key, then looks the key up, and on a miss inserts the instrument (`recorded_at` and `valid_from` are the database's `now()`) and the identifiers `key` and `extra`. It never closes an identifier. For a new `option` whose `extra` holds an `osi` identifier of 21 characters (symbol padded to 6, `yymmdd` in 2000 to 2099, `C` or `P`, strike times 1000 in 8 digits) it also inserts the current row of `master.option_terms` in the same transaction: `right`, `strike` and `expiration_date` from the `osi`, `strike_currency` from `Currency`, `multiplier` from `LotSize`, and the text `unknown` for `exercise_style` and `settlement_type`. The insert runs between `SAVEPOINT option_terms` and `RELEASE SAVEPOINT option_terms` with `ON CONFLICT (instrument_id) WHERE valid_to IS NULL DO NOTHING`; on any error the transaction does `ROLLBACK TO SAVEPOINT option_terms` and commits, so the call still returns the id and a nil error and the option has no terms row. After the transaction has committed, that rollback writes one `WARN` line through the store's logger (`slog.Default()` unless a test sets one): message `option terms insert rolled back`, attributes `component=store`, `status=rolled_back`, `instrument_id=<n>` and `err=<class>`, where `err` is the SQLSTATE of the error (for example `42501`) or `other` when it has none, never an error text, because a database message can carry values. A terms insert skipped by `ON CONFLICT DO NOTHING` is not a failure and is not logged; nor is a call whose transaction fails. The same holds for an `osi` that does not parse, a type other than `option`, an option with no `osi` and an existing key: no terms statement, no error. An `osi` that already names another instrument (an SPX and an SPXW option, or an adjusted one, give the same `osi`) is a `Permanent` error as before. The table is versioned and the code never updates it: a later correction of the `unknown` defaults closes the row by setting `valid_to` and inserts a new version. Options that exist before the writer has no row (no backfill). An `extra` identifier that already names an instrument is a `Permanent` error and nothing is written; so is an unknown scheme, an empty value, a `Type` outside the three, a `Currency` that is not three upper-case letters or a decimal that does not parse, all before any statement.
- Migration `0008` adds the foreign keys `obs.option_eod.instrument_id`, `obs.option_eod.underlying_id` and `obs.quote_snapshot.instrument_id` to `master.instrument(instrument_id)`; compression of both hypertables is switched off while they are added and on again with the settings of `0006` and `0007`, the tables being empty. `0008` fails when the role `ot_w_master` is missing: `ot setup pg` must run before `ot migrate`.
- `ot_w_master` (LOGIN, made by `setup.Setup`) has `USAGE` on schema `master` and `SELECT, INSERT` on the two tables: no UPDATE, DELETE or TRUNCATE. `ot_ro_pages` and `ot_runner` have `SELECT` on both tables and no other grant from `0008`.

- `master.option_terms` (migration `0009`): `terms_version_id` (identity primary key), `instrument_id` (not null, foreign key to `master.instrument`), `right` (`char(1)`, `C` or `P`), `strike`, `strike_currency` (`char(3)`), `multiplier`, `expiration_date`, `exercise_style`, `settlement_type`, `valid_from` (all not null) and `valid_to` (null while current). The unique partial index `option_terms_current` on `instrument_id` where `valid_to IS NULL` allows one current row per instrument and any number of closed ones.
- `rd.option_terms_r1` names every column and has `WHERE valid_to IS NULL`; table and view belong to `ot_owner`. `ot_ro_pages` has `USAGE` on schema `rd` and `SELECT` on the view, nothing on schema `master`, no write; the view runs with its owner's rights. `0009` grants nothing to `ot_w_master`; `0011` grants `ot_w_master` `INSERT` on `master.option_terms` and `SELECT` on its two columns `instrument_id` and `valid_to` (PostgreSQL reads the conflict target of the insert), no UPDATE or DELETE; Down revokes both.
- The reader's statement reads `rd.option_terms_r1` only, never `master`.

- `readings.reading` is insert-only. Its key is `(name, version, subject_kind, subject, day, rev)`; `value` is `numeric(38,12)` or NULL; `rev` is at least 1; the insert is `ON CONFLICT DO NOTHING` in one transaction per call, record and children together.
- The view `rd.reading_r1` applies the winner rule per `(name, version, subject_kind, subject, day)`: the row with the highest `rev` of state `ok` wins; a row of state `missing_input` yields to any `ok` row and shows only when the day has no `ok` row (then its highest `rev`). `LatestReadings` is not the view: it returns the newest rev whatever its state.
- The enum `reading_unit` has nine words: `decimal, percent, vol_point, per_calendar_day, count, days, money, ratio, text_tag`.
- Grants: `ot_w_readings` (LOGIN, made by `setup.Setup`, line `OT_PG_DSN_READINGS`) has `INSERT` and `SELECT` on the four tables and `SELECT` on the views `rd.reading_r1` and `rd.reading_parameter_r1`; `ot_ro_pages` has `SELECT` on both views and nothing on the tables; `ot_runner` has nothing. No role has UPDATE, DELETE or TRUNCATE.
- The view `rd.reading_parameter_r1` (migration `0016`, owner `ot_owner`) names every column of `readings.reading_parameter`; no grant is made on the table.
- `reading.OpenView(ctx, dsn)` returns a `store.ReadingViewReader` (`WinnerReadings`, `Close`) that reads `rd.reading_r1` and `rd.reading_parameter_r1` only, so it runs as `ot_ro_pages` or `ot_w_readings`; the caller passes the DSN (the page process reads the line `store.DSNEnvPages`, `OT_PG_DSN_PAGES`), the package reads no environment. `WinnerReadings(ctx, name, subjectKind, subject, from, to)` returns one row per day, ascending by day: the winner and version rule is the highest `version` of the day, then in that version the highest-rev `ok` row, else the highest-rev row (the winner rule of `rd.reading_r1`). Each row carries its `Parameters` (`param`, `value_num`, `value_tag`; `data_day` among them) read from the second view for the same keys, and no `Inputs` (empty). No rows gives an empty slice; `from` after `to` or a bad day is a `Permanent` error and makes no query; a database error is `Retryable`.

## Alert sent marks

`internal/store/alert` (stub; the implementation is a later issue) will hold `alert.Open`, a `store.OpenSentFunc` returning a `store.SentStore` (`SentSince`, `MarkSent`, `Close`) from the line `store.DSNEnvAlerts` (`OT_PG_DSN_ALERTS`) of the role `ot_w_alerts`.

- Table `alerts.sent(rule_id, day, sent_at)`, key `(rule_id, day)`. `SentSince(from)` returns the marks with `day >= from`, ascending by day then rule id; none gives an empty slice.
- `MarkSent` inserts `ON CONFLICT DO NOTHING`; `sent_at` comes from the database's `now()`. A second mark of the same key changes nothing.
- Mark after send: the caller calls `MarkSent` only after the message was sent, so a failed send leaves no mark and the result is said again on the next pass.

## Scheduler store

Declared in `internal/store/api.go` beside `OpsLedger` (unchanged); tables, views and implementations come from `migrations/0012_scheduler.sql` and `sched-store-ops` in later entries. Design: `docs/design/scheduler.md#sched-store-interface`.

- `InstanceFence.TryLock(ctx, build)` gives a `Fence` (`Lost() <-chan struct{}`, `Close() error`), or a `Retryable` error while another holds it. Writer: none (an advisory lock on one dedicated connection). Reader: `cmd/ot` only.
- `SchedulerLedger` (role `ot_runner`) is the only writer of `ops.job_gap`, `ops.scheduler_state` (one row, the build) and `ops.scheduler_job`, and the reader of `Status` (reads `ops.*` only). `RenewLease` and every gap time use the database's `now()`. `MarkGapReported` is called only by `notify`; a page never sets `ReportedAt`.
- `RunStatus` gains `RunPartial` and `RunAbandoned` (additive; the column is text).
- `GapReader` (role `ot_ro_pages`) reads `OpenGaps` and `Expectations(ctx, from, to)` from two views of schema `rd`, never from a base table:
  - `rd.job_gap_r1`: the open and cleared gaps of `ops.job_gap`.
  - `rd.expectation_r1`: derived from `ops.dataset_window` (`close_at` is the due-by instant) and `ops.capture_present`.
- Grants (recorded here, made by migration `0012` in another entry): both views belong to `ot_owner`, which can read `ops`; `SELECT` on both views to `ot_ro_pages` and `ot_runner`. `ot_ro_pages` reads views of `rd` only and has no grant on an `ops` table, as schema v3 says.
- Constructors: `OpenFenceFunc`, `OpenSchedulerLedgerFunc`, `OpenGapReaderFunc` (the last opens with the line `DSNEnvPages`).

## Fundamental facts

Declared in `internal/store/api.go`: `FactWriter` (`InsertFacts`), `FactReader` (`FactsFiledBy`), `FactStore` (both and `Close`), `OpenFactStoreFunc` and `DSNEnvFundamental` (`OT_PG_DSN_FUNDAMENTAL`). `internal/store/fundamental.Open` is the implementation. Design: `docs/design/valuation.md#Decisions` (6).

- Table `obs.fundamental_fact` (migration `0017`), append only. Key `(source, subject, doc_id, taxonomy, concept, unit, period_start_key, period_end)`; `period_start_key` is `NOT NULL` and holds `0001-01-01` for an absent `period_start`, so a repeated instant fact is a duplicate. `InsertFacts` inserts `ON CONFLICT DO NOTHING` on that key in one transaction: a rerun adds 0 rows.
- View `rd.fundamental_fact_r1` returns `period_start` as NULL again for `0001-01-01`. `FactsFiledBy(ctx, source, subject, cutoff)` reads the view only and returns every row of the source and subject with `filed` on or before the cutoff, no winner picked; none gives an empty slice; a bad cutoff is `Permanent`, a database error `Retryable`.
- Grants: `ot_w_fundamental` (LOGIN, made by `setup.Setup`, line `OT_PG_DSN_FUNDAMENTAL`) has `INSERT` on the table and `SELECT` on the view; `ot_ro_pages` has `SELECT` on the view. Neither role reads the table; the page role cannot write; no role has UPDATE, DELETE or TRUNCATE. One implementation serves the figures job (opened with `DSNEnvFundamental`) and the page (opened with `DSNEnvPages`).

## Earnings dates

Declared in `internal/store/api.go`: `EarningsDateWriter` (`InsertEarningsDate`), `EarningsDateReader` (`EarningsDates`), `EarningsDateStore` (both and `Close`), `OpenEarningsDateStoreFunc` and `DSNEnvEvents` (`OT_PG_DSN_EVENTS`, role `ot_w_events`). `internal/store/events.OpenEarningsDate` is the implementation; the row is `contracts.EarningsDate`. Design: `docs/design/event-sources.md#Decisions` (7, 8, 10).

- Table `obs.earnings_date` (migration `0020`), append only, key `(observed_on, issuer, attempt)`; the enums, `attempt >= 1`, a `report_date` only for `listed` and source `none` for `unsupported` are table checks. `InsertEarningsDate` inserts `ON CONFLICT DO NOTHING`: a row whose key exists stays as it is and the call returns no error. An empty issuer or an attempt below 1 is `Permanent`, a database error `Retryable`.
- View `rd.earnings_date_r1`. `EarningsDates(ctx, issuer, from, to)` reads the view only, inclusive, ascending by day, the highest `attempt` of each day only; none gives an empty slice; a bad or reversed day range is `Permanent`.
- Grants: `ot_w_events` (LOGIN, made by `setup.Setup`, line `OT_PG_DSN_EVENTS`) has `INSERT` on the table and `SELECT` on the view (the job reads the rows of the day); `ot_ro_pages` has `SELECT` on the view. Neither role reads the table; the page role cannot write; no role but the owner has UPDATE, DELETE or TRUNCATE. The rows hold dates, status words and vendor text, no account data.

## Option ledger

Declared in `internal/store/api.go`: `OptionLedgerWriter` (`RecordFlexFetch` applies the revision rule of Decision 5 in one transaction, `ImportFlexTradeRows` applies Decision 6), `OptionLedgerReader` (`FlexTradeRows` the highest revision per transaction sorted by transaction id, `LatestOkFetch`, `StoredAliases`), `OptionLedgerStore` (both and `Close`), `OpenOptionLedgerFunc`, the plain types `FlexTradeRow`, `FlexFetchRecord`, `FlexInsert`, `FlexImportResult`, and `DSNEnvOptionLedger` (`OT_PG_DSN_OPTION_LEDGER`). Schema `optionledger` (tables `flex_fetch`, `flex_trade_row`, insert-only), role `ot_w_optionledger` (INSERT and SELECT only), views `rd.flex_trade_row_r1` and `rd.flex_fetch_r1` read by `ot_ro_pages`. Revision rule: a new key is revision 1, an equal hash is not written, a changed hash is the next revision. Import rule: an absent key with no equal hash is inserted, an equal hash is `same`, a taken key with another hash is a `conflict`. Imports: `internal/store` imports neither `internal/compute` nor the generated records; callers map. The implementation is `internal/store/optionledger` (a later issue). Design: `docs/design/option-ledger.md#Interface`.

## Flex sections

Declared in the declarations-only package `internal/store/flexsection` (not in `internal/store/api.go`): `Writer` (`RecordSections`), `Reader` (`Rows`, `Statuses`), `Store` (both and `Close`), `OpenFunc`, and the plain types `Row`, `Status` and `Insert`; the implementation is `internal/store/flexsectionpg`.

- Revision rule: on `(Alias, Section, RowKey)`. A new key is revision 1; a key whose attributes differ from its newest revision is written at that revision plus one; an identical one is counted `Unchanged` and not written. The `Revision` of a `Row` given to `RecordSections` is ignored.
- One transaction per `RecordSections`. Attributes that hold `accountId` or `acctAlias` are an error and nothing is written. No rows and no statuses makes no database call.
- Views: `Rows` reads `rd.flex_section_row_r1` and returns the highest revision of every key sorted by `RowKey`; `Statuses` reads `rd.flex_section_status_r1` and returns the newest status per section of the alias. Neither reads a base table.
- Contract test: `internal/store/flexsection/api_test.go`: `TestSectionStoreContract`, `TestRecordSectionsRefusesAccountAttributes` and `TestRecordSectionsEmptyMakesNoCall`.

## Account data

Declared in `internal/store/api.go`: `AccountWriter` (`WriteCapture`, `WriteExecutions`), `AccountReader` (`Positions`, `Values`, `Executions`, rows sorted by key, an empty slice when none), `AccountStore` (both and `Close`), `OpenAccountFunc`, `DSNEnvAccount` (`OT_PG_DSN_ACCOUNT`, role `ot_w_account`), `Capture` and the plain row types `Execution`, `AccountValue` and `Position` (decimals as text, days as `YYYY-MM-DD` text). `internal/store` imports neither `internal/broker` nor the generated records; the job maps the broker types to these. The implementation is `internal/store/account.Open` (a later issue). Design: `docs/design/account-data.md#Interface`.

- Schema `account`: tables `account.capture`, `account.position`, `account.value` and `account.execution`; the Reader reads the views `rd.account_*_r1`.
- Keys (Decision 5): the capture id is `<alias>:<session_day>:<run key>`, so a retry of a run writes the same id; an execution is keyed by `(alias, exec_id)`. Every row carries the alias, never an account id.
- Insert-only rule: rows are never updated or deleted. A `account.capture` whose id exists writes nothing, children included; `WriteExecutions` is `ON CONFLICT DO NOTHING`. `ot_w_account` has INSERT and SELECT only.
- Delivery rule (Decision 7): nothing of account data reaches notify; a job result carries a job id, a status and an alias only.
