# Option open gap, Japan: a stage that repairs the stored contracts live before the plan, and a post-run check that makes an empty stage retry and show

Goal: on a JP session day, a watched JP name that has no stored option contract for the day is resolved live by a stage that runs before the plan, inside a cap that the gateway survives; and on both chains a stage that is given names and ends with nothing stored is a visible gap, never a green run. After this design the one rule reads: each stage reads its stored input, and the gap stage repairs that input live before the plan.

## What main holds today

- US: `option_open_resolve` (evening), `option_open_resolve_gap` (08:00 ET, `job_gap.toml`, `gap_only = true`, built by `NewGap` as `newListed(gapManifest, ...)`, `listed.go`), `option_open_plan` (08:45), `option_open` (09:45). The gap pass calls `ListChains` per stock and resolves only what neither the cache nor the marks hold; `GapOnly` is read at `listed.go` lines 122, 211 and 533.
- JP: `option_open_resolve_jp` (evening, `NewResolveJP`), `option_open_plan_jp` (08:15 JST), `option_open_jp` (09:05 JST). There is no JP gap pass: a JP name whose evening resolve failed or never ran has no stored contract at the plan and is planned as the underlying only.
- Wiring orders in `cmd/ot/wire_optionopen.go`: 120 resolve, 130 plan, 140 pull, 190 gap (US); 165, 170, 180 (JP).
- `contracts.Job` has the optional method `Postcondition(ctx, day, datasetID, subjectKey) (bool, error)` (`docs/contracts/runner.md`), and this design does not use it: a false answer is a counted run that is never re-run (`runkey.go:182-188`, `reconcile.go:349-357`). A `Retryable` run before the window close is not counted and is run again at every turn (`reconcile.go:349`). No job of `internal/jobs/optionopen` has a `Postcondition`.
- `master.option_list_run` (`openquote.ListRunRecord`, `OptionListStore.PutListRuns` and `ListRuns`, implemented by `internal/store/optionopenpg/lists.go`) holds one row per (session, underlying) and nothing in `internal/jobs` writes it today.

## Decisions

### The rule, stated once for both chains

1. Each stage of the chain (resolve, plan, pull) reads its stored input and nothing else. The gap stage is the only stage that may ask the broker for what the stored input lacks, and it runs before the plan: US `option_open_resolve_gap` at `session_open` minus 90 minutes (exists), JP `option_open_resolve_gap_jp` (new) at the same anchor on XTKS. The plan never asks the broker (Decision 1 of the pull design stands) and the pull never resolves at the open. This sentence goes into `docs/contracts/ot/jobs/option_open_resolve_gap.md` and the new JP file; it is the only place the rule is written.

### The JP gap stage

2. Job `option_open_resolve_gap_jp`, built by `NewGapJP` (new, `gapjp.go`) as `NewGap` over the JP rules, as `NewResolveJP` is `NewResolve` over them: `newListed(gapManifestJP, d, o)` with `d.Stored = r.stored(d.Stored)` and `d.Broker = jpBroker{...}`, and the JP rules are parsed from `planManifestJP` exactly as `NewResolveJP` does (the gap toml has no `[chain]` table, so the chain is written once). No new resolve code: the US gap logic is reused, and the JP rules (names without options, the chain of OSE.JPN with multiplier 100 and class = stock code, `N225` as the index of class 225) already exist in `jp.go`.
3. Manifest `job_gap_jp.toml`: zone `Asia/Tokyo`, calendar `XTKS`, `anchor = "session_open"`, `offset = "-90m"` (07:30 JST), `run_bound = "10m"`, `budget_minutes = 40` (ends 08:10, before the plan at 08:15), `gap_only = true`, `max_new = 300`, the band of `job_resolve_jp.toml` (`store_k = 1.75`, `store_drop = 0.25`, `min_dte = 14`, `max_dte = 90`, `calls = "held"`, `min_puts = 6`), and two new keys, `max_per_name = 60` and `dataset = "master.option_contract.gap_jp"` (its own dataset id, so that the first job to plan a key does not give a JP key the XNYS window of `master.option_contract.gap`; `Plan` of `listed.go` reads it, the other manifests keep their defaults) (the JP ceiling per stock of `job_plan_jp.toml`; the index keeps `max_per_index = 80` from the chain table).
4. Which names: the watched JP names (`jpRules.watch`, so names of `no_option` and the entries that are neither stock nor `N225` are out) that have no stored option contract of the band for the day. A name that has stored contracts for every expiry the chain lists inside the band gets no resolve. The stage is not free on a good day: `keyRun.run` calls `ListChains` once for every watched name before it looks at candidates (`listed.go`), so a good day costs one chain call per watched JP name and no resolve. Resolves are asked only for names with a gap.
5. The request shape, from the option-trader advisor: every request is fully specified (symbol, exchange `OSE.JPN`, currency `JPY`, multiplier `100`, trading class = stock code, expiry, strike, right), from the chain definition of `ListChains`, never SMART, one resolve in flight (`ResolveInFlight: 1`, as the US gap family), the 25 s call timeout of `broker.Options` (the service waits 20 s, `docs/design/broker.md`). The contracts of a name are those of the sigma band of Decision 3 of the pull design, nearest the spot first, so a name that hits its cap keeps the strikes the owner sells. A name is never asked as the whole chain (no 148-expiry refresh).
6. The caps, per run and per name, are values of the manifest: `max_new` (300 across all names, the first-day limit `OT_OPEN_RESOLVE_MAX_NEW` still overrides it) and `max_per_name` (60). A contract beyond a cap is `deferred`, counted in the summary line (`deferred=`, exists) and not an error; a run that defers is `Retryable` only through the existing `unsent` rule. Two timeouts in a row stop the run (the existing resolve rule), so a sick gateway is not hammered.
7. The gap stage writes one `ListRunRecord` per name it repaired (session = the key day, `Reason = "gap_live"`, `Listed` = the contracts it stored) through the optional port `ResolveDeps.Lists` (an `openquote.OptionListStore` reader and writer; nil means none are written). The same code path serves the US gap pass, so the pull can say which names were fetched live on both chains (Decision 11). No store or schema is added: the table and the PG implementation exist.

### The post-run check (one mechanism: Run returns the outcome)

8. Each stage ends its `Run` with a read-back of what it stored, from the store and not from its own counts, for the key it ran: resolve and gap read `Stored.Options.ListOptions` of the stock, plan reads `PlanReader.Plan` of the day and slot, pull reads `OptionOpenReader.OptionOpen` and counts rows `ok` or `partial` (`no_data` and `not_listed` do not count). The key of resolve and plan is one stock (a `no_option` name is no key, `jpRules.watch` drops it); the key of the pull is one batch. The rule splits two cases, the same split as `ErrNotServed`, short and error in `docs/design/option-contract-lists.md`:
   - the gateway answered and listed nothing (the chain answer is empty, or every contract of the band is cached, marked not listed, or answered "no security definition"): `Err` nil when stored > 0, and `NoValue` ("chain lists no contract in the band") when stored = 0; an honest `no_value`, not a gap, so a stock with no options in its band is never a gap forever;
   - nothing came back (`ListChains` error, timeout, disconnect, an ambiguous or other error code, contracts `deferred` or `unsent`, found = 0): `Retryable` ("stored 0 of N names"), with the fault line of Decision 9.
   The `Postcondition` method is not added: with `Run` returning `Retryable` or `NoValue` whenever the read-back is 0 and names > 0, a false `Postcondition` could only fire when `Run` said clean and the store disagrees, which is a lost write that `Run` already returns as `Retryable`. Its verdict also counts a false answer as a final run (`runkey.go:182-188`: `done` without a mark; `reconcile.go:349-357`: counted, and not re-run because `latest.Status != RunPartial`), which is the one thing this design must avoid. One mechanism, not two.
9. What a `Retryable` run does, from the code, and its limits:
   - No cap and no backoff of the runner: `nextAttempt` does not count a retryable run before the window close (`reconcile.go:349`), so the key is run again at every Reconcile turn, that is every 15 minutes (`sched/ticker.go:32`, the first tick 10 minutes after start) and at every published slot instant (`ticker.go:229`), until the close of its dataset window. The close is the XTKS session close with the offsets of the job: 15:30 JST for the three JP datasets (the gap and the plan state lateness 0; the pull has no `Window` method, so the reconciler's zero offsets apply to its calendar). From 07:30 JST the gap key can be run at most about 32 times (8 hours at 15 minutes), the plan key from 08:15 about 29 times; the pull key is Retryable only until `stop_after = "0930"`, after which `Run` returns `Permanent` "key not started" (`jp.go`, `pull.go`), so at most 2 or 3 re-runs from 09:05. For the US chain the gap at 08:00 ET to the 16:00 close is about 32.
   - The per-day cap bounds the gateway, and a re-run after the cap is spent must cost nothing. On main a re-run with the cap spent still calls `ListChains` first (`listed.go`, `keyRun.run` before `resolveAll`) and only then defers every contract at `take` (`listed.go:364`). The design therefore adds a check at the top of the key run (entry 2): when `usedOn(day) >= maxNew`, return `Retryable` ("cap spent") at once, with no broker call, in milliseconds. A key whose cap is spent cannot fill that day: the counter belongs to the job and the day (`take` resets it at the next day), not to the key. The per-name cap is also per day and per name (a map in the job, entry 2), not per run, otherwise each re-run would spend another `max_per_name`: a name that fails (every resolve times out) costs at most 60 asks that day, counted when asked (`take` is called before `ResolveContract`), so 5 failing names spend the whole 300. The two-timeouts stop (`listed.go`) ends the run early for a sick gateway.
   - The turn: one worker runs the keys of a turn in order of dataset id and then subject (`reconcile.go:183-190`, `reconcileOn` is a plain loop). `master.option_contract.gap_jp` sorts before `obs.option_open` and `plan.option_open_item`, so on the turn that finds the plan due (08:15 JST) a retried gap key runs before the plan key and the plan reads what that run stored; the pull keys of a turn are those of the plan rows read at the start of the turn (`pull.go` `Plan`), so the pull never runs in the turn that stores the plan. A gap run delays the plan of its turn by at most its run bound (10 minutes per key, `run_bound`); the plan job keeps its own `Retryable` for a stock with stored 0 until the gap stage has filled it.
   - Same-day visibility is the weak point and is stated as such: on main a missing key becomes an ops gap only at the window close (`sched/gaps.go` `keyKind`: `!closed || running` gives no gap, except the crash brake), and the Telegram gap notifier (`cmd/ot/notify.go`, `NotifyGaps`) reads the same open gaps. So the page and the notice show a Retryable stage at 15:30 JST as an `expired` gap (row 3 of the Close table: `retryableLast` gives `gapExpired`). For the same morning the one path the code gives is the fault line of Decision 10, written by each re-run to the scheduler log (`wire_optionopen.go` passes `a.log.Info(line, "component", "ot", "job", id)` as `Log`). A same-morning gap on the ops page needs a change in `internal/runner/sched/gaps.go` (a key whose latest run is Retryable with reason `stored_zero` is a gap before the close), which is another module and is not in this design (Left out, owner call).
10. One fault line per Retryable or NoValue run that ended on stored = 0, through the `Log` the jobs have (`ResolveDeps.Log`, a `func(string)`; `PullDeps.Log`, a `*slog.Logger`; the new `PlanDeps.Log`, a `func(string)`): `fault stage=<job id> day=<day> key=<key> names=<n> stored=<m> asked=<k>`. One builder returns the text, each job writes it with its own sink (`Info` on the logger). The line names the stage and the count. It is written by every re-run, so a stage stuck all morning leaves one line per 15 minutes, not one.

### The pull states per name

11. The pull's run summary (`Summary.String`, one line per key) gains the state of each name, in the order of the plan, as separate tokens `state[<SYMBOL>]=stored|live|missing` (the existing `<SYMBOL>=done/total@time` tokens stay as they are). `stored` is a name with planned items whose contracts were stored before the session day's gap stage began (no `ListRunRecord` of reason `gap_live` for it); `live` means the contracts of the name were repaired live by the gap stage that day (it says nothing about the quotes, which the pull always fetches live); it is a name that has a `gap_live` record of the session (`PullDeps.Lists.ListRuns(day)`, nil means every name with items is `stored`); `missing` is a watched name of the batch with no planned item or whose rows are all `no_data` or `not_listed`. The counts of the three go into the one line (`names=3 stored=2 live=1 missing=0`) and a name that is `missing` while the watch list has it is a gap of the pull, through Decision 8.
12. The page side is unchanged: the option pages already show a gap line per name from the verdict path; a name `missing` is that gap. No pages entry, no new column, no contract change.

### What does not change

13. `Contracts: unchanged`: no schema, dataset or proto changes; no migration; `internal/jobs/api.go` and `internal/store/openquote/api.go` are not edited (the new ports are types of the `optionopen` package, as `PullDeps.Plans` is). `docs/design/modules.md` is not edited: the new files are inside the module row `jobs` and the wiring is inside the row `ot`.

## Interface

None. The post-run check is inside `Run` (no new method of `contracts.Job`), `NewGapJP` has the type of `NewResolveJP` and the new dependency fields are types of the package `optionopen`.

## Left out

- The JP resolve at the pull (a refresh of a name with no contract on the option pages): same reason as the pull design, the resolves cost seconds and cannot run inside the 15 seconds of the button.
- A second gap pass at 09:15 JST for empty books (the advisor's retry of empty books): the pull's own `retry_classes` already retry the planned classes; a gap pass after the plan would replan, which the pull design leaves out.
- A notification to Telegram for a fault line: the line goes to the same log as the summary, and the ops page shows the gap; a channel is the owner's to add.
- Calendar rules of the JP expiry (monthly European, last trading day the business day before the second Friday): the chain definition of `ListChains` carries the expiry, so the stage computes no date.
- A page column for the state of a name: Decision 12; the verdict path already shows a gap.
- Stopping or skipping the next stage on a stored-zero run (the stages are ordered by the clock only), and a same-morning gap on the ops page (a key with a Retryable latest run is a gap only at the close, `sched/gaps.go`; a gap before the close is a change of `internal/runner/sched`, another module), and a repair of a missing stored close (the plan keeps its `NoValue`) or of the underlying con_id (draft A).
- A US-only change of the gap pass beyond the shared hooks of entry 2: the US pass is not tuned here.

## Doubts

- "Fault line" has no sink on main under that name. This design uses the job `Log` (the same line family as the summary); if the owner means another channel, only the one place that builds the line (acceptance 2 of entry 1) changes.
- Decision 11 takes "fetched live" from `master.option_list_run`, a table that no job writes yet, not from a timestamp: `OptionRef` has no resolved-at field, and adding one is a store interface change that this design does not want. If the pull design's list run is redesigned, entry 3 follows.
- A name whose whole band is marked not listed is `NoValue` (an answered, honest no_value), not a gap. The advisor's rule says stored 0 for an active underlying is FAILED; the marks show it. Owner call if it should retry.
- `listed.go` is 602 lines: over the 600 of a new file and under the 800 above which `ratchet.json` needs a ceiling (it lists no optionopen file), so entries 1 and 2 may add the small hooks; if the file passes 800 the entry reports instead of splitting.
- The store recounts `Listed` of a `ListRunRecord` from `master.option_list` (`openquote/api.go`), so the `Listed` of a `gap_live` row may be overwritten; the pull reads `Reason` only. `option_list_run` gets a second meaning (a gap record) beside the list run of the pull design.
- The window of the dataset `master.option_contract.gap_jp` is not registered anywhere on main; entry 4 or the runner's dataset table may need the XTKS window (unverified: not read in `internal/runner`).
- `store()` in the optionopen package creates the instrument of an option with `CalendarID: "XNYS"`; for JP options the calendar is wrong. Not changed here (unverified whether any reader uses it).
- The Retryable gap shows on the ops page and in Telegram only at 15:30 JST; the fault line in the scheduler log is the only same-morning signal. `crew fault` is not part of this repository and is not used by the design. The design also relies on each re-run being cheap: a pull re-run asks the whole batch again (at most 120 contracts, until 09:30); a pull with `ok` rows is not Retryable, so no row is asked twice.

## Adversarial

A fresh read-only sub-agent read this file and the repository at c96f513f and answered the six questions. Its full answer is the file `adversarial-gap-jp.md` in the dispatcher scratchpad.

1. Gap against the goal (a false postcondition stops nothing; the ops page shows it only at the close; only option contracts are repaired; "live" is not live quotes): adopted in part. The text now says that the gap is shown at the close and that the fault line is the early signal (Decision 8), that the next stage is not stopped (Left out and Doubts, owner call), that the close and the underlying con_id are not repaired (Left out), and that `live` means contracts repaired live, not quotes (Decision 11). Not adopted: stopping the plan, because it needs a runner change outside these modules.
2. Biggest unnamed risk (the postcondition has no run state; it is asked only when the run has no error, so it adds nothing for NoValue): adopted. Decision 8 now keeps a per-key counts map filled by `Run` and tests stored only after a restart, and states that the postcondition covers the clean-run-stored-nothing case only. The wrong premise "a `no_option` name is planned as the underlying only" is removed.
3. Simpler way (a JP manifest on the gap job, fail the plan loudly, take the pull state from the existing summary token): partly adopted. The JP gap is already the reuse of the gap job. Not adopted: failing the plan, since the plan already returns NoValue for the cases it can see and the owner asked for a visible postcondition on every stage; and the pull state from the existing token, since `done/total` cannot tell a repaired name from a stored one. The tokens are now separate (`state[SYMBOL]=...`) so they do not collide.
4. Lock-in (a second meaning of `option_list_run`, the token collision, the shared gap dataset, a silent nil `Lists`): adopted. Own dataset id and a manifest key `dataset`, separate tokens, a startup line when the store lacks `OptionListStore`, and a Doubt on the recount of `Listed`.
5. Claim most likely false ("the gap stage costs nothing on a good day"; the no_option plan row): adopted; both corrected (Decision 4: one `ListChains` per watched name per run).
6. Likeliest slip (entry 1: `listed.go` missing from Files, acceptance 4 printed 3, `Log` types differ, depends on drafts A and B; entry 2 acceptance 1 and 3; entry 3 acceptance 1; entry 4 acceptance 2 vacuous; the ratchet doubt wrong): adopted. `listed.go` is in the Files of entry 1, the Log types are reconciled in Decision 9, the acceptance commands are corrected (10 in entry 2, no `[chain]` table in the gap toml, per-file counts in entry 3, at least 4 in entry 4), and the ratchet doubt is rewritten.
