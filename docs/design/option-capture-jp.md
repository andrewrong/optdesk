Goal: after the Japanese option close, one capture per Tokyo session day of the Nikkei 225 monthly option chain (OSE, trading class `225`), written to the table `obs.option_eod` next to the US rows, so that the JP covered calls and cash-secured puts of a later `option-candidates-jp` have a stored chain to read. The set of underlyings is fixed in the JP manifest; JP single stocks from `watch.toml` wait for the watch loader (Left out). This design builds the capture, its schedule and the runner change that lets a second market run; it builds no gate, no candidate row and no page.

## What main holds today

- `option_eod` is US only by construction: `job.toml` has `zone = "America/New_York"`, `freeze_after = "1615"`, window and schedule calendar `XNYS` anchored at `session_close`, one `[[underlying]]` SPY (`SMART`, `USD`, `XNYS`). `Run` takes the day check from the manifest zone (`wrong day` unless the day is today in the zone) and the freeze from `freeze_after`.
- `pairs()` (`run.go`) picks the first chain whose `Exchange` equals the underlying's exchange, else the first chain; it does not look at the trading class. N225 has the classes `225`, `225W` and `N225M` all on `OSE.JPN`, so the first match would be arbitrary. `broker.Contract` and `broker.Chain` already carry `TradingClass` and `Multiplier`; `selectContracts` copies both to every contract.
- The manifest `canonical()` (the plan hash) prints every underlying with `%+v`, so a new field of the `underlying` struct changes the US plan hash. The hash of the US manifest for 2026-11-09 at 89fb03b is `b0d82cca23eaf155867cd2eb356018f7b204fce2977ac4388c7d42f674f71ab7` (a design-time value for reading only; the pinned value is the one read at the merge base, Decision 4 and issue 3). `validate()` requires a non-zero `con_id` for every underlying.
- The reconciler refuses a job whose window calendar is not its own: `Reconcile` begins with `checkCalendars` (`reconcile.go:85-87`, `window.go:50-59`), and `cmd/ot/runonce.go` and `cmd/ot/scheduler.go` build it with `runner.WindowRule{}` (XNYS). The day loop (`sessions`) walks one calendar with one cursor row `ops.reconcile_cursor`; the ticker's `walked` (`sched/ticker.go`) does the same with `defaultCalendar`. A job on XTKS is refused, and the refusal covers every job in the list, so the US jobs would stop too.
- The ledger keys windows and expected keys by dataset id: `ops.dataset_window (dataset_id, session_day)`, `putWindows` takes the window of a dataset from the first key's job (`reconcile.go`, `seen[k.DatasetID]`). The ledger dataset id is free text, not a file of `contracts/datasets/`: `calendarrefresh` uses `master.session_day`, `computefigures` `readings.reading`. No code reads the ledger id `obs.option_eod`: `computefigures` reads the table by name, and `migrations/0012_scheduler.sql` takes the ids from the ledger rows themselves.
- The dataset `obs.option_eod` r1 carries `currency` and `underlying_ccy` per row but no exchange; the market of a row is the `calendar_id` and `mic` of its instrument in `master.instrument`. Migration `0006_option_eod.sql` constrains currency to three letters only, so JPY rows need no dataset change.
- Calendars: `pyside/src/optdesk/calendar/api.py` has `SUPPORTED_CALENDARS = ("XNYS",)`; the generator (`generate.py`) reads `calendar.opens` and `calendar.closes` of `exchange_calendars` per session, which for a calendar with a lunch break is the first open and the last close, and is otherwise calendar-agnostic. `docs/design/pyside-calendar.md` left Tokyo out because one open and close pair per day hides the lunch break. `calendarrefresh` refreshes XNYS only (`job.toml`).
- `sched.NextStarts` calls `cal.Session` for the calendar of every slot and returns an error naming the job when it fails, so a slot on a calendar that is not loaded stops the schedule of all jobs.
- Hours (ADR 0004 and the JPX index option specification): the option day session runs to 15:40 with the closing auction at 15:45; the night session of the Nikkei 225 options opens at 17:00 JST since the extension of 5 November 2024 (not 16:30; 16:30 applies to other products). The cash market of XTKS closes at 15:30 since the same date.

## Decisions

1. One capture code, a second manifest, a second job. The JP capture is the job `option_eod_jp`, built by the same `optioneod` package from a second embedded manifest `job_jp.toml` through a second constructor `optioneod.NewJP` of the existing type `jobs.NewOptionEodFunc`; `internal/jobs/api.go` is unchanged. A job has one window calendar, one zone and one slot, and the US and JP closes are 13 hours apart, so the market is manifest data and not a code branch. It writes the same table through the same `store.OptionEodWriter`.
2. A fixed underlying set, no watch loader. The first cut captures what the JP manifest declares: one `[[underlying]]` N225 (`sec_type = "IND"`, `exchange = "OSE.JPN"`, `currency = "JPY"`, `con_id = 14087999` from the probe, `mic = "XOSE"`, `calendar_id = "XTKS"`, `lot_size = "1000"`). A non-zero `con_id` is required by `validate()` and stays required. The cut does not wait for the `option-candidates` or `event-sources` watch-loader issues, and `jobs.WatchEntry` is not used. JP single stocks from `watch.toml` are Left out. A con_id of an index contract is public reference data and is not an account id.
3. Chain choice by exchange and trading class, from the manifest, outside the `underlying` struct. The manifest gets the top-level key `trading_class` (default empty). When it is set, `pairs()` takes the first chain whose `Exchange` and `TradingClass` both equal the underlying's exchange and the key; a manifest without the key behaves as today. The JP manifest sets `trading_class = "225"`: the monthly class only. The weekly class `225W` and the mini class `N225M` are left out because their option contracts have the same symbol, expiry, strike and right as the monthly one, and the OSI identifier (`map.go`: symbol padded to 6, yymmdd, C or P, strike times 1000 in 8 digits) has no trading class, so a second class would collide on the `osi` identifier; they need their own design with an identifier scheme. The underlying contract carries no trading class.
4. The plan hash of the US manifest does not change. The new manifest keys (`trading_class`, `ledger_dataset`, `stop_after`) are top-level manifest fields, and `canonical()` appends each of them only when it is set, after the existing text. No field is added to the `underlying` struct. The US plan hash and the field count of the `underlying` struct are read at the merge base when the entry is cut (not at design time, because `option-eod-watch` and `option-eod-held-calls` land first and may change the manifest) and written into the test; a test pins the US hash; if a later change must alter it, that change names the test as expected to change and gives the new value.
5. The ledger key: a separate ledger dataset id for JP, no contracts change. The manifest key `ledger_dataset` (default `obs.option_eod`, the value of today's constant) names the dataset id of the plan keys; the JP manifest sets `obs.option_eod_jp`. The table written stays `obs.option_eod` and the dataset file `contracts/datasets/obs.option_eod.r1.json` is untouched, because the ledger id identifies the window, the expected keys and the stop logic, not the table. Alternatives rejected: keying the ledger by job needs a migration of `ops.dataset_window`, `ops.capture_expected_key`, `ops.capture_present`, `ops.capture_run` and the `store.OpsLedger` interface (store, runner, jobs, ot and pages all change); a new dataset file adds a contract and generated code for a table that does not change. The cost: the JP `capture_id` (hash of day, dataset id and symbol) differs from a US one by construction, which is wanted; the gap notices and the status page name the ledger id `obs.option_eod_jp`, which is more informative than one shared name. A market column on the row is a later dataset revision, not this design.
6. The runner walks the union of the calendars of its jobs, one cursor. The change is in module runner only, behind unchanged types (`runner.WindowRule`, `runner.Windowed`, `runner.Reconciler`, the `OpsLedger`): (a) `checkCalendars` is removed; (b) the calendars of a reconciler are the distinct calendars of its jobs (a job without `Window` or with an empty calendar uses the calendar of the rule, as today); (c) `Reconcile` walks the days after the cursor up to the day that are a session of at least one of those calendars, in order, and the cursor advances over the complete prefix as today; (d) on a day, a job is planned only when its own calendar has a session that day, and the window of each dataset is computed from the session of the calendar of the job that plans it (`windowFor(ruleOf(job), dataset, session of that calendar)`); (e) the ticker's `walked` uses the same union, so the gap sync covers a day that is a session only in Tokyo; (f) a calendar that answers `NoValue` for "next session" ends only its own list; an error of the rule's calendar (the calendar of `runner.WindowRule`, XNYS in `ot`) is returned as today, and an error of any other calendar (`UnknownCalendar` included, e.g. a hand-loaded XTKS file that runs out while `ot scheduler` runs) ends only that calendar's list: the keys and the slot of the jobs of that calendar are dropped for the days it cannot answer, with one named log line (`calendar XTKS: <error>, jobs dropped`), `Reconcile` and `sched.NextStarts` do not fail, and the jobs of the other calendars keep running. A reconciler whose jobs share one calendar behaves as before, byte for byte in what it writes. A Tokyo-only day (an XNYS holiday) is walked and the US jobs are not planned on it; an XNYS-only day plans no JP key.
7. Calendar XTKS. `SUPPORTED_CALENDARS` becomes `("XNYS", "XTKS")` and the generator needs no other change: one pair per day, the first open (09:00 JST) and the last close of `exchange_calendars`; the lunch break is not stored because the capture uses the calendar for "is it a session day" and the window close only (Decision 8). This reverses the "Tokyo is a later design" line of `pyside-calendar.md` for the day list only; break columns stay out. The generator test pins a stub of `exchange_calendars.get_calendar` and asserts nothing about the library's holiday data or version. The owner generates the file and runs `ot calendar load` for XTKS (as in `week1-run.md`); `calendarrefresh` stays XNYS only, so the XTKS rows are refreshed by the owner until a later design (Left out).
8. Times. Verified against JPX (index option specification, 2025-11-17): day session to 15:40, closing auction 15:45; night session opens 17:00 JST; XTKS cash close 15:30. The slot is `anchor = "time"`, `zone = "Asia/Tokyo"`, `offset = "15h50m"` (five minutes after the closing auction, as ADR 0004 gives close plus 5 minutes), calendar `XTKS`; `freeze_after = "1550"` in zone `Asia/Tokyo`. The window is `after_close` with `lateness_hours = 2` (the key is whole hours): the window closes at the calendar close plus two hours, 17:30 JST for the XTKS close of 15:30 and 17:00 JST for a close of 15:00 from an old library; 17:00 is after the slot plus the run bound (15:50 plus 16 minutes is 16:06), and `stop_after` 1700 keeps a late start from writing night-session quotes. A run that has started before the window close is not cut by the window: it ends within `run_bound`, and a start at or after the window close is not planned and the day is reported as a gap; `run_bound = "16m"`, `budget_minutes = 8`. The manifest key `stop_after` (HHMM in the zone, default unset and not in the US manifest) makes a run at or after that local time return `NoValue` with "after session" and no broker call; the JP manifest sets `stop_after = "1700"`, so a late or manual re-run never writes night-session quotes under the day-session date. A time anchor is used and not `session_close` plus an offset because the close is the cash close, not the option close.
9. Day semantics of `run-once`. The default `--day` stays the New York date. The JP job requires `day` equal to the date in `Asia/Tokyo` at run time (the existing `wrong day` check), so `ot run-once` runs it on the JST date of the live quote: from 15:50 JST (01:50 New York under EST, 02:50 under EDT) until 10:00 New York time under EST (11:00 under EDT) the same calendar date is on both sides; later the job returns `wrong day`, a named line and no row. A JP backfill of a past day is not possible (the capture is a live snapshot), as for US.
10. The index is an underlying. The index snapshot is `PARTIAL` (last and close); the price comes from `last`, else `close`, else `und_price`, which the existing code already accepts. The index has no company, so there is no earnings call and no dividend call; an index option is European and cash-settled, so there is no assignment guard.
11. Prices and increments. Prices are decimal JPY. The manifest `option_price_increment` is one value for every option instrument of the job and is recorded in `master.instrument`; the JP manifest sets the minimum tick `"1"` (JPY) and `lot_size` is the chain multiplier (1000), which `selectContracts` already copies. The tick table of N225 options (1 yen under 100 yen, 5 yen from 100 yen) is not verified here; the instrument row records the minimum only, and the owner reads the first run (Checked by CI).
12. Cost and limits. The JP manifest keeps the defaults `max_expiries = 3`, `strike_band = 0.10`, `max_strikes_per_side = 8`: at most 96 contracts per run, a fixed handful with no DTE logic. When the budget is spent the job stops with the existing `Retryable` error and the day is re-run inside the window. No test reaches a broker (`broker.Broker` fake).
13. The missing-calendar case is explicit. When the XTKS calendar is not loaded, `ot` leaves the job `option_eod_jp` out of the wired jobs with one named line (`calendar XTKS is not loaded`), so that a calendar that is missing at start never reaches the slot call. A calendar that is loaded at start and runs out later (the XTKS rows are refreshed by hand only, Decision 7) is covered by Decision 6(f): the error ends only the XTKS list and drops only `option_eod_jp`, one named line, and the US jobs run as before. The owner loads the calendar and restarts.
14. Nothing account-specific leaves the machine: the JP job reads no account position and writes nothing to Telegram; a named line carries the job id and the symbol only. `watch.toml` stays in `$OT_HOME`; the fixtures use the synthetic symbol `N225` with a made-up `con_id` except the manifest `job_jp.toml`, which carries the public con_id of Decision 2.
15. Reuse before parallel pipeline: the new code is three manifest keys, one chain filter and one stop check in `internal/jobs/optioneod`, one constructor, the calendar union in `internal/runner`, one calendar value in pyside and the wiring in `cmd/ot`. No second table, store, writer, broker client or scheduler.

- A JPX hours overlay (ADR 0004) and the lunch-break columns of the session day: the fixed slot and the `stop_after` time of Decision 8 do not need them.
