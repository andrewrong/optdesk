## Decisions

1. What the module does. The scheduler writes a row in `ops.job_gap` when work is missed (`expired`, `crashed_repeatedly`, `preflight_failed`) and catches the work up (one `Reconcile` at start, a retry at each 15-minute tick); the row is cleared when the key is present. `notify` is a package the scheduler process calls: after each gap pass it calls `Notifier.NotifyGaps(ctx)`, which reads the open rows that have no `reported_at`, sends one text, and marks the rows it printed reported. `notify` is the one owner of `reported_at` (#358, Decision 9); the pages never write it and show every open gap. It never decides that something is missed and never runs a job: the gap rows are the whole input.
2. Ownership of `MarkGapReported`: store. It is already declared on `store.SchedulerLedger` (written by role `ot_runner`) in the Interface section of `docs/design/scheduler.md` (#358), and the open gaps are in `SchedulerLedger.Status(ctx).Gaps`. This design does not edit the store interface. `internal/notify/api.go` declares its own consumer-side port, `GapSource`, with the two methods it needs; the wiring issue (5) builds it from the `SchedulerLedger` the scheduler process already holds, with an adapter of a few lines inside `cmd/ot/scheduler.go` (no file of its own, no second store handle). Result: notify can be built and tested now against a fake `GapSource`, and if the store signature of `MarkGapReported` ends up different from the one assumed here, only the adapter changes. No store edit is needed; the (interface) entry is notify's plus repo, for the regenerated `.go-arch-lint.yml` only, as `## Modules` says.
3. Interface in one file, no logic: `internal/notify/api.go` holds `Sender`, `GapSource`, `Notifier`, `Config` and the constructor types, as the one interface file of the package (AGENTS.md). The implementations are sub-packages, so each can be built in parallel: `internal/notify/core` (the Notifier), `internal/notify/dryrun` (stdout), `internal/notify/telegram` (the library). The fake `Sender` and fake `GapSource` for tests are `internal/notify/notifytest` (a test kit, never imported by `cmd/ot`).
4. Who runs it: nobody separately. `notify` stays a package (`Sender`, `Notifier.NotifyGaps(ctx)`, quiet hours, the backoff state in memory) and the scheduler process calls `NotifyGaps` after each gap pass, so there is no resident `ot notify`, no keeper entry, health check or drain for it, and no second DSN consumer. It is not a scheduler job (`runner.Scheduled` produces a key for a window; notify produces none). `ot serve` reads through `ot_ro_pages` and stays without a write. A dead scheduler writes no gap and sends no text: that silence is the scheduler's watchdog and `/health` (`docs/design/scheduler.md`, Decision 2), not notify's. A failed or panicking `NotifyGaps` never stops the ticker: the wiring logs the error class and goes on. The optional hand command `ot notify --once [--dry-run]` (Decision 12) exists only so the owner can test the token.
5. Role and DSN: the write is `ot_runner`'s, inside the scheduler process: `migrations/0012_scheduler.sql` (#358) makes `ot_runner` the writer of `ops.job_gap`, and the scheduler already holds that connection. No new role, no new DSN line, no migration. The notify code can call only the two methods of `GapSource`, so the only write it can make is `MarkGapReported`. A narrower role (`UPDATE reported_at` only) is left out; the owner may ask for it (question 1).
6. One pass, `Notifier.NotifyGaps(ctx)`: if the backoff (9) has not elapsed, return 0; read open gaps; drop a gap with `ClearedAt` set or `ReportedAt` set; if none, send nothing and return 0; inside quiet hours (7) return 0 and leave the rows unmarked; otherwise build one text (8) from the first 20 gaps, send it once, and only after the sender returned nil call `MarkGapReported(ctx, gap, now)` for each gap printed in it, and only those: the gaps behind "and M more" stay unmarked and are said at the next pass. Never mark what was not shown. A failed send marks nothing. A failed mark after a confirmed send returns the error and is retried at the next pass, so the delivery is at-least-once: the text of a gap may repeat only when the mark itself fails. That is stated in `docs/contracts/notify.md`; it is the one case where "said once" can break, and the alternative (mark first) can lose a message, which is worse.
7. Quiet hours, a setting with a code default: `Config.QuietFrom` and `Config.QuietTo` as `"HH:MM"` in the zone `Config.Zone`, which is `profile.Zone`, the owner's zone (`internal/profile/api.go` lines 13-14, `OT_ZONE`; no market hours are written by hand). The default is 23:00 to 07:00 (question 2) and the window may cross midnight. It covers the US session: an `expired` option_eod gap found at 05:00 is held and said at 07:00. The owner may change the two strings; `ot notify --once --quiet 23:00-07:00` overrides them for the hand command (`--quiet off` disables them). Held gaps are said at the first pass after the window; nothing is lost because the rows stay unreported.
8. Message text, fixed by the code and not by the gap: first line `optdesk: N job(s) missed work`, then one line per printed gap: `job <JobID> day <YYYY-MM-DD> <reason>` for `preflight_failed` (the only reason with a `JobID`; #358, Decision 9), and `dataset <DatasetID> day <YYYY-MM-DD> <reason>` for `expired` and `crashed_repeatedly`; `reason` is one of those three, and `unknown` for anything else (the stored string is never copied). At most 20 lines, then `and M more`; the whole text stays under 3500 bytes (Telegram's limit is 4096). Plain text: no parse mode, so no escaping. One message per pass. A dataset id is not a secret; the text carries no account id, DSN, path, token, chat id or error text; ADR 0010 holds (no account-derived information). Gaps are sorted by `FirstSeenAt`, then `JobID`, then `DatasetID`, so the text is deterministic. The test of a text sets a sentinel in `Reason`, in `JobID` of a key gap and in an error and asserts it is absent; the dataset line is asserted to hold the `DatasetID`.
9. Retry is bounded so an outage does not loop. A pass makes one send attempt; there is no `Run`, no loop and no sleep. The scheduler calls `NotifyGaps` after each gap pass (15 minutes). The backoff is state in memory on the injected `clockwork.Clock`: after a failed pass the next 15, then 30, then 60 minutes are skipped (`NotifyGaps` returns 0), and 60 stays until a pass succeeds; the state is lost at a restart, which only means one earlier attempt. `NewNotifierFunc` returns an error only for a bad `Config`.
10. Secrets: the bot token and the chat id are two lines of `$OT_HOME/.env`, `OT_TELEGRAM_TOKEN` and `OT_TELEGRAM_CHAT_ID` (constants `notify.TokenEnv` and `notify.ChatIDEnv`), read only by the scheduler wiring (and the hand command) through `deps.readEnv` as the DSN lines are; the owner supplies the values and no agent writes them. They are in no code, no configuration, no fixture, no log line and no error text (AGENTS.md); tests use synthetic values (a token `test-token`, a chat id `1000001`, which are not real) and never call Telegram. A missing line when the scheduler starts is an error that names the variable and nothing else (the scheduler always needs both lines; only the hand command `ot notify --once --dry-run` runs without them). The Telegram sender returns its own error classes (`notify.ErrSend`, with an HTTP status class when there is one) and never wraps the library's error, because the library's errors can carry the request URL, which holds the token; `TestTelegramErrorHoldsNoToken` uses a sentinel token against an `httptest` server.
11. Library, per AGENTS.md "Libraries": `github.com/go-telegram/bot` v1.27.0 (module proxy, tagged 2026-09-11; repository pushed 2026-11-02), license MIT, `go 1.18`, no `require` line in its `go.mod` (no transitive dependency), 1.9k stars, one `SendMessage` call is all we use (`bot.New(token, WithServerURL, WithHTTPClient, WithSkipGetMe)`, so a test points it at an `httptest` server with no fixed port). It is chosen by the owner's word of 2026-11-08, and it touches secrets and the network, so the owner's word is also the sign-off the rule asks for. The Design line of issue 4 reads "library chosen by the owner on 2026-11-08; own code is the sender wrapper only, behind `notify.Sender`". The own glue (`telegram.Sender`, the Notifier, the text) sits behind `Sender` and `GapSource`, so the library can be replaced by editing one package (owner, 2026-11-08).
12. Dry run and the hand command: `dryrun.Sender` writes the text to an `io.Writer` (stdout in the hand command, a buffer in tests) and needs neither token nor chat id. The optional `ot notify --once [--dry-run]` (wiring only, small, in issue 5) makes one pass for the owner to test the token; with `--dry-run` it reads the gaps and prints the text but calls no `MarkGapReported` (the `GapSource` is wrapped by a read-only view), so a dry run never uses up a message. It does not start the scheduler and does not take its lock.
13. Tests (all of them): `t.Parallel()`, a fake clock (`clockwork.NewFakeClock`), no sleep, a fake `Sender` and a fake `GapSource` from `notifytest`, no live Telegram, no fixed port or file; the Telegram package tests run against `httptest`.
14. "Recovered" line: left out in stage 1. A gap that clears before the next pass is never said, and a gap that was said and then clears gets no close-out text. Reason: the one-owner rule makes `reported_at` the only state, a recovery text needs a second state ("said, then cleared, close-out sent") on the same row, which #358 does not carry, and the scheduler's catch-up is the repair; the owner sees the alarm and, if it matters, `ot scheduler status`. Adding it later is a new column and a `Sender` call, not a change of this interface.

## Second opinion

This is a second-opinion case: a new outside service and a new account (Telegram), and a new credential (the token, the chat id) that the scheduler process holds. The brief goes to the advisor (optdesk-advisor) after the design review; the answer is recorded here in a later revision, and the merge waits for it and for the owner's word. The issues that wire Telegram, 4 and 5, carry the waiver lines when the advisor has answered, not now.

Brief for the advisor: (a) the sender never wraps a library error, so the token cannot reach a log; (b) the text is generic by construction (job or dataset id, day, a fixed reason word); (c) at-least-once delivery with the mark after the send, only for the gaps printed; (d) the write is `ot_runner`'s inside the scheduler process, no new role; (e) the token and chat id in `.env` only.

## Interface

Owner: notify. Frozen by `notify-interface`; read by every issue after it. In `internal/notify/api.go`:

- `Sender`: `Send(ctx context.Context, text string) error`. Delivers one text message; nil only when the service confirmed it. `ErrSend` is the error class; the text of an error never holds a token, a chat id or a URL.
- `GapSource`: `OpenGaps(ctx) ([]store.Gap, error)` and `MarkGapReported(ctx, g store.Gap, at time.Time) error` (the first is read from `store.SchedulerLedger.Status`, the second is `store.SchedulerLedger.MarkGapReported`, joined by the adapter of issue 5).
- `Notifier`: `NotifyGaps(ctx) (int, error)` (one pass, the number of gaps reported; no `Run`). `Config{QuietFrom, QuietTo string; Zone *time.Location}`. `TelegramOptions{ServerURL string; HTTPClient *http.Client}` (both optional; for tests). Constants `TokenEnv`, `ChatIDEnv`, `DefaultQuietFrom`, `DefaultQuietTo`. Constructor types `NewNotifierFunc(GapSource, Sender, clockwork.Clock, Config) (Notifier, error)`, `NewTelegramSenderFunc(token, chatID string, o TelegramOptions) (Sender, error)` and `NewDryRunSenderFunc(io.Writer) Sender`.
