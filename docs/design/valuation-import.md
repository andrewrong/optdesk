## Goal

The owner opens `/valuation-import`, picks the file, and gets one preview: the R of the three markets, the margin table, and one line per company with its key, R market, V, P, version date, the action the import would take (new first review, change as an event review, same as stored, refused with the reason) and the site's own buy-zone top computed from that V and P beside the file's, and what is skipped as older than stored. He ticks what the page asks him to tick and presses one confirm. The tables and reviews are written through the existing `valuation.Writer`; the valuation table and company pages then show the lines. Uploading the same file again changes nothing.

## Decisions

1. One page, two posts of one route, stateless. The page `/valuation-import` (schema `page.valuation_import_page.v1`) has one file field and a "Preview" button. The browser makes no network request by script (ADR 0034); both posts are native `<form method="post" encType="multipart/form-data" action={post_path}>` posts, as `web/src/pages/flex_import/view.tsx` does, and each answers the whole page with its page document embedded, as `cmd/ot/flex_import_post.go` answers (the page handler runs with the result), not as JSON. The Preview form has the file field and `action=preview`; the answer is the page with the document of view `preview`. The preview page holds a second multipart form, Confirm, with its own file field (the owner picks the same file again), `action=confirm`, a hidden `file_sha256` (the `file.sha256` of the previewed file), the ticks and, for each unmatched row, `key.<ticker>` and `r_market.<ticker>`; the answer is the page with the document of view `result`. Nothing is kept between the two posts. Two ways were weighed: a digest of the plan posted back (the confirm writes only when its recomputed plan has the same digest), or a confirm that only recomputes. The second is simpler and is chosen: the confirm post re-parses the file, recomputes the plan against the stored state at that moment and writes what that plan says (equality makes it idempotent, Decision 8). The only comparison kept is the sha256 of the file that the preview showed, posted back as the hidden `file_sha256`: when the file picked again has another hash the confirm writes nothing and answers the page with the preview of that file. There is no digest. The owner's file is never written to disk: the post streams the multipart body with `MultipartReader` into memory under a cap of 1 MiB (`MaxFileBytes`), never calls `ParseMultipartForm`, and the page keeps the file name only for display (at most 64 characters, no path).
2. The guard. The post is an owner post: the owner cookie (`ownerCookieOK`) is checked before a byte of the body is read, then the stream; method other than POST is 405. The multipart upload cannot pass `guardOwnerPost` (urlencoded, 64 KiB), so the new post follows the pattern of `flex_import_post.go`: declared length against the cap, cookie, `MultipartReader`. No write happens before the cookie check. The write goes through the role `ot_w_settings` and `openValuationStore` as every valuation post does; no file or service outside the repository's PostgreSQL is written, so no entry names `docs/writes.md`.
3. Parse and map live in one package behind one interface: `valueimportapi.Importer.Plan(Input) (Plan, error)` (Interface 1), implemented in `internal/compute/valueimport`. It is pure: bytes and the stored state in (plain text), a plan out; no clock, no I/O, no store type. Numbers are read from the JSON text as decimal text (`json.Number`), never through `float64`, so `0.20` stays `0.20` and no rounding is added. The calculator is passed in `Input`; the importer computes no price itself. Unknown keys of the file are ignored (the export may grow). The keys the import needs are exactly these paths: `meta.as_of`, `meta.R_table_current.US`, `.JP`, `.HK`, `.CN`, `meta.params_by_P`, `companies`, and per company `ticker`, `name`, `market`, `currency`, `v_version`, `V`, `P`, `R`, `B_hi`; the paths `meta.R_note`, `meta.removed`, `meta.unvalued` and per company `note`, `q_note`, `source_report`, `breakpoint_flag` are optional (absent is empty). A missing needed path, a wrong type, more than `MaxCompanies` (500) companies or a file over `MaxFileBytes` is `ErrBadFile` and the answer names the path, never a value; so a renamed key of the export stops the import with its path named, and the parser is the one place to change. The page text for it is a plain sentence.
4. R: one `valuation.r_version` row (advisor 1). `effective_date` is `meta.as_of`; `r_us` and `r_jp` are `meta.R_table_current.US` and `.JP`; `r_hkcn` is `.HK` and `.CN`, which must be equal as decimals, else the R part is refused with the text "HK and CN differ: the site has one HKCN column" and no company of market HK or CN is written; `note` is `R_note` (cut to 600 characters); `yield_used` is empty (Today). The AI switch and its expiry are carried over from the newest stored R version exactly as the params post does (`valuation_post.go:285`; off and empty when none is stored). A company row whose `R` differs from the `meta.R_table_current` value of its file market is refused (the lines come from the R version, so a row with another R would show other lines than the file says). The plan action for R is `same` when the three R values equal the newest R version as decimals (no insert); `older` when the stored newest R version has an `effective_date` not before `as_of` (the store picks the newest by `effective_date`, then `set_at`, so an older-dated insert would move no line): nothing is written and the preview lists it as "older than stored"; else `insert`. `r_table` is not written and no bucket is invented (Left out).
5. Margin table (advisor 2): one `valuation.margin_table` version with `effective_date` `meta.as_of`, rows from `meta.params_by_P`, one row per key: `p_from` from the key text (`>=4.5` is 4.5, `4` is 4.0, `3-3.5` is 3.0, `<=2.5` is 0), the four numbers in the order `m`, `w`, `h`, `s` (the order was proven against the sample: the importer's own check, Decision 6, reproduces the file's buy-zone top). A key the importer cannot read, or two keys with one `p_from`, is `ErrBadFile`. The action is `same` when the rows equal the newest margin table as decimals, `older` by the same date rule as R, else `insert`. The plan's check (Decision 6) uses the R and margin that will be the newest after the import: the file's when `insert` or `same`, else the stored.
6. The importer's own check. For every company the plan computes, with the calculator and the file's R and margin rows (the tables that will be stored), the site's buy-zone top (`Lines.BuyHigh`) from the file's V and P, and shows it beside the file's `B_hi`. A row whose computed value differs from the file's by more than rounding is refused with both numbers and the text "the site computes another buy-zone top"; rounding means a difference of at most `RoundTolerance` (relative 0.005, or absolute 0.5, whichever is larger, both constants of the interface package). The same pass runs `Calculator.Check` (Decision 12 of the structure design) with type, version date, V and P of the row, and refuses the row with its texts when a problem is returned (for example the buy zone above the fair zone). A refused row is skipped at confirm and the others are written.
7. Keys (advisor 3, changed by adversarial point 1). The key is never built from the file's `market`. Each file ticker is matched to a current `settings.underlying` row: the ticker upper-cased, the exchange suffix cut (`.T`, `.HK`, `.SZ`, `.SS`) and, for a ticker with no suffix, the dot changed to a space (`BRK.B` to `BRK B`, the IBKR form the list holds), equal to the row's `Symbol` upper-cased. When a row matches, its `Key` is the company key (`US:BRK B`, `JP:7974`) and the R market column is that row's market (US to `US`, JP to `JP`), whatever the file's `market` says; this keeps one key per company, also for a US-listed ADR. When two rows match, the one whose market equals the file's market wins, else the row is unmatched. A row with no match is an unmatched name: the preview shows a proposed key (the file market as prefix, then the cleaned symbol, such as `HK:0700`) in a text field the owner may change, and an R market select (default from the file market: US `US`, JP `JP`, HK and CN `HKCN`), and the row is written only when the owner ticks it (Decision 11); an unmatched name is never created silently. The key the owner picks must fit `valuationKeyPat` and must not equal a `Key` of the list (then the name is matched, not new); it is posted as `key.<ticker>` and `r_market.<ticker>` and validated by the importer again at confirm (a bad key makes the row `refused`). The Writer is used directly, not the entry form. The profile `symbol` is the cleaned symbol for R market `US` or `JP` and empty for `HKCN` (no price source: structure Decision 3); `name` and `currency` come from the file. A key with no profile gets a new profile (pool `in_pool`) and the preview marks it "new profile"; an existing profile is not rewritten unless the pool changes (Decision 10).
8. Reviews (advisor 4 and 6). For a company with no current review the import inserts one review of type `first`; for a company with a current review that differs it inserts one of type `event`. The file has no field that says "after earnings", so `post_earnings` is never chosen by the import (the owner can still enter one on the form); `backfill` is never used, because a backfill is never current (structure Decisions 8 and 12). `version_date` is the row's `v_version`; status `effective`; source `owner`; `V` and `P` as decimal text from the file. The review id is new for every inserted review: `imp-` plus the first 12 hex characters of the sha256 of the file plus `-` plus the first 8 hex characters of the sha256 of the key, so it matches the id form `^[A-Za-z0-9_-]{1,64}$` and a rerun of the same file after a partial failure meets `ErrClosed` for an id already written and reads it as written. Equality to the stored valuation is decimal equality of V and P, and equality of the R market column and the pool, against `Reader.Current`; equal rows are `same` and nothing is written for them. An older file never overwrites a newer valuation: the current valuation is the latest insert (`EffectiveAt`), not the latest `version_date`, so a row that differs from the stored one and whose `v_version` is not after the stored current `version_date` is `older`: skipped, listed "older than stored" and never written. The same rule holds for R and margin (Decisions 4 and 5). A company in the stored state and not in the file is left unchanged and listed "not in file"; the import never writes a void row (voiding stays on the review page).
9. The fields that have no column (advisor 5). `source_report` goes to `report_text`. `note`, `q_note`, `breakpoint_flag` and the clear and core lines are not stored as fields: `note` and `q_note` become `change_memo` as labelled lines in this fixed order, `note: <text>` then `q_note: <text>`, a line left out when its text is empty; the clear and core lines are computed by the site and are not stored. `next_earnings` and `breakpoint_flag` are left out (Left out): the page lists the number of rows that carry a non-empty `breakpoint_flag` that is not `ok` as one line of text, nothing more.
10. Pool. A name in `meta.removed` gets a profile row with pool `removed` and `pool_date` the date of its entry when it has a profile, or a new profile with pool `removed` and no review when it has none; the entry's other fields (reason, last V, document) are not stored. A name with a current review in the file is never moved to `removed`. A ticker of `meta.unvalued` is listed in the preview as "no valuation in the file" and nothing is written for it.
11. Confirm and ticks (advisor 3). The preview carries one general line that the owner must tick before the Confirm button works: "V is per listed share, in the listing currency". A company whose `currency` is not the currency of its R market (USD for `US`, JPY for `JP`, HKD or CNY for `HKCN`: an ADR priced in another currency than the file's market) needs its own tick, and so does every unmatched name (Decision 7); an unticked row is skipped and listed as "not confirmed". The ticks are posted as the tickers of the rows ticked. The Confirm button is also off when the plan has no insert at all.
12. The write order and failure. The confirm post writes, in this order and each as one Writer call: the margin table if `insert`, the R version if `insert`, then per row in file order the profile (new or pool change), then the review. A failure of one call stops that row, is listed with a fixed text without any value, and the other rows go on; no half row is hidden: the result lists every row with `inserted`, `same`, `older`, `refused`, `not_confirmed` or `failed`. Running the confirm again with the same file writes only what is not yet stored (equality, Decision 8).
13. The page shows data and computes nothing: every number and text of the preview is written by the page builder from the plan (the buy-zone tops of both sides are plan fields). The web prints them. The page is in Chinese for hints, with the technical word explained next to it (the owner's rule): "R (折现倍数 R)", "买入区间上沿", "重估类型 first / event".
14. The upload is the only input. No command line wrapper, no folder watch, no scheduled import. An `ot` wrapper would be one thin call of the same two functions and is not built (Left out).
