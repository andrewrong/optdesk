Goal (stage 1): one long-running process, `ot scheduler`, that calls the existing `Reconcile` at the slots the jobs declare (slots come from the trading calendar), once at start plus 10 minutes and every 15 minutes, keeps every fact of
its work in PostgreSQL, runs alone (a PostgreSQL advisory lock), and says in one place what is late, partial or missing. Job contents (fetches, compute, reports, alerts) are not designed here. Lanes, hand requests and resumable units are stage 2 (Left out):
today there are three jobs and one gateway, and stage 2 needs a real job that asks for it.

What main holds today: `ot run-once` and `ot backfill` (`cmd/ot/runonce.go`, `cmd/ot/backfill.go`) run one `Reconcile` call and exit. The runner runs the keys of a day one at a time on the calling goroutine (private `reconciler.run`), holds the one row of
`ops.run_lease` (10 minutes, no renewal, expiry computed from the database's `now()` in `Acquire`) for the whole call, and nothing starts a call. The run table, the present marks, the windows and the cursor in `ops.*` already are the state machine; this design starts the calls and adds what is missing around them.

## Decisions

1. Own code behind an interface, no scheduling library. Owner rule of 2026-11-08: our own code, even thin glue, sits behind an interface so that a library can replace it later. The interface is `runner.Scheduler` (`Run(ctx) error`, `LastTick() time.Time`, `FenceHeld() bool`, in `internal/runner/api.go`), built by `runner.NewSchedulerFunc`;
   the fence is behind `store.InstanceFence` and `store.Fence` and the run of one key behind `runner.KeyRunner` (Decision 8). `cmd/ot` sees only these. The real reasons, replacing the revision-1 text:
   - The state is already in `ops.*`: `ops.capture_run` (run, lease, heartbeat, reason), `ops.capture_present`, `ops.dataset_window`, `ops.reconcile_cursor`, and `Reconcile` is the state machine over them. A library that keeps a job table or a job list (river, gocron) would hold a second copy of that state or replace `Reconcile`, which works and has tests. That is the deciding reason.
   - `github.com/riverqueue/river` (v0.51.1 of 2026-11-05, MPL-2.0, deps: pgx v5, its own driver module and others): pre-1.0, so the API is not stable (AGENTS.md criterion); MPL-2.0 is file-level copyleft, short of "permissive"; it brings its own schema outside the goose migrations and the per-role grants. Its periodic jobs could take a calendar-driven next time
     (`PeriodicSchedule.Next`), and `.golangci.yml` lets pgx be imported under `internal/store/**`, so it could be placed there; neither changes the first reason. Not chosen. Its PG touching would also need the owner's word.
   - `github.com/go-co-op/gocron/v2` (v2.23.0 of 2026-10-26, MIT; deps: clockwork, uuid, robfig/cron/v3): it has `WithClock`, one-time jobs and an elector hook, so a calendar slot can be expressed; but its job list lives in memory and the fence and the missed-run logic would still be ours. Not chosen now; it is the likeliest library behind `runner.Scheduler` later.
   - `github.com/robfig/cron/v3` (MIT, last tag 2020-01): cron strings only, no injectable clock. Not chosen.
   - Size, stated as it is: the wait loop is small (the part a library would replace); the stage-1 work is fourteen issues around it (slots, run of a key, gaps, fence, commands). The pull request that lands the ticker carries `Design: own implementation, because ...` with this text. No issue below adds a direct dependency;
     `github.com/jonboulle/clockwork` v0.5.0 is already one (`go.mod`).
2. Process: resident, not one-shot (owner requirement of 2026-11-08). `ot scheduler` is a subcommand of the one `ot` binary, a long-running process that stays up, and a separate process from `ot serve` (`cmd/ot/serve.go`); serve never starts, stops or embeds it, and no cron or launchd runs it. It shuts down gracefully on SIGTERM (Decision 10), runs alone (Decision 5)
   and answers health: a listener on `127.0.0.1` only (port `OT_SCHED_HEALTH_PORT`, default 8765 in code, since `.env` holds secrets only), `GET /health` is 200 while `Scheduler.FenceHeld()` is true and `Scheduler.LastTick()` is no older than 60 seconds on the clock, 503 otherwise; `LastTick` is set to the clock's now when `sched.New` builds the scheduler (the first tick is at start + 10 minutes, so a zero value would make every deploy 503 for 10 minutes and crew would roll it back) (any other path 404), and `ot scheduler status` (Decision 11) gives the detail.
   The way is a host service under the crew keeper (tmux, no launchd), decided by a trial of 2026-11-08 (the dispatcher's): a Unix socket listening on the host in a directory bind-mounted into a container (OrbStack running, `docker run --rm -v <dir>:/sock ...` connecting to `/sock/s.sock`) gave `ConnectionRefusedError` twice and the host listener never saw a connection. OrbStack does not forward a host Unix
   socket through a bind mount here, and the broker jobs reach pyside only by the sockets under `$OT_HOME/run/` (`docs/deploy/pyside.md`), so the scheduler cannot run in a container; `rules/service.md` allows the host for what a container cannot do. The entry is `way = "host"`, proposed in `docs/deploy/scheduler.md`. `ot serve` stays in docker: `cmd/ot/serve.go`, `site.go` and `page.go` name no broker and no socket
   (checked on main), it reads PostgreSQL only. Owner decisions of 2026-11-08: the machine itself starts nothing (the IB gateways need a re-login after a boot anyway) and the owner starts the keeper, which brings the scheduler up and restarts it after a crash. In crew's terms that is `boot = true`: the keeper skips every host service with `boot = false` (`cap_keeper.go:294`, confirmed by agent-crew-dispatcher), no other `services.toml` key gives restart on a crash, and the exit status 75 contract below also needs `boot = true`. So the entry is `boot = true`, which here means "started and restarted by the keeper the owner starts", not a start at machine boot (no launchd);
   after the owner's first deploy, deploys run automatically on merge with automatic rollback (`deploy` is not `"owner"` after the first). PostgreSQL is in docker and is the only state.
3. Schedule, plain values, not a runner type. Each job answers one optional method, in the manner of `Windowed`: `Schedule() (calendarID, anchor, zone string, offset time.Duration)`. A job package imports no runner type, so the `jobs` row of `docs/design/modules.md` keeps its depends cell as it stands (this design does not change it; the revision-1 claim that a job returns `runner.Slot` was wrong).
   `anchor` is `session_open` or `session_close` (taken from `clock.Calendar.Session` of the calendar, so an early close moves the slot; `zone` empty) or `time` (`offset` is the wall time since midnight in the named `zone`, on session days of the calendar). `offset` may be negative (the US close slot is `session_close` with `-30m`).
   The runner root declares the same values, with the job id, as `runner.Slot{JobID, CalendarID, Anchor, Zone string; Offset time.Duration}` for its own use, and `internal/runner/sched` converts. One slot per job in stage 1 (several a day: stage 2). Instants are computed in UTC from the calendar and `time.LoadLocation`; the owner's display time zone (from configuration) is only for printing.
   A job without `Schedule()` is run only by the 15-minute ticks.
4. The ticker. One goroutine waits with a `clockwork.Clock` timer to the next of: the next slot start, the next reconcile tick (start + 10 minutes, then every 15), and a 30-second ceiling; after every wake it recomputes from `Now()` (never from a monotonic delta: a sleeping Mac stops it). When a slot start has passed or a tick is due it hands one
   `Reconcile(ctx, day)` for today (and the open days after the cursor, which `Reconcile` already walks in order and in one call) to a worker goroutine and goes back to waiting. The loop calls no ledger, broker or job; every worker call has a `context.WithTimeout` and the ledger connection sets `lock_timeout` and `statement_timeout`.
   A stop of 15 hours is one `Reconcile` call at start, not one close per missed occurrence. Time is injected: `clock.Clock` has only `Now()` (`internal/clock/api.go`), so `runner.NewSchedulerFunc` takes a `clockwork.Clock` (a subset of which `clock.Clock` already is) and the root package of runner gains that import (see Reversals).
5. Single instance by a PostgreSQL session advisory lock, taken before anything else is opened. `cmd/ot` is the one owner of the lock: it calls `store.InstanceFence.TryLock(ctx, build)` once, before anything else is opened, and hands the held `Fence` to `sched.New`, which never locks (a second `TryLock` of one process would open a new connection and fail). `TryLock` runs `pg_try_advisory_lock` on a dedicated connection that nothing else uses and returns a `Fence`: it is released by the database when the connection or the process dies (no TTL, no epoch,
   no table), and `Fence.Lost()` closes when the connection drops, which the ticker turns into a cancel of the process context; the ticker closes the `Fence` on drain (the run lease is not the ticker's: Decision 6). A second `ot scheduler` retries in `cmd/ot` for 60 seconds and exits non-zero (the retry loop is new in `sched-cmd-run`: `cmd/ot` at main calls no `TryLock`, and the loop runs on the injected clock). A watchdog goroutine of the ticker makes `Run` return a sentinel error (the exit is `cmd/ot`'s) when the loop's tick counter has not advanced for 60 seconds (a frozen loop does not hold the fence; the keeper restarts it). The build id is written by `cmd/ot` to
   `ops.scheduler_state` (below) after the lock is held, so `status` shows which build runs. Stated residual: a process frozen so long that its connection drops, and that then wakes, can write once before it sees `Lost()`; the writes of `Reconcile` are idempotent (deterministic run and capture ids), so the cost is a repeated key, not a wrong one.
6. Run lease. The existing `ops.run_lease` stays and is renewed: `Reconcile` and `Backfill` are given a renewal every 30 seconds while they run (`RenewLease` on `SchedulerLedger`, SQL `now()`), so a call longer than 10 minutes no longer lapses its lease, and a scheduler that is killed leaves the lease for at most the remaining TTL, which the next
   `Acquire` already waits out as `Retryable` (the next 15-minute tick). `Reconcile` releases the lease itself, by its own `defer`, when the context is cancelled on drain; the ticker does not touch the lease. Hand commands (`ot run-once`, `ot backfill`) first try the advisory lock; while the scheduler holds it they refuse (exit non-zero, the text names `ot scheduler status`). The one hand path for a key the scheduler gave up on (a key closed by the Close table) is: stop the scheduler, run `ot backfill` for the day, which is behind the cursor once its window has closed, and start the scheduler again.
7. Counting of runs (changes `docs/contracts/runner.md`: v4). Only a run that reached a verdict spends the allowance of two runs per key and day, and only a `partial` run can take the second one: a verdict of any other kind (done, a `Permanent` error, `NoValue`) ends the key at its first counted run, as in v3 (Decision 8 gives the start rule). A run ended by a graceful stop (reason `abandoned_stop`) or a `running` run whose lease ran out without a verdict (`crashed`) is not counted, as lessons 7 and 9 require. The brake against a crash loop stays, and it is in the unit that
   exists, the key and the day (there is no occurrence in stage 1): three runs of one `(day, dataset, subject)` that ended `crashed` or `abandoned_stop` (the brake counts only these two; `empty_before_close` runs and retryable runs before the close are not counted by anything) stop the key with reason `crashed_repeatedly`: no new run before the close, and a gap is written; the cursor holds until the window close, where the Close table (after Decision 8) decides. The encoding is one rule counted twice, with no new run row: the reasons are the fixed strings `crashed` (the reconciler's mark on a `running` run whose lease lapsed) and `abandoned_stop`, written in `docs/contracts/runner.md` by `sched-runner-interface`; `Reconcile` counts the runs of the key that carry them and stops at three, and the gap syncer counts the same runs through `store.OpsLedger` and writes the gap when it finds three. Before the close no run carries `crashed_repeatedly`; the Close table says on which run it is written at the close, and the gap syncer treats that run as proof of the stop, as it treats three runs that carry `crashed` or `abandoned_stop`, so `sched-gaps` and `sched-reconcile-count` need no order between them. This replaces runner v3's "a crashed run counts" and its cap of one crash re-run by the brake of three; the replacement lets three process deaths happen before the gap, and the keeper's own restart backoff
   bounds how fast they can.
8. One entry point for one key, in the runner. `runner.KeyRunner.RunKey(ctx context.Context, job contracts.Job, day contracts.Day, key contracts.ExpectedKey, attempt int, closeAt, deadline time.Time, reason string) (store.Run, error)` runs one key through the given job (`attempt` makes the deterministic `Run.ID` `day|dataset|subject|attempt`; `closeAt` is the window close that `empty_before_close` needs; `reason` is `late` or empty) under a context that ends at `deadline` (the run bound; a cut run with `Returned > 0` is recorded `partial`: a verdict that spends the allowance (the crash brake and the two-run allowance of Decision 7 still bound the reruns) but does not end the key and does not mark the key present, even when `Usable > 0`. The key stays missing, and `nextAttempt` gets a new start rule for it (v3 starts a run only when no counted run exists): start a run when no run of the key is `running`, fewer than two counted runs exist, and the latest counted run is `RunPartial`; a verdict of any other kind (a `Permanent` error, `NoValue`, done) ends the key as in v3, and the crash re-run of a lapsed `running` lease stays (the lapsed run is marked `crashed`, which Decision 7 does not count, so the key is started again, up to the brake of three). So the key is run again on each tick until a full run, a second `partial`, or the window close. `reconcileDay` (which already runs a missing key through `nextAttempt`), the completeness rule of runner v3 (a day is complete when every key is `present` or `no_value`) and the cursor do not change: the day is not complete while the key is missing, so the cursor holds (the owner's "关键补": the scheduler repairs an incomplete key itself inside its window). At the window close the Close table below decides, in its order, and every other place refers to it. A rerun only fills the missing rows (`ON CONFLICT DO NOTHING`, the advisor's decision of 2026-11-08). The present mark of every other run is decided by the run path of runner v3 as before. A rerun relies on one runner contract: the same key written again adds the rows that are missing and leaves the rows that exist, with no duplicate. Main already gives it: `internal/store/series/writer.go` (`insertPointSQL`, `ON CONFLICT DO NOTHING`, line 29) and the snapshot writers (`internal/store/snapshot/optioneod.go`, `quotesnapshot.go`, `ON CONFLICT DO NOTHING`) insert on the natural key, so a rerun completes a partial without changing its rows (a source value that was revised is not overwritten; that is the writers' rule and not changed here). A job whose writer is not idempotent in this way must not be registered; this issue adds no job),
   writes the run row with heartbeat and lease renewal every 30 seconds, consults the job's optional `Postcondition` for "present" (`Postcondition(ctx context.Context, day, datasetID, subjectKey string) (bool, error)`: whether the rows of the key exist now; `RunKey` calls it after a run that was not cut, passing the strings of `contracts.Day` and `contracts.ExpectedKey`, and marks the key present only on true with a nil error; a cut run never marks present; a false or an error is recorded as a `done` run without a mark, not as `partial`: the key stays missing, the start rule below does not run it again, and row 4 of the Close table closes it), and is what the private `run` of `reconcile.go` becomes: `Reconcile` and `Backfill` call it for every key (so there is one path that runs a job, and a hand backfill and a tick cannot differ). It takes no lease of its own in stage 1 (the caller holds `ops.run_lease`);
   a per-key lease is what stage 2 changes to run lanes in parallel. The deadline of a run is `max(CloseAt, start) + RunBound`, where `start` is the instant of the injected clock when `RunKey` begins the run and `RunBound` is a plain value of an optional `Bounded` method of the job (default 30 minutes): a run that starts before the close is cut 30 minutes after the close, and a late run (reason `late`, started after the close, Decision 4 and the Close table) or a hand `Backfill` of a closed day is cut `RunBound` after its own start, so a run is never open-ended and never already expired when it starts.
   Preflight in `cmd/ot`, run at start and again on every tick (no job-side `Preflighter`; it is in Left out). A job never holds the FRED key or the socket path (`fredseries.New` gets a built `sources.Source`; `optioneod.New` and `quotesnapshot.New` get a `broker.Broker`, the stand-in `unreachableBroker` after a failed dial; `internal/jobs/api.go` does not change), and `broker.Broker` has no status method. So `cmd/ot` checks the inputs of each job (`cmd/ot/preflight.go`, `sched-cmd-run`): an empty `FRED_API_KEY` leaves `fred_series` out, a failed broker dial leaves `option_eod` and `quote_snapshot` out. The check runs first at process start, before the reconciler is built, and then again by the ticker for every job that is left out, on every tick (the re-probe below). In plain words: a job whose key or broker is missing is not in the job list that goes to `NewReconcilerFunc`, nor in the ticker's schedule; `cmd/ot` logs one line with the job id and the reason (no key, no path), the other jobs run, and the left-out job comes back on the first tick whose probe passes, with no restart. Nothing of a job is forwarded or wrapped: `Schedule`, `RunBound`, `Postcondition` and the others stay on the real job.
   The left-out ids go to the scheduler: `cmd/ot` passes `disabled map[string]string` (job id to reason text, nil for none), a parameter of `runner.NewSchedulerFunc` declared in `internal/runner/api.go` (`sched-runner-interface`). It is the initial set, and its owner is the ticker, one rule: `sched.New` copies it on entry, `cmd/ot` never touches the map after the call, only the ticker's goroutine (and its worker tasks, one at a time) reads or writes the copy, and every `GapSyncer.Sync` is given a fresh copy, so no map is shared between goroutines. The ticker writes each reason to `ops.scheduler_job.disabled_reason` (`JobState.DisabledReason`) and hands the copy to `GapSyncer.Sync`, which writes one `preflight_failed` gap per left-out job per day (Decision 9), so the notify module alerts on it; `ot scheduler status` is red while the gap is open.
   The re-probe (the owner's decision of 2026-11-08 that dropped it was reversed by the owner on 2026-11-08, choosing option a after the advisor's review: a broker dial that fails at start would otherwise leave `option_eod` and `quote_snapshot` out for the whole day, against the self-repair rule). The probe is the optional interface `runner.Prober` (`Probe(ctx context.Context, jobID string) (reason string)`, an empty reason means the inputs are there), declared by `sched-runner-probe`; the value given to `sched.New` as `rec` may implement it, and the `NewSchedulerFunc` signature does not change (a `rec` without it means no re-probe, so the ticker tests that need none stay as they are). On every tick, before it calls `Reconcile`, the ticker calls `Probe` for each id in its copy of the map, one after the other as one worker task with its own timeout, on the same worker goroutine as `Reconcile`, so a probe never runs at the same time as a `Reconcile` (one dial and one env check per disabled job: cheap). A non-empty reason updates the entry and `disabled_reason`; an empty reason removes the job from the map, and the same tick's `Reconcile` already runs its keys. A probe that panics or times out counts as a failure and keeps the old reason. The next `GapSyncer.Sync` gets a map without the job and clears `preflight_failed` (Decision 9), and the job's keys reconcile for the rest of the window and on the later days. In `cmd/ot` the `Prober` is `swapReconciler` (`preflight.go`), a type that holds the `Reconciler` built by `NewReconcilerFunc` from the enabled jobs and implements `Reconciler` and `Prober`: on a passing probe it builds the job anew (a fresh dial for the two broker jobs; for `fred_series` the key as loaded), builds a new reconciler from the enabled list plus that job through `NewReconcilerFunc`, and swaps it under a mutex (between two `Reconcile` calls, by the rule above). A static cause is simply checked again: `FRED_API_KEY` is read once at start (the source is built with it), so the probe of `fred_series` returns the same reason every tick until the process restarts; it goes through the same path, so there is one rule for every disabled job and no second one for a static failure. Own implementation, because no library probes a job's inputs; it sits behind `runner.Prober`, so a library can replace it (Decision 1).

**Close table.** In `reconcileDay`, `expireIfClosed` (runner v3, changed in `sched-reconcile-count`) runs before `nextAttempt`, and it looks only at a key that is still missing, whose window has closed, and no run of which is `running`. For such a key it takes the first row that matches. The table is not total: a key that matches no row is not closed, and `nextAttempt` then decides (the cases are listed under the table). Every row makes the key `no_value`, so the day completes and the cursor advances. A dataset with no window has no close, and no row applies to its key. The one clearing rule, for all rows: the gap clears when the key is present, or `no_value` with a reason other than `expired` and `crashed_repeatedly`; the hand path that gets there is `ot backfill` of the day with the scheduler stopped (Decision 6), checked by the next `Sync`.

| # | Case | Run whose reason is rewritten | Status and reason after | Gap kind |
|---|------|-------------------------------|-------------------------|----------|
| 1 | the key was stopped by the crash brake (three runs that ended `crashed` or `abandoned_stop`, Decision 7); this row wins over row 2 | the latest of those runs; runs after it stay as they are | key `no_value`; run reason `crashed_repeatedly` | `crashed_repeatedly` |
| 2 | else the latest counted run is `RunPartial` | that `RunPartial` run; uncounted retryable runs after it stay as they are | key `no_value`; run reason `expired`; run status stays `partial` | `partial` |
| 3 | else the key is retryable (runner v3: its last run is a retryable run that is not `crashed`) | its last run | key `no_value`; run reason `expired` | `expired` |
| 4 | else the latest counted run ended `done` without a mark (a `Permanent` or other non-retryable error that is not `NoValue`, or a false or erroring `Postcondition`) | that latest counted run | key `no_value`; run reason `expired` | `expired` |

Keys the table leaves alone, and what happens to each: a key with no counted run and not stopped by the brake (no run yet, only `empty_before_close` runs, or one or two `crashed` or `abandoned_stop` runs) is not closed: `nextAttempt` starts a late run (reason `late`, Decisions 4 and 11, lesson 11), and the table applies only after that run has been counted (a late run that is empty gives `no_value` at once, v3); a key with a `running` run is not closed: it waits for its lease, and a lapsed lease is the crash path of `nextAttempt`. Where a key is not missing, nothing applies: present (usable rows and `Postcondition` true), `NoValue`, and an empty answer after the close are `no_value` at once (v3). The outcomes that do reach the table: a retryable error, or an empty answer before the close, then the close, is row 3 when the last run is the retryable one (an `empty_before_close` run carries no error code, so it is the late-run case above); a cut run with rows is row 2; the brake is row 1; a `Permanent` error and a false `Postcondition` are row 4.

9. Gaps, one record. `ops.job_gap` (job, dataset, day, reason, `first_seen_at`, `reported_at`, `cleared_at`) is written by the scheduler after each `Reconcile` from the runs and the present marks: a key closed at its window close by the Close table (gap kinds `expired`, `partial`, `crashed_repeatedly`, as its last column says; a key that is still missing past the close gets the kind of the row that matches), a `preflight_failed` job (one per left-out job per day, Decision 8); `Gap.JobID` is set only for `preflight_failed` (the syncer is given the left-out job ids, not the jobs); a key gap (`expired`, `partial`, `crashed_repeatedly`) carries `DatasetID` and no `JobID`, and a `preflight_failed` gap carries `JobID` and no `DatasetID`; the key columns of `ops.job_gap` are not null and hold the empty string for the missing one, and `ot scheduler status` prints the dataset for a key gap and the job for a preflight gap; `ops.job_gap.reason` is free text (no CHECK or enum in a migration on main; `sched-store-ops` writes none, and `Gap.Reason` is a string), so `partial` is a new value and no migration changes; key gaps clear as the Close table says; `reported_at` has one owner, the `notify` module (stage 1, `docs/design/notify.md`, not an issue of this design): the scheduler process calls `Notifier.NotifyGaps` after each gap pass, which says the open gaps that have no `reported_at` and then calls `SchedulerLedger.MarkGapReported` (writer `ot_runner`), so no issue of this design calls `MarkGapReported`, and the column is set by the notify wiring; a page never sets it (pages read through `ot_ro_pages`, which may not write), shows every open gap whether or not `reported_at` is set, and prints `reported_at` as information only ("said at ..."); it never skips or repeats a gap because of it.
   Pages read through `store.GapReader` (role `ot_ro_pages`) from two views in schema `rd`, not from base tables: `rd.job_gap_r1` (the open and cleared gaps) and `rd.expectation_r1` (derived from `ops.dataset_window`, whose `close_at` is the due-by instant, and `ops.capture_present`); `OpenGaps(ctx)` and `Expectations(ctx, from, to)` read them, and an `Expectation` is `{DatasetID, ExpectedDay, PresentDay, DueBy, Gap, Closed}` (`Closed` true: the day has no session, so CLOSED; the landed view `rd.expectation_r1` of `sched-store-ops` (#427) takes it from `ops.dataset_window`: a window row with neither `open_at` nor `close_at` is a day without a session, and a day with no window row at all has no expectation, so UNKNOWN; `Closed` false with a zero `ExpectedDay`: no expectation, so UNKNOWN). This keeps the owner's schema v3 rule (restated in `docs/design/store-week2.md`): `ops` is written by `ot_runner` only and `ot_ro_pages` reads views of `rd` with no grant on a base table.
   `ops.job_gap`, `ops.scheduler_state` (one row, the build) and `ops.scheduler_job` (one row per job: next start, window end, `restart_sensitive`, `disabled_reason`; written by the ticker) sit beside `ops.capture_run` and the other tables of `migrations/0003_ops_ledger.sql`; they replace nothing. Schema v3's `ops.job_run`, `ops.job_event` and `ops.stream_gap` are not on main (`docs/design/store-week2.md` defers `ops.job_event` to a design `capture-ledger`, and `docs/design/modules.md` names `job_event` as an input of notify): this design neither creates nor replaces them; `notify` will read `rd.job_gap_r1` until that design says otherwise, and the advisor is asked whether `job_gap` should later be folded into `job_event`.
   One pure function `gaps.Freshness(Expectation, now) State` in `internal/pages/gaps` gives FRESH, LATE, STALE, UNKNOWN, INVALID or CLOSED: the five of lesson 14 plus CLOSED, because the owner wants 休市 and not 过期; a day without a session has no window, so a holiday is CLOSED. INVALID is a `PresentDay` after the expected day, or an expectation with no `DatasetID`.
   `stale_after` of a page is the `DueBy`. Sending a message is the `notify` module, left out; it will read the same rows.
10. Restart guard. Crew has no hook that asks a service before a restart or a deploy (both end the tmux session), so safe restart is the scheduler's own job. It drains: on SIGTERM the loop stops, the worker gets a 30-second grace, the run in hand is finished or cut at the end of the grace, and the drain rule is one: a cut run with `Returned > 0` ends `partial` (a verdict, counted like any partial run, and rerun by the tick under Decision 8), a cut run with `Returned = 0` ends `abandoned` with reason `abandoned_stop` (not counted, Decision 7); then the fence is closed and the process exits (the lease is released by the cancelled `Reconcile`'s own `defer`, Decision 6). The run row is written by `RunKey` (`sched-run-key`: `TestRunKeyCutWithoutRowsIsAbandonedStop` and `TestRunKeyCutWithRowsIsPartial`); the ticker only cancels the worker after the grace and closes the fence (`TestDrainCancelsWorkerAndClosesFence`). For a replacement of its binary the scheduler compares its executable identity (size, mtime, inode of the first element of `run`) at each tick, drains when it changed and exits with status 75, the one drain contract of crew (`rules/service.md`: one uncounted keeper restart per new identity). `ot scheduler can-restart` exits 0 only when no run is non-terminal and no job marked `restart_sensitive` is between its slot start and its window close; it prints the reason otherwise. `restart_sensitive` is a boolean key of the `[schedule]` table of a job's `job.toml` (default false), answered by the optional plain method `RestartSensitive() bool`; the ticker writes it with each job's window end to `ops.scheduler_job`, and `can-restart` reads that table (so it needs no job code); crew never calls it, a person or the dispatcher runs it before a hand restart. The key and the method are owned by `sched-jobs-schedule`; the method is declared in `sched-runner-interface`.
    It is advice, and after the first deploy it is not even asked: crew's automatic deploy and rollback restart the scheduler on merge without calling it, and crew's `restart` bypasses it. Lesson 8's "no restart in a window" is therefore recorded, not enforced, and a merge during a sensitive slot costs a drain (the run in hand ends `partial` or `abandoned` by the drain rule above) and, for an `abandoned` run, a repeat of that key on restart. Enforcing it needs a pre-deploy hook in crew, which is not ours (open question 1).
11. Progress. A run row's `heartbeat_at` and `lease_until` are renewed by `RunKey`; `ot scheduler status` reads only `ops.*` (instance build, non-terminal runs with age and last heartbeat, next slot per job, open gaps) and opens no dataset store and no broker; exit 0 green, 1 red.
12. A generic job, not a fetch. The scheduler core knows a job only as `contracts.Job` registered by id, plus the optional plain-value methods: `Schedule` (when), `Bounded` (the time budget), `Postcondition` (what must exist afterwards), and `Run`/`Plan` (what it does). An `ExpectedKey{DatasetID, SubjectKey}` is opaque to the runner
    (`docs/contracts/runner.md`: "Keys are opaque; it never reads dataset content") and names an output, not a fetch: `{obs.option_eod, SPY}` for a capture, `{report.morning, 2026-11-09}` for a report, `{alert.margin, 2026-11-09}` for an alert evaluation. "Postcondition" is "this output exists for the day". The core imports no job package and no dataset type;
    adding a new kind of job (compute, report, alert) is a new package under `internal/jobs/` that implements `contracts.Job` and the optional methods, plus one line in the registry that `cmd/ot` wires: no change to `internal/runner`, `internal/runner/sched` or the ledger. Data collection (`fred_series`, `option_eod`, `quote_snapshot`) is only the first registered jobs.
    Stage-1 limits that a later job may meet and that are in Left out: one slot a day per job, and a day-keyed output (a job whose unit is not a session day, such as an intraday alert, needs the occurrence of stage 2).
13. Time and tests. No `time.Now`, `time.Sleep` or `time.After` in the packages below; time comes from a `clockwork.Clock` (the fake in tests, advanced with `Advance` and `BlockUntilContext`; the existing runner tests use `clockwork` fakes); no test sleeps; every test is `t.Parallel`; PostgreSQL tests carry the build tag `pg` and run in GitHub CI only; no test dials a broker.

## Reversals this design makes, stated

- No departure from schema v3 or from `migrations/0003_ops_ledger.sql` ("ot_ro_pages reads views of rd only: no grant on ops"): pages read the views `rd.job_gap_r1` and `rd.expectation_r1`, and `ot_ro_pages` gets `SELECT` on those two views only. (An earlier draft granted three base tables; the advisor's opinion of 2026-11-08 replaced that.)
- Two invariants of `docs/contracts/runner.md` change, both in `sched-runner-interface`: line 30 "No `time.Now` or `time.Sleep`: time comes from the injected `clock.Clock`" becomes "... from the injected `clock.Clock`, and from a `clockwork.Clock` where a timer is needed", and line 31 (the root depends on `contracts`, `clock` and `store` only) gains `clockwork`: the root package imports `github.com/jonboulle/clockwork` because `runner.NewSchedulerFunc` takes a `clockwork.Clock`. `clock.Clock` is not widened (`internal/clock/api.go` is not edited).
- Runner v4: a crashed or abandoned run is no longer counted, with the per-key brake of Decision 7 (reverses v3 "a crashed run is not covered by this and still counts"); the brake of three is written into `docs/contracts/runner.md` next to the two-run cap, in `sched-reconcile-count`.
- Lease arithmetic stays on PostgreSQL's `now()`: `Acquire` already computes expiry in SQL, the new `RenewLease` does the same, and the advisory lock has no expiry at all. No process-clock lease exists (revision 1's instance lease, which would have used the process clock, is dropped).
- `ot run-once` and `ot backfill` refuse while the scheduler lives (a change of the commands of `docs/contracts/ot.md`).
