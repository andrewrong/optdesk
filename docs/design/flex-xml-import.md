Status: draft. Read on origin/main at 3ee2a21ad79f (code unchanged since 6a6a646e55db). "[unverified]" marks a claim not checked in code, docs or a probe.

Goal. On `/flex-import` of `ot serve --owner-edit` the owner chooses one or more `.xml` or `.gz` files, presses one button, and the page shows, per file, one of five statuses (stored, already present, nothing found, account not configured, failed) with the counts per alias, and, after a reload, the recent imports and their failures (every request that read at least one file leaves its records; a request refused before any file is read leaves none, Decision 3). The trades are parsed, mapped and stored by the daily job's code. The import only adds: a trade whose key is already stored is left as it is and counted as already present. No terminal step.

## What main holds today

- The daily job reaches a report through `FlexSource.Fetch` (`internal/jobs/optionledger/job.go:293`). `parseReport` (`internal/sources/flex/parse.go:119`, called at `client.go:162`) is unexported and takes the whole body as `[]byte`; `maxBody` is 50 MiB (`client.go:24`); `prelude` (`parse.go:17`) refuses a DTD or an entity. `RawSHA256` is the SHA-256 of the raw body (`client.go:166`). Only `<Trade>` rows of level `EXECUTION` are kept; other levels are counted and dropped (`parse.go:12` and the comment at `:115-118`). A Trade without `transactionID` or `levelOfDetail`, a wrong root, a document type, an encoding or XML error all refuse the report as kind `not_report` with a code (`parse.go:23`, `:27`, `:125`, `:143`, `:179`, `:195`, `:198`). The raw XML is not kept (`option-ledger.md` Decision 5).
- `mapStatement` (`internal/jobs/optionledger/map.go:19`) is unexported; it maps an account number to its alias through `OptionLedgerConfig.Accounts` and reports an unmapped account as `ok` false.
- `RecordFlexFetch(ctx, rec, rows)` (`internal/store/api.go:673`) is one transaction, with the revision rule per row (a new key is New, an equal hash is Unchanged, a changed hash is written as the next revision, Revised). The table `optionledger.flex_fetch` has the primary key `fetch_id` only (`migrations/0022_optionledger.sql:11-30`), and `fetchID` is `Login/QueryID/StartedAt` with no alias (`internal/store/optionledger/store.go:263-265`); `insertFetchSQL` is `ON CONFLICT DO NOTHING` and a count other than 1 is an error that rolls the transaction back (`store.go:119`). So two records with the same login, query id and start instant cannot both be written.
- The store replaces the counts a record carries for new, revised and unchanged rows by what the call did (`store.go:75-76`, `fetchArgs`), so only `RowsParsed` of a record is the caller's. The view `rd.flex_fetch_r1` shows every record, failed ones too, with the columns `fetch_id`, `login`, `query_id`, `first_date`, `last_date`, `started_at`, `finished_at`, `status`, `error_kind`, `error_code`, `raw_sha256`, `parser_version`, `statements`, `statements_unmapped`, `rows_parsed`, `rows_new`, `rows_revised`, `rows_unchanged` (`0022:54-56`), and `ot_ro_pages` and `ot_w_optionledger` can read it (`0022:72` and `:77`). The only read of it in Go is `LatestOkFetch` (status ok only; `store.OptionLedgerReader` has `FlexTradeRows`, `LatestOkFetch`, `StoredAliases`). `FlexTradeRows(alias)` returns the highest revision of every transaction of the alias. The job's window reads `LatestOkFetch(login, queryID)` (`job.go:267`); a record under another login leaves the window untouched.
- The dataset `optionledger.flex_fetch` r1 is a published contract (`contracts/datasets/optionledger.flex_fetch.r1.json`, its page `docs/contracts/datasets/optionledger.flex_fetch.md`, the generated `FlexFetch` in `internal/contracts/gen/records.go`): `login` matches `^[a-z][a-z0-9_-]{0,31}$` and is the name of a login of flex.toml, `query_id` matches `^[0-9]+$` (Flex query id, digits), `first_date` and `last_date` are required dates, `status` is `ok` or `failed`. The table has no CHECK beyond the key (`0022:11-30`) and only fixtures are validated against the schema, so the database would accept what the import writes, but the import's records (Decision 2) do not fit r1. The rule of `docs/contracts/00-protocol.md` is: a version freezes at its first consumer, an incompatible change bumps it, and "a version that has a consumer changes by a bump in its own issue"; r1 has consumers (`LatestOkFetch`, the daily job's records, the generated type). So Decision 12 and entry 0 bump it.
- `internal/store/api.go` has 800 lines and is not in `docs/design/ratchet.json`; a line added there is a file over 800 lines, which needs a ceiling an agent never writes. So the new read below is declared in a file of its own (Decision 8).
- `cmd/ot/optionledger.go:162` `flexConfig` builds `Accounts` (account number to alias) from `flex.toml` and the env file; the number never leaves it. This design does not read `flex.toml` itself.
- `ImportOptionTrader` (`importfile.go:47`) and `cmd/ot/ledgerimport.go` are the older file import, for option-trader's JSON Lines; they stay.
- `ot serve` writes through one pattern today: `--owner-edit`, a loopback `--addr` (`serve.go:46` and `:52-53`), `OT_FORM_KEY` (at least 32 bytes) and the settings DSN (`newOwnerEdit`, `settings.go:53`, through `ownerEditSecrets`, `env.go:70`), a hidden `expires` and `mac` token on the page, `guardOwnerPost` (`settings.go:245`: Host, 64 KiB cap, `settingsform.Check`: remote address, Host, Origin, content type `application/x-www-form-urlencoded`, 64 KiB, MAC, expiry), and a store opened per post (`underlyings_post.go:116-120`). The guard refuses a multipart body, so it cannot carry an upload as it is.
- The page parts of a page are: a schema `contracts/schemas/page.<name>.vN.json`, a generated type `web/src/generated/<name>.vN.ts`, a builder in `internal/pages/<name>/`, a route in `cmd/ot`, a view in `web/src/pages/<name>/` (`docs/design/underlyings.md`, entries 3, 4, 8 and 11, are the model). `rules/frontend-stack.md` does not exist on main; the rule is `docs/adr/0034-frontend-stack.md`, which the UI lines below cite.
- The pages that read the stored trades are `positions_page`, `risk_page`, `household_page`, `option_result_page`, `home_options`, `option_tracking_page`, `structures_page` and `report_blocks` (`FlexTradeRows`). The Flex sections are written by the job (`sections.go`, `flexsection`) and no page or compute package on main reads them.

## Decisions

1. **One parse entry, shared.** `sources.ParseFlexFunc` (`func(r io.Reader) (FlexReport, error)`) is declared in `internal/sources/api.go`; its implementation is `flex.Parse` in `internal/sources/flex`, a new file that calls the same `parseReport` and `prelude`. `cmd/ot` is the composition root and imports `internal/sources/flex` and `internal/jobs/optionledger` directly in its new files; `cmd/ot/wire.go` (797 lines) is not touched and the deps struct gets no field. `flex.Parse` reads at most `maxBody` bytes after decompression; a body that starts with the gzip magic `1f 8b` is decompressed first (this is what makes option-trader's raw archive, one gzip per report, importable by upload: a `.gz` costs a few lines here, so it is in). `RawSHA256` is the hash of the decompressed bytes, so a file and its gzip have one hash, and it equals the daily job's hash of the same body. `FetchedAt` is left zero; the caller sets it. Errors are the existing kinds with codes: a body over the limit is `too_large`; a non-report, and any refusal of `parseReport` (Decision 3 lists them), is `not_report`; a gzip that cannot be read is `not_report` with the code `gzip`. No text carries a value. `client.go` is not changed.
2. **One mapping, add-only storage, one key rule.** `optionledger.ImportFlexReport` (a new file in `internal/jobs/optionledger`) takes the `FlexReport`, the `Accounts` map, a `store.OptionLedgerWriter`, a `store.OptionLedgerReader`, a `FlexFileRef` (request id, file ordinal) and `now`. It maps every statement with `mapStatement`, groups the rows by alias, and for each alias (sorted) reads `FlexTradeRows(alias)`. A row whose key (level of detail, transaction id) is stored, or repeats an earlier row of the same report, is already present and is not passed on; the rest is written by one `RecordFlexFetch`, so each of those rows is a key that was absent and is New. The import writes no revision of a stored key whatever its field set or hash, except when another writer commits that key between the import's read and its write (Doubt 8). There is no date rule: the 2025-12-01 boundary is not checked. The days of a record are always true dates (r2, Decision 12): the period of the file (`fromDate`, `toDate`) when both read, else the first and last trade date of the rows of that record, else the day of the request in UTC; an unreadable period does not refuse the file. A record of a failure carries the day of the request.
   **The key of every record** (success, no rows, unmapped only, failure) is the one rule: `Login` `import`, `QueryID` `file:<request8>:<ordinal>:<alias or ->`, `StartedAt` and `FinishedAt` the instant of the request (`now`, the same for all records of one post), `Status` `ok` for a record of a stored, present, empty or unmapped file and `failed` for a failure, `ParserVersion` the job's `parserVersion` (`job.go:30`, same package). Records of one post tie on `finished_at`; the read breaks the tie by `fetch_id` (Decision 8). `request8` is 8 hex characters from `crypto/rand`, made once per post by `cmd/ot` and passed in `FlexFileRef` (a fixed value in tests); `ordinal` is the position of the file in the post, counted from 1 (the entry `(more files)` of Decision 9 takes the ordinal of the first part not read); the last part is the alias of the record, or `-` for a record that has no alias. So `fetch_id` (`Login/QueryID/StartedAt`, `store.go:263-265`) differs for every alias of a file, for every file of a post (two files of equal bytes included), for a success and a failure of one file, and, through `request8`, for every post. The hash of the file is in the column `raw_sha256` of a success record, not in the key, so a refused file that has no hash needs no special key. No account number is in the key: the alias is a value of `Accounts` and is already in every ledger row.
   **The counts of a record.** `RowsParsed` is the mapped rows of the alias (new and already present together); the store writes `RowsNew` itself (all the rows passed on) and `RowsUnchanged` and `RowsRevised` as 0 (`store.go:75-76`). So the already-present count is derived, never read: `rows_present = RowsParsed - RowsNew - RowsRevised` (the revised term is 0 unless the race of Doubt 8 happened, and then the row is not counted as present). `Statements` is the statements of that alias. Unmapped statements are counted into the record of the first alias in sorted order, or into one record with the alias part `-` and no rows when no alias matched. A file that finds no trade row and no unmapped statement is also one record with `-` (status `nothing_found`). A mapped statement with no `EXECUTION` trade makes no alias group, so `Statements` of an alias counts only statements that had rows; if another statement of the file is unmapped, the file is `unconfigured` (one `-` record with the unmapped count), although the first alias is configured; this is accepted and named in Doubt 10.
3. **A failure is a record, and the writer is opened for it.** An import is not a runner job and has no job result, so its only trace is `flex_fetch`. A request that read at least one file opens the writer once, at the first record to write, failed records included, and writes: for each file refused or failed (`not_report`, `too_large`, `too_many_files`, `bad_gzip`, `store_error`) one record with `Status` failed, `ErrorKind` the fixed text `import`, `ErrorCode` the reason code (the column the page reads as `reason`; at most 64 bytes, never a value), the alias part `-`. The condition of each reason: `not_report` is any `not_report` of `flex.Parse` except the code `gzip`, and also a statement `mapStatement` refuses with `errBadRow` (a state `parseReport` already refuses at `parse.go:195` and `:198`, so unreachable and kept as a guard); `bad_gzip` is that code; `too_large` is the kind of that name; `too_many_files` is the ninth part of a post; `store_error` is a failed write of rows. The page's `reason` enum has exactly these five codes (there is no `bad_row` and no `bad_period`). A request refused before any file is read (the guard answers 403, the declared length is over the cap or unknown: 413, no ledger line, no `flex.toml`) opens no writer and leaves no record; its answer is a fixed text or the read-only page, and `recent` shows nothing for it. A write of a failed record can itself fail (the store is down): the page of that response shows `failed` / `store_error` and says nothing remains to reload (Doubt 2). The page after a reload reads the newest 50 records of the login `import` from the view (Decision 8) and shows each by the five statuses derived from the stored columns by one function, `optionledger.DeriveImportStatus` (entry 5), which the POST page and the recent list both use: `failed` when `status` is failed (reason from `error_code`); `stored` when `rows_new + rows_revised` is above 0; `present` when `rows_parsed` is above 0 and both are 0; `unconfigured` when `statements_unmapped` is above 0 and `rows_parsed` is 0; else `nothing_found`. The 50 records hold one post of eight files with a few aliases each; an older post falls out of the list (Doubt 9).
4. **Idempotence stated exactly.** A re-import of the same file writes no trade row: every key is already present, and the record says `RowsParsed` N, `RowsNew` 0, which the page reads as `present`. It appends one `flex_fetch` record per alias (the fetch table is a log, as for every daily run). No file name is stored (the record has no column for it): the recent list shows the time, the alias, the status and the counts.
5. **Account mapping is the job's.** The `Accounts` map comes from one function extracted out of `flexConfig` (`flexAccounts`) and used by both; so the alias-pattern issue, when it lands, changes the map for both. The daughter's alias maps when `flex.toml` lists it; before that her statement is counted as unmapped and the page says "account not configured by the alias rule". An account number never reaches the page, a log line, an error text or a query id.
6. **Who writes (second opinion).** The upload route is the first path by which `ot serve` holds the option-ledger writer: the role `ot_w_optionledger` (INSERT and SELECT only, no UPDATE or DELETE), opened per post from the env file and closed after it, never kept open. The post route exists where the two settings posts exist: `rd.edit` is set, which `newOwnerEdit` does only with `--owner-edit`, a loopback address, `OT_FORM_KEY` and `OT_PG_DSN_SETTINGS` (`ownerEditSecrets` knows nothing of the ledger line; `env.go` and `settings.go` are not changed). The ledger line is checked by the new route's own code: the GET builder shows `form` null with one gap line when `OT_PG_DSN_OPTION_LEDGER` is unset or `flex.toml` does not load, and the post answers the same refusal without opening a store. The GET reads the recent records with the read-only pages line `OT_PG_DSN_PAGES` (role `ot_ro_pages`), not with the writer, through `deps.openOptionLedgerRO` (the opener `site.go:286-287` already uses for the pages that read the ledger; it is `openOptionLedgerStore` in `wire.go:262`, a different field so a test can fake the read and the write apart). `GET /flex-import` is reached by a registered page: `flex_import_site.go` calls `registerPage(pageFamily{route: siteFlexImportRoute, ...})` in `init()` with the route `flex-import`, as `underlyings_site.go:24` does; `site.go` is edited only for the POST route. No new `.env` line is needed on the owner's machine, which has all of these lines. No new library: `mime/multipart`, `compress/gzip` and `encoding/xml` are the standard library.
7. **Guard for an upload.** `settingsapi` gains a second interface `UploadChecker` with `CheckUpload(r FormRequest, maxBody int64, now time.Time) error`: the checks of `Check` (remote, Host, Origin, token, expiry) with the content type `multipart/form-data` and the cap given instead of 64 KiB. `settingsform` implements it on the same value; `cmd/ot` reaches it by a type assertion on `rd.edit.form`, so no existing fake of `SettingsForm` changes. The token is the one of the page (`Token(now)`), which is also a valid settings token (Adversarial, token point).
8. **The read of past imports, in a file of its own.** `optionledger.ImportLog` is declared in a new `internal/store/optionledger/api.go`, declarations only: `RecentFetches(ctx context.Context, login string, limit int) ([]store.FlexFetchRecord, error)`, the records of `login` whose `query_id` starts with `file:`, newest first by `finished_at` and then `fetch_id` (both descending), from `rd.flex_fetch_r1`. The filter on the query form keeps a login of flex.toml that is itself named `import` (`loginNameRE`, `internal/sources/flex/config.go:18` allows it) out of the list: its daily records have digit query ids, and r2 gives `file:` ids to the import only. A separate `api.go` is right here because the natural place, `internal/store/api.go`, is at its 800-line ceiling and a line added there would need a ceiling entry no agent may write; and because the new read has one user, `cmd/ot`, which reaches it by a type assertion on the opened store, as for `UploadChecker`. `internal/store/optionledger` is an implementation package (`store.go`, `queries.go`), so `api.go` there is an interface file inside an implementation package, the first of its kind in the store row: `scripts/arch` reads the kind of a package from the tree and not from the entry cell (`docs/design/modules.md`, the paragraph on the entry cells), so the check is not broken. This pull request adds the path `internal/store/optionledger/api.go` to the entry cell of the store row of `docs/design/modules.md`; `docs/design/modules.md` is not among the owner-only paths the file lists, and the owner's merge of this pull request is his word for that edit. The type of the store implements it in a later entry (entry 4). No migration, grant or view changes (the view and both grants exist; the view keeps its name `rd.flex_fetch_r1`, Doubt 11).
9. **Limits.** All three are chosen by the designer, not measured on a real 365-day export (Doubt 6); each is enforced in one place and refuses with one fixed text, and the other files of the post go on.

| limit | value | why | enforced in | refusal |
|---|---|---|---|---|
| one file, after decompression | 50 MiB | the live fetch's own bound (`maxBody`), so the import accepts what the job accepts; the parser holds a file and an upper-case copy in memory | `flex.Parse` (entry 1), `LimitReader` of `maxBody+1` behind the gzip reader | the file is `failed`, reason `too_large`: "file too large: at most 50 MiB after decompression" |
| one post | 64 MiB | files are parsed one at a time, so memory is one file and its copy, not the post; 64 MiB is above one file and below eight | `cmd/ot` before the guard (declared length over the cap or unknown: 413) and `http.MaxBytesReader` while reading (413); `CheckUpload` refuses the same lengths | 413, no page, no record: "upload too large: at most 64 MiB" |
| files per post | 8 | eight years of 365-day files; more is a second post | `cmd/ot`, the ninth part is not read | one entry `(more files)` `failed`, reason `too_many_files`: "too many files: at most 8 per upload" |

10. **The page.** `page.flex_import.v1`: `title`, `sentence`, `scope_note`, `form` (null when the route is off; otherwise `post_path` `/owner-flex-import`, `expires`, `mac`, `max_files`, `max_file_text`), `gaps`, `files` and `recent`. Per file in `files`: `name` (the base name, at most 80 characters, shown only in the POST response), `status` (one of `stored`, `present`, `nothing_found`, `unconfigured`, `failed`), `reason` (the five codes of Decision 3 for `failed`, empty otherwise), `status_text`, `period_first`, `period_last`, `aliases` (alias, statements, rows_parsed, rows_new, rows_present, all integers) and `unmapped_statements`. The file status is the first that applies: `failed`; `stored` when any alias has rows_new above 0; `present` when any alias has rows_parsed above 0; `unconfigured` when `statements_unmapped` is above 0 and no alias has rows_parsed above 0; else `nothing_found` (the same rule as a record, Decision 3; the file status is `DeriveImportStatus` over the file's records). Per record in `recent`: `at_text`, `alias` (the last part of `query_id`, split into at most four parts at `:`; empty for `-`), `status` and `reason` by the derivation of Decision 3, `rows_parsed`, `rows_new`, `rows_present` and `unmapped_statements`. `scope_note` is one fixed line: "Only trades of level EXECUTION are read, from the same Flex query that option_ledger uses for trades (the TradeQueries entry of its login in flex.toml); cash, positions, NAV and the other sections of the file are not imported." Every sentence is built in Go; the view computes nothing. A GET shows the form, an empty `files` and the `recent` list; the POST answers with the page carrying the results (200, no redirect: the results are in `recent` after a reload).
11. **No CLI.** `ot flex import FILE...` would be a second front for the same calls; it costs a command file, a test and a second opener path. It is under `## Left out`.
12. **Dataset contract: r1 is bumped to r2 (route (a) of the advisor's review r3).** The records of the import are the only ones that do not fit r1, and the rule of `00-protocol.md` (cited above) makes the widening a bump in its own issue, first in the order (entry 0). `optionledger.flex_fetch` r2 changes three things and nothing else (columns, key, status enum, view and migration stay): `query_id` matches `^([0-9]+|file:[0-9a-f]{8}:[1-9][0-9]*:[^:\s]+)$` (digits for a window of the daily job, the file form for the import); the description of `login` adds that `import` names the web import; the description of `first_date` and `last_date` says that for an import record they are the period of the file, else the trade dates, else the day of the request, so both stay required and true. `LatestOkFetch` never takes an import record: the daily job asks for a login of flex.toml with a digit query id, and a `file:` id is never digits; the pg test of entry 4 stores an import record with status `ok` and shows that `LatestOkFetch` of that login with a digit id finds none. A second revision file beside r1 does not work: `contracts/gendoc` writes one page per dataset name (`main.go:136`), so r2 replaces r1 (`git mv`) and `generate.sh` and the generated `FlexFetch` follow. The other route, a separate table for import records, would leave r1 alone but costs a migration (which the owner holds), a grant and a view, a new dataset with its contract, fixtures and generated type, and a new write method, because `RecordFlexFetch` writes the record and the rows in one transaction and `store/api.go` has no line to spare; it is not simpler (`## Adversarial`).

## Interface

- Entry 0: dataset `optionledger.flex_fetch` r2 (replaces r1), the generated type `FlexFetch`.
- Entry 1: `sources.ParseFlexFunc` in `internal/sources/api.go`, declarations only; the implementation is named `flex.Parse`. `api_test.go` tests the declaration from both sides: a fake used by a caller, and a caller of the fake; the cases of the real `flex.Parse` are in `parse_entry_test.go`.
- Entry 2: `settingsapi.UploadChecker`, declarations only; `api_test.go` has a fake and a caller; that the real form value satisfies it is a compile-time assertion in `upload_test.go`.

## Doubts (least sure)

1. The date format of `fromDate` and `toDate` in the owner's own export [unverified]: the fixtures use `yyyy-MM-dd`; IBKR can also send `yyyyMMdd`. Both are read; any other makes the record's days the first and last trade date of its rows (or the day of the request), which loses only the exact period.
2. If the write of a failed record itself fails (the store is down), nothing remains to reload for that file; the POST response shows it and the page says so. Per-alias writes are not atomic across aliases: a file whose second alias fails keeps the first stored, shows `failed` for the file, and importing it again adds the alias that failed and counts the stored one as already present. Two posts at the same nanosecond with the same `request8` (32 random bits) would collide on `fetch_id`, and the second write fails with `store_error`. A post that read `FlexTradeRows` before another committed the same keys is not an error: `RecordFlexFetch` selects again inside its own transaction (`store.go:93`), an equal committed row is counted `Unchanged`, and the record reads as present (`rows_parsed` N, `rows_new` 0). `store_error` (`store.go:111-112`) happens only when two transactions are in flight on the same new key; the data is then present and nothing is lost. No test covers the two-post cases.
3. The upload token is also a valid settings token (Adversarial, round 1).
4. Entry 8 is the first route of `ot serve` that holds `ot_w_optionledger` and the first multipart body on the site: a second-opinion case. The modules.md edit is in this pull request, so the owner's merge of it is his word for that edit; `internal/store/optionledger/api.go` is an interface file inside an implementation package, which `scripts/arch` reads by the tree and so allows [checked in the text of `docs/design/modules.md`, not run].
5. A re-import appends a `flex_fetch` record per alias (Decision 4); "changes nothing" holds for trade rows only.
6. The limits (64 MiB per post, 8 files, 50 MiB each decompressed) are chosen, not measured on a real 365-day export.
7. An upload before the daily job's first run, or of part of the history, stores rows for an alias, which makes `rowsForAll` true in `planWindows` (`window.go:24`; `job.go:253-262`) and so can end the daily job's re-fetch of an alias that had no rows. With no stored `LatestOkFetch` the job still starts at `history_from`; the effect is only for an alias that had no rows after the first run. Accepted and named, not changed.
8. A trade the daily job stores between the import's read of `FlexTradeRows` and its `RecordFlexFetch` (seconds) is written by the store as a revision if its hash differs; the two cover different days for a pre-2025-12-01 export, so it is unlikely, and the record's `rows_revised` would show it (`rows_new` and `rows_revised` are the store's own counts); `rows_present` subtracts it and the record reads as `stored`.
9. The recent list keeps 50 records; a post of eight files with more than six aliases each, or two large posts, push older records out.
10. A mapped statement with no `EXECUTION` trade makes no alias group and is not counted in `Statements`; a file whose other statement is unmapped shows `unconfigured` though the first alias is configured. Accepted: the page counts what is stored per alias, and the unmapped count says why.
11. The view keeps the name `rd.flex_fetch_r1` while the dataset is r2: the columns are equal and the view is not renamed, because a rename is a migration the owner holds for a change of no behaviour. A reader who takes the view name for the contract revision reads r1; accepted.
12. `contracts/gendoc` names a page by dataset only, so r2 replaces r1 in the tree instead of sitting beside it; the only readers of the r1 file name on main are `generate.sh`, `schema_test.go` (through its dataset loader) and the schema itself (`git grep "flex_fetch.r1"` outside `docs/design` and `migrations`); the generator was not run [unverified].
