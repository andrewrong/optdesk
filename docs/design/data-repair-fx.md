# data repair, step 1: the stored USDJPY rate can be replaced by a forced run from the job console

Author: the optdesk designer (draft)
Owner approved: (pending)
Date: 2026-11-13
Revision: 2

Source: owner 2026-11-13 "overwrite by natural key and keep no old value", "storage plan v2 OK", and that he works on the web, so a repair is a page action (job console: a day plus Force). Storage plan v2 of the advisor (2026-11-13), P1, P4, P6, the cut order step 1 "FX upsert and Force on its console row" and the correction "the writers skip a key that exists (ON CONFLICT DO NOTHING)"; the advisor's definitions of repairable data (2026-11-13T06:32Z), section 3 (rules of a by-key write) and section 4 (the page action). The decisions of those two documents are not changed here.

Goal: `obs.fx_rate` becomes repairable. A run of `fx_refresh` for a past day, forced from the job console, fetches the IBKR midpoint bars that end on that day and stores each one by its natural key `(pair, rate_day)`: a value that differs replaces the stored one (no old value is kept), an equal value touches nothing, an empty answer never replaces anything. Nothing else of the storage plan is built here: bars, series, dividends, earnings and the range field of the console are later steps.

Existing design: `market-bars.md` (Decisions 4 and 8) made the table insert-only and `fx_refresh` its writer; `single-runner.md` made the scheduler the only process that runs a job and `ot run-once` and `ot backfill` enqueue console requests; `job-console.md` (Decisions 6 and 10) owns the table of console rows and which rows offer force. This design changes the first and uses the other two as they are.

## Decisions

1. Table (advisor P1, P6; definitions section 3). `obs.fx_rate` keeps its key `(pair, rate_day)` and gains `status` (`ok`, `no_value`, `void`; default `ok`), `updated_at` (timestamptz, set from the existing `received_at` for the rows already stored) and `written_by` (text, default empty), appended after `received_at` so that a positional INSERT of five values still works. `rate` becomes `numeric` and loses NOT NULL; the text pattern check goes and a check keeps it positive whenever `status` is not `no_value` (then `rate` is NULL). `source` stays `ibkr_midpoint` (a second FX source is step 9 of the plan). `received_at` stays the time of the first insert and is never updated.
2. The view `rd.fx_rate_r1` is dropped and created again over the new table with the same five columns and types (`rate` as text: `rate::text`, which keeps the scale a decimal text carried, so `153.4250` reads back as `153.4250`), and only rows with `status = 'ok'`. No reader, page or record changes: `barpg/read.go`, the pages and `contracts.FxRate` stay as they are.
3. Roles (definitions section 1, "a writer role has INSERT and UPDATE on its own by-key tables and nothing else"). `ot_w_bar` gets `UPDATE` on the columns `rate`, `source`, `status`, `updated_at` and `written_by` of `obs.fx_rate` only, and `SELECT` on the columns `pair`, `rate_day`, `rate`, `source` and `status`: PostgreSQL needs the right to read the arbiter columns of `ON CONFLICT (pair, rate_day)` and the columns the `DO UPDATE ... WHERE` reads. `received_at`, `updated_at` and `written_by` stay unreadable for it. It keeps its table-level INSERT of 0021 and gets no DELETE, no TRUNCATE, no UPDATE of the key or of `received_at`, no UPDATE on `obs.price_bar`; `ot_ro_pages` is unchanged. Nobody deletes by hand.
4. The write (P6, definitions rules 1 and 2). One statement per row inside one transaction: `INSERT ... ON CONFLICT (pair, rate_day) DO UPDATE SET rate, source, status = 'ok', updated_at, written_by WHERE (stored rate, source, status) IS DISTINCT FROM (new ones)`, `RETURNING pair`, which gives one row only when a row was inserted or replaced (`pair` is readable by the grants of Decision 3; no system column such as `xmax` is read, so no further grant is needed). Numeric equality decides: `153.425` and `153.4250` are equal and nothing is rewritten. A row stored `void` or `no_value` and then answered with a rate differs and is replaced. The writer returns two counts: written (rows the statement returned: inserted or replaced) and unchanged (rows given minus rows returned). An empty list makes no call. A key twice in one call is applied in order (the second is unchanged or written again), never an error.
5. Interface (additive, so no fake or implementer of `BarStore` breaks): `bar.FxRateUpserter` with `UpsertFxRates(ctx, rows, writtenBy) (FxWriteCount, error)` and `bar.FxWriteCount`. `FxRateWriter`, `BarStore`, `NewFxRefreshFunc` and `InsertFxRates` are not changed: the fakes of `bar/api_test.go`, `fxrefresh/run_test.go` and `cmd/ot/wire_computefigures_test.go:89` keep compiling. `cmd/ot/wire.go` `noBarStore` (the writer `fxrefresh.New` gets when `OT_PG_DSN_BAR` is empty) is not edited and does not get the method: its `InsertFxRates` already returns `errors.New(reasonNoBarDSN)`, so a write without a bar store fails today and fails the same way after (Decision 6). The `barpg.Store` implements both. `InsertFxRates` stays as the insert-only writer; it is no longer called by `fx_refresh`, and removing it with the reader argument of `fxrefresh.New` is a later change of two interfaces (Left out).
6. The job (definitions rules 1 and 2, section 4). `fxrefresh.New` takes the writer as before and does not fail. At the start of `Run`, the job asserts the writer to `bar.FxRateUpserter`; a writer without the method (`noBarStore`, no bar DSN) makes `Run` return a Retryable error whose text names the missing bar store, the class and outcome of today, when `noBarStore.InsertFxRates` already returns `reasonNoBarDSN` and `asTyped(err, Retryable)` wraps it; it is never a silent insert-only fallback. No entry edits `cmd/ot/wire.go`, so there is no sibling build dependency. `Run(day)` asks the bars with `End` = the given day when that day is before today's UTC date and empty otherwise (so the scheduled run of today is unchanged), keeps only bars whose day is not after the given day, and upserts them in one call with `writtenBy = "fx_refresh:" + day`. It no longer reads the stored days. An empty answer writes nothing and the run returns zero returned rows as today; a bar that is not a positive decimal is Permanent as today; a store error is Retryable unless typed. The window is `duration_days` (5) ending at the day: a forced run of day D repairs the rate days D-4 to D that the source has. A longer range is the console range field of step 2 of the plan (Left out). `RestartSensitive` stays false: a re-run is idempotent.
7. The page action (definitions section 4; owner: a repair is a page action). The console row of `fx_refresh` becomes an any-day row with force: `{ID: "fx_refresh", Kind: kindAnyDay, Force: true}`. The page then offers a day (not after today) and the Force box as it does for `calendar_refresh`; the post handler, the queue, `BackfillWith` and the plan-only step of single-runner are used as they are, and no second runner is added. Without Force a request for a day whose key is present is `already_present` and does nothing (`backfill_force.go:181`); with Force the key is run again and Decision 4 decides what changes. `ot backfill --job fx_refresh --day D --force` (single-runner Decision 2) reaches the same path: it enqueues.
8. Not-forced runs. A scheduled run happens only for a day whose key is missing (`backfill_force.go:181`); it upserts the whole window of its day, so on that run a stored day of the window whose value differs is replaced (rule 1 of the definitions). A scheduled run repairs a missing key only and does not repair a present one by itself: Force from the console (or `ot backfill --force`) is the way to run a key that is present and overwrites. Today's unfinished bar: the run of day T stores the bar still in progress; the run of day T+1 replaces it with the final value.
9. Deploy (the migration holds the auto-deploy). Entry 2 carries a migration; code merges auto-deploy, but a migration holds. The window runs, after the merge of entry 2: rebuild `ot`, `ot setup pg`, migrate, `ot setup pg` again (the owner's rule of 2026-11-09). Entries 3 and 4 are merged only after the migration has run (entry 4 is a deploy-meaning order, not a build order). If entry 3 or 4 lands before the migration, `UpsertFxRates` fails Retryable (the column `status` does not exist, not a constraint class) and no data is touched; the run is retried. Between the migration and entry 3 the old binary still runs `insertFxRateSQL` on the migrated table; a pg test of entry 2 shows it still works. The migration rewrites a small table (one pair a day); the Down part restores the text column and the INSERT-only grant, and refuses (raises an exception, changing nothing) when any row has a status other than `ok` or a rate whose text fails the old pattern.
10. No old value is kept (owner 2026-11-13). The row keeps `source`, `updated_at` and `written_by` (job and day); a wrong forced overwrite is repaired only by another run from a source that still has the right value. No `void` is written by any code here: marking a day the source no longer has needs the range of a forced pull and comes with the console range field (Left out).

## Interface

One interface change, entry 1, in `internal/store/bar/api.go` (additive):

    // FxWriteCount is what one UpsertFxRates call did to the rows it was given: Written rows were inserted or
    // replaced, Unchanged rows were equal to the stored one.
    type FxWriteCount struct {
        Written, Unchanged int
    }

    // FxRateUpserter writes daily FX rates by the key (pair, RateDay): a row that differs replaces the stored
    // one, an equal row changes nothing, no old value is kept. writtenBy names the run (job and day). It is an
    // optional method of the value OpenBarFunc returns; the job asserts it at Run.
    type FxRateUpserter interface {
        UpsertFxRates(ctx context.Context, rows []contracts.FxRate, writtenBy string) (FxWriteCount, error)
    }

`FxRateWriter`, `FxRateReader`, `BarStore` and `contracts.FxRate` are unchanged. The record keeps `Rate` as decimal text, `ReceivedAt` becomes `updated_at` of a replaced row, and the first insert sets both.

## Doubts

1. The grants (Decision 3) follow the PostgreSQL rules: the arbiter columns of `ON CONFLICT` and the columns of `DO UPDATE ... WHERE` need SELECT, and `RETURNING pair` needs only `pair`. No database was available to run it here; the pg tests of entry 2 are the check, and they run only in GitHub CI.
2. Settled by a read-only probe on the main gateway (USDJPY CASH, `MIDPOINT`, 1 day, 5 days): with `End` empty the window ends now (5 bars, last 2026-11-13); with a past `End` of 2026-11-06 it returned 5 bars, 2026-11-02 to 2026-11-06, and with 2025-06-13 it returned 5 bars, 2025-06-09 to 2025-06-13. So the service honours `End` for midpoint bars and the last bar is the end day. The probe used the US/Eastern form `YYYYMMDD 23:59:59 US/Eastern`; `pyside/src/optdesk/ibkr/history.py` sends the UTC form `YYYYMMDD-23:59:59` for `end_day`; that is the form `bars deepen` already sends successfully for TRADES bars, but it was not probed for MIDPOINT, so this stays a doubt: a forced past day that returns the wrong window is the sign.
3. The migration number 0039 is the next free one on origin/main b5d4421b; another design that lands first moves it, and the Files of entry 2 and the test that applies it follow.
4. Range: the owner asked for "a day or a range". This design gives a day, which repairs the window of five rate days ending there, and leaves the range field to step 2 so that it is built once for every by-key row. If he wants a longer window at once, `duration_days` in `job.toml` can be raised (bounded 730 by the service) without a migration; not done here because a larger window on every scheduled run also replaces more of the stored history each day.
5. A past-day run replaces a value with what IBKR answers now. IBKR midpoint bars of an old day may differ from the first answer by a rounding or by a restated close; the owner accepted that no old value is kept. A repair that reads a worse value than the stored one cannot be undone from the database.
6. The writing run is `written_by` = job and day, not a run id (Left out): two runs of the same day are not told apart, only the later one is kept.

2. Biggest risk, the column grants: adopted. `pair` and `rate_day` are granted for SELECT, the hedge is gone (Decision 3, Doubt 1); the `SELECT 1` denial becomes `SELECT received_at` (entry 2, item 5); `rate_ck` is dropped before the type change (entry 2, item 1); the old insert SQL gets a pg test for the deploy window (entry 2, item 5); `RETURNING (xmax = 0)` is dropped for `RETURNING pair`, with two counts (Decision 4).
