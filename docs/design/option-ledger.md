## What main holds today

- Nothing: no ledger, event, lot, cost-basis or P&L code, dataset or table, and no Flex client. The only "ledger" names are the operations ledger of the runner (`store.OpsLedger`, `SchedulerLedger`), which this design neither touches nor reuses; every name here carries `Option`.
- `sources` holds the FRED client behind `sources.Source` (the key is passed in, the package reads no environment). `store` holds one role and one schema per data class, `compute` holds pure rule packages behind interfaces (`internal/compute/ease`, `alertrules`), `jobs` holds one package per job with a `job.toml`. `obs.option_eod` (rows of option bid and ask per contract and day) is landed; the held-contract capture is 612 issue 9.
- option-trader already fetches IBKR Flex (ADR 0017) and holds the trade rows of both accounts since 2025-12-01 in its own DuckDB file (`flex_trade_row`, `flex_fetch`). The owner wants that fetch moved over, not built new, and that history copied: Decisions 1 to 7. Nothing in this repository reads it until issue 10.

## Decisions

1. Truth source: IBKR Flex (owner answer 1), moved over from option-trader (ADR 0017). A port into Go of its fetch and parser, as `internal/sources/flex` behind `sources.FlexSource`, module sources: Flex is plain HTTPS to a fixed host, the same kind of outside client as the FRED source (`internal/sources/fred`); `pyside/` hosts only the code that talks to the IB gateway socket, which Flex does not use, so it stays out of Python. Opens, closes, expiry (note `Ep`), assignment (`A`) and exercise (`Ex`) are all explicit `<Trade>` rows. Nothing is detected from position captures or the API execution list, and nothing of `account.*` (561) is read: this design has no dependency on 561 or 606.
2. Stored rows, computed positions (adversarial point 3). Only the Flex rows are stored, append-only, as option-trader stores them (Decision 5 and 6). Positions, cycles and P&L are not stored: the pure rule `internal/compute/optionledger` behind `compute.OptionLedger` replays the trade rows of one alias, with the marks and the session days, at read time, in `ot ledger` and later in the page builders. The replay is deterministic: the same rows give the same figures. A few hundred rows per account make it cheap.
3. Private login file, ported from option-trader (`flex/config.py`). `$OT_HOME/flex.toml`: `$OT_HOME` is optdesk's private home, already read for `.env`, and outside the repository by the same rule; option-trader's `~/.config` path is not reused because optdesk finds its private files through `$OT_HOME`. Guards ported unchanged: the file must be outside any Git work tree, must have no group or other permission bit, and a bad or unsafe file is refused with an error that names the entry and the field and never a value. Content: `[[login]]` with `name` (`[a-z][a-z0-9_-]{0,31}`, unique), `token_env` (the NAME of the environment variable that holds the token) and `trade_queries` (a non-empty list of query ids, digits, unique); and `[[account]]` with `alias` (the label `a` or `b`) and `account_env` (the NAME of the environment variable that holds that account's number), the allow-list of Decision 5. Tokens and account numbers live only in the environment (the process environment or `$OT_HOME/.env` through the one reader of `internal/store/setup`) under the names the file gives; they are never logged, stored, put in an error, a fixture or a row. A login whose token variable is empty fails alone as `not_configured` and the other logins still run. Main (owner decision 2026-11-09: "only my main IBKR account must work; the second account may be unavailable; one account failing is fine as long as the main one works"): the login that serves main carries `required = true` (boolean, default false) in its `[[login]]`; `flex.toml` is the only source this design reads for it; it is not read from the gateways file and nothing here depends on `account-data.md`, so the owner marks the login of the main account in both files by hand (the login covers accounts, not one alias, so no check ties the two). The loader refuses a file with no required login, or with more than one. A failed, missing or `not_configured` non-required login ends the job `ok` with one `degraded` log record per run (login and status only; no `job_event` field or contract exists on main, and a fresh process keeps no state, so there is no deduplication), never `failed`, never a gap row, never a notification; only a required login that fails (or is missing) fails the job result. No `IBKR_FLEX_*` key exists. One query per login covers the accounts of that login; how many logins and queries the owner makes is the owner's choice, and the statement is stored under the alias its account maps to. The owner creates the token and the queries in the IBKR portal: the query asks for the section Trades at level of detail Execution, all asset categories, XML. The only new `.env` line is `OT_PG_DSN_OPTION_LEDGER`.
4. The fetch, ported from `client.py` and `refresh.py` with the same limits. Two requests per report (`SendRequest`, then `GetStatement` by reference code), version 3, `fd` and `td` from the window. The host `https://ndcdyn.interactivebrokers.com` and both paths are constants of `internal/sources/flex`; an address inside an answer is never used, redirects are not followed, a body over 50 MB is refused, the XML is parsed with no document type or entity declaration and no UTF-16 or UTF-32 body. Any two requests of the process to this service are at least 7 seconds apart (one shared pacer for every login), `GetStatement` is repeated at most 10 times and only while the service answers error 1019, any other error is not repeated: no retry storm. The job runs once per session day under the runner key; a failed window of a required login is a failed result, of another login a `degraded` record (Decision 3); either way it stops that query for the run and is not retried that day. Window rule as in ADR 0017: the last day is the day before the job's time in New York; the first day is `history_from` (default 2025-12-01, a key of `job.toml`) for a query without a stored `ok` fetch or when an allow-listed account has no stored row (the rule of option-trader issue 284, one larger report per day is accepted), else 30 days before the last day of the latest `ok` fetch and never before `history_from`, so late corrections by IBKR arrive by themselves; the span is cut into windows of at most 365 days, oldest first, one fetch each. The wait between requests is a function of the config, so tests never sleep and no test reaches IBKR; tests use XML fixtures only. The token is in the request URL and nowhere else.
5. Storage, ported from `store.py`, in the schema `optionledger`. Only `<Trade>` rows of level `EXECUTION` are stored, each with all its attributes as sent, as text (a JSON object in one text column), keyed by `(alias, level_of_detail, transaction_id, revision)`. A new key is revision 1; a row whose `attributes_sha256` equals the latest stored revision is not written again; a changed row becomes the next revision. The attributes `accountId` and `acctAlias` are removed before a row is stored or hashed. The alias allow-list: a statement whose account is not mapped by an `[[account]]` is not stored, it is counted in the fetch record, and its number is not logged. One fetch record per request pair (`login`, `query_id`, first and last day, start and finish times, status, error kind and code, `raw_sha256` of the report, parser version, counts of statements, unmapped statements, rows parsed, new, revised and unchanged); a report's fetch record and rows are written in one transaction. A report with a document type, another root, or a `<Trade>` without `transactionID` or `levelOfDetail` or of another account than its statement is refused as a whole. The raw XML is not kept (Left out). Each stored row also carries `source`: `flex` for a fetch, `ot_import` for Decision 7. Nothing is updated, deleted or pruned.
6. The kind of a row is told by the rule, not by the store, from its attributes: an option (`assetCategory` OPT) with `openCloseIndicator` `O` is `open`; `C` with notes holding `Ep` is `expire`, `A` is `assign`, `Ex` is `exercise`, otherwise `close`; stock (STK) is `stock_buy` or `stock_sell` by the sign of `quantity`. A cancel or correction row (`transactionType` or notes that mark it) is not entered in a figure: the position is listed as `review` and counted apart, never a guess. Dedupe and the source tags (answer 3): the identity of a Flex transaction is `(alias, level_of_detail, transaction_id)`; the reader returns the highest revision of it. The import (Decision 7) inserts a row only when its key `(alias, level_of_detail, transaction_id, revision)` is absent and no stored row of the transaction has the same `attributes_sha256`; a key that exists with another hash is a `conflict`, counted and not stored. So the import and the daily fetch never double count the same transaction, and a later fetch that finds the imported latest revision unchanged writes nothing, and a Flex correction is the next revision.
7. The import of history (owner answer 3, issues 10 and 11). option-trader's store is a DuckDB file, not a server, so there is no DSN. A one-off exporter `tools/ot-flex-export/` (its own uv project with a committed `uv.lock`, not run in CI, imported by nothing at run time, as AGENTS.md allows for a dev-only tool; the mainstream, MIT `duckdb` package) opens the file the owner names, read-only, and writes every revision of `flex_trade_row` to a JSON Lines file: `alias`, `level_of_detail`, `transaction_id`, `revision`, `attributes` (the text as stored), `attributes_sha256`, `recorded_at`. The owner points it at a copy of the file, not at the live one. Then `ot ledger-import FILE [--map from=to ...]` maps option-trader's aliases to the labels here (default: the same label; an unmapped alias refuses the whole file before any write), stores the rows with source `ot_import` under the rule of Decision 6 and prints counts only. `flex_section_row` (nav, cash, open position) is not copied: the ledger reads trades only (Left out). No test touches option-trader's database or service data: the exporter's test builds a tiny DuckDB in a temporary directory from the same table definitions, with invented rows; the import's tests read JSON Lines fixtures.
8. Matching and positions. Per alias and contract (`conid`, else `symbol:expiry:strike:put_call`), a closing event (`close`, `expire`, `assign`, `exercise`) matches opens first in, first out; a close with no open before it (history before the first stored row) is `unresolved`, listed apart, never a negative lot and never in a figure. Long and short are one mechanism (the sign of the quantity). A position is an open lot or the part a close left; a lot closed in two steps is two rows. Spreads are not grouped: each leg is its own position (Left out). An assignment before the expiry date is marked `early`. An `assign` or `exercise` event closes only the option position; the shares come only from the stock row Flex sends for the delivery, so nothing is counted twice, and a test pins that.
9. Premium income, realized and unrealized (answer 2). Per position, in the currency of the contract, before tax: `premium_income` is the cash of the opens plus the cash of the closes (`proceeds`, a buy-back is negative), as Flex gives it, `commissions` the sum of `ibCommission` of every row of the position, `realized_pnl = premium_income - commissions` once the position is closed, expired or assigned (an assigned position has realized option P&L like an expired one; the premium is income of the position and is never moved into a share basis). Open position: `unrealized_pnl = premium_income - commissions - mark x quantity x multiplier` for a short (the mirror for a long), where `mark` is the mid of the bid and ask of the newest `obs.option_eod` row of the contract and `mark_day` is stored with it. No row, or a row older than 5 session days, gives an empty `unrealized_pnl` and the mark `no_mark`; nothing is estimated. Held contracts are captured by 612 issue 9 for short calls only. Capturing every held option (short puts, long options) and the underlying of a held share is a follow-up of 612 (Left out); until it lands a short put, a long option and a share price show `no_mark`.
10. Wheel cycle and stock cost (answer 2). A cycle starts when shares of an alias and underlying appear (a `stock_buy`, an assignment shows as one) and ends when the shares are flat. `cycle_id` is `<alias>:<underlying>:<transaction_id of the first stock event>`. Shares are first in, first out. `cost_basis_per_share` is the price of the buy row, the strike for an assignment; the basis total is that price x shares; commissions of stock rows are summed apart in `stock_commissions` and are not in the basis. No premium is ever subtracted from a basis. `premium_income` of a cycle is the sum of the `premium_income` of the positions of the name that belong to it: the position whose assignment gave the shares, and every option position on the name opened while the shares were held. Premiums outside any cycle (a put that expired worthless, a put closed) are in their positions and in `premium_outside_cycles` of the alias and name. A shares sale or a call assignment sells at its row price; `stock_realized_pnl = proceeds of the sale - basis of the shares sold - the commissions of the sale`. `unrealized_stock_pnl = (stock_mark - cost_basis_per_share) x shares` with the stock mark the underlying price of the newest `obs.option_eod` row of the name (mark rule of Decision 9). The cycle shows `stock_realized_pnl`, `premium_income` and the commissions as separate numbers; no total hides them.
11. Numbers. Money and quantities are `math/big.Rat` inside the rule (exact sums, no decimal library in `go.mod`, the precedent of 612 Decision 1), decimal text at every boundary, rounded half-even to 4 places in printed figures. No float in the rule or the dataset. Every figure carries its currency; no function adds two currencies and no FX conversion is built, so a total is per alias and currency.
12. Ids that survive a later history import (adversarial point 4). `position_id` is `<alias>:<transaction_id of the opening event>:<n>`, `n` the part of a lot closed in steps (1 for a whole lot). `cycle_id` is `<alias>:<underlying>:<transaction_id of the first stock event>`. Both come from Flex's own transaction ids, not from a day, a capture, an order of replay or the source tag, so an import after a first Flex fetch gives the same ids for the same transactions. An import that finds an earlier stock event of the same shares changes that cycle's id, which is named under Left out.
13. Store. Schema `optionledger`, two insert-only tables (`flex_fetch`, `flex_trade_row`), a role of its own `ot_w_optionledger` with INSERT and SELECT only (no UPDATE, no DELETE), DSN line `OT_PG_DSN_OPTION_LEDGER`, `store.DSNEnvOptionLedger`; `ot_ro_pages` reads views only: `rd.flex_trade_row_r1` (and `rd.flex_fetch_r1` if a page needs it) get SELECT, the base tables get none for it, as for the account data. A duplicate key cannot be inserted by construction (the highest revision is selected and the next one written in the same transaction), and `ON CONFLICT DO NOTHING` is a second guard, so no insert fails halfway. Every row is account-derived and lives under that rule, not with market data. Alias is the only identity; no account number is stored.
14. Delivery rule, binding: nothing here reaches notify. A job result carries a job id, a status and an alias only (a login name in the `degraded` log record is a label of the same kind); no position, premium or P&L. `internal/notify` imports none of the new sub-packages (`scripts/arch` enforces that and only that: `store.OptionLedgerReader`, `store.OptionLedgerWriter` and `compute.OptionLedger` are declared in the root packages `internal/store` and `internal/compute`, which notify may import). Notify is kept clear of them by the grep of issue 12, acceptance 2, which finds no `OptionLedger` or `optionledger` text under `internal/notify`. The text formatter of `ot ledger` is in `cmd/ot`.
15. Order and parameters. In `run-once`: `option_eod`, then `option_ledger`; in the scheduler it is anchored at `session_close` plus 60 minutes (Flex statements are produced after the close). Keys of its `job.toml`: `history_from` (2025-12-01), `mark_max_age_sessions` (5). `rule_version` of the figures starts at 1 and is printed.
16. Reader and command. `store.OptionLedgerReader` returns the latest-revision trade rows of an alias; `ot ledger [--alias a] [--status S] [--cycles]` reads them, replays through `compute.OptionLedger` with the marks of `obs.option_eod` and the session days of the master calendar, and prints text. `option-tracking` does the same call; no figure is stored.
