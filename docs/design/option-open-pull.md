# Option open pull: the contracts are decided before the open, quoted live at 09:45 ET, and a button on the option pages pulls the newest quotes of the symbols on screen

Author: the optdesk designer (draft)
Owner approved: (pending)
Date: 2026-11-10
Revision: 1

Source: owner decision 2026-11-10 (dispatcher window): the owner sells options and trades at the US open, so option quotes must be fresh at the open, not only after the close. Wanted:
(1) decide the contract list in advance, then pull at the open (learned from option-trader); (2) on the option pages a refresh button that pulls the newest quotes on click, not streaming.
The after-close `option_eod` archive (history, IV rank) stays as it is. Owner addition the same day: a planned contract that does not exist is remembered with a validity period and not asked again until it ends.
Learned from option-trader (read, code and docs only): `scheduler/snapshot_jobs.py`, `snapshots/plan.py`, `params/plan_v4.toml`, `snapshots/listed_store.py`, `snapshots/listed_refresh.py`, `sources/ibkr/quote_port.py`, `reports/option_route.py`, ADR 0003 and 0004, issues #240 #241 #757 #775 #776 #793 #1811.
Read on origin/main at 62e68b0c: `AGENTS.md`, `docs/design/modules.md`, `docs/design/option-jobs.md`, `docs/design/option-page-builders.md`, `docs/design/scheduler.md`, `contracts/datasets/obs.option_eod.r1.json`, `contracts/datasets/obs.quote_snapshot.r1.json`, `contracts/proto/ibkr/v1/{marketdata,quote_types}.proto`, `pyside/src/optdesk/ibkr/{spec,ibgateway,gateways,pacing,server}.py`, `internal/jobs/optioneod/*`, `internal/jobs/optioncandidates/input.go`, `cmd/ot/serve.go`. Also read: the design `docs/design/option-page-names.md` (PR 1333, on main; its `Names` fields landed in #1347); this design does not edit its files and its remaining issues are ordered before this design's page issues 3, 9 and 10.

Goal: at 09:45 ET on a US session day the store holds a quote (bid, ask, size, model IV and Greeks, the data type and the quote time) of every contract the owner could sell or already holds, for the stocks of the watch list. On `/options` and `/options/stock/<symbol>` a button pulls the newest quotes of the contracts on screen, within 15 seconds, and the page shows the time and type of every quote it prints. The 16:15 `option_eod` job and its rows are not touched.

## What main holds today

- `option_eod` runs once, after the close (`job.toml`: anchor `session_close`, offset 0). Its quotes come from `QUOTE_KIND_OPTION_EOD` (ticks "100,101", release on bid, ask, close and the model values, 20 s, 5 s open-interest grace) over the pyside gateway, which sets one market-data type per connection and defaults it to 2, frozen (`gateways.py:20`, `ibgateway.py:216`, since #1143). That is right for the archive and wrong at the open.
- Plan today: `max_expiries` 3, band 0.10, two strikes below and two at-or-above (#1302), held calls through `NewWithHeldSymbols` (#1310); a watch-list variant has `min_dte` 21, `max_dte` 45, `max_strikes` 24. Contracts are resolved by `ResolveContract` (one con_id each, `Snapshot` demands a con_id) and cached in `master.instrument`.
- `option_eod` rows have a `capture_id` that is a random uuid, and `optioncandidates/input.go:157-163` takes "the newest capture of the day" per instrument by generation and then by comparing `CaptureID` strings. A second capture of the day in that table would make that choice random. This is why the open rows do not go into `option_eod` (Decision 7).
- `obs.quote_snapshot` has a `slot` and a `market_data_type` but no IV and no Greeks; it is no fit for a seller's read.
- `ot serve` is read-only: the role `OT_PG_DSN_PAGES`, no broker, one POST route (`--owner-edit`, loopback only, `/owner-settings`). The pages `/options` and `/options/stock/<key>` are built from `store.Candidate` rows (computed after the close) and `option_eod` rows by `internal/pages/option_boards`.
- The runner has no control socket in code (`docs/contracts/runner.md` only names one), so a page cannot ask the scheduler process to run anything.

## Decisions

### Plan

1. Four jobs, in one new package `internal/jobs/optionopen`: `option_open_resolve` (evening, `session_close` plus 60 minutes of the previous trading day by the calendar, a Friday for a Monday, not the calendar day before), `option_open_resolve_gap` (the pre-open pass, manifest `job_gap.toml`, `session_open` minus 90 minutes, 08:00 ET, budget 30 minutes so that it ends before the plan: it calls `ListChains` of each stock first, so that trigger (c) of Decision 5 sees the morning chain, and resolves only the gap of the band, the new expiries and strikes listed overnight that the cache does not hold; option-trader #241), `option_open_plan` (08:45 ET, `session_open` minus 45 minutes) and `option_open` (09:45 ET, `session_open` plus 15 minutes). Resolving con_ids is slow in option-trader (about 5 s per expiry serialised, #776: 148 expiries overloaded the gateway; measured on the probe of 2026-11-10 at 0.16 s per contract, 37 percent not listed) and must not run at the open: the plan job at 08:45 uses stored con_ids only (Decision 3) and resolving is the evening job `option_open_resolve` plus the pre-open gap pass `option_open_resolve_gap`. Its output is a stored plan; the pull job reads it. No plan rows for the day: the pull job ends `NoValue` "no plan" and the page shows a gap; it never plans on its own at 09:45.
2. Which stocks: the watch list and the held underlyings, the same two sources `optioneod` reads (the plan job takes the ports of `held.go` and `watch.go` through the store readers they use; it imports no other jobs package).
3. Which contracts of a stock, a pure function `PlanFunc` in the jobs package `internal/jobs/optionopen` (file `planfunc.go`: no I/O, no clock, the same split as option-trader `plan.py`; it is in the jobs package, not in a compute sub-package, because `modules.md` lets a jobs package import only the roots, declarations-only packages and test kits of other rows, and no compute interface for it is worth an interface change; it sits behind the function type so a library can replace it):
   - expiries: every expiry of 20 to 45 calendar days to expiry for every name (owner decision 2026-11-10, 15:33Z: no cap of three expiries and no first round for the two expiries nearest 30 days; weeklies give 3 to 4 expiries); `(|DTE - 30|, DTE)` is only the tie-break that decides which expiry is cut first when a ceiling bites.
   - strikes, per expiry and in this order (option-trader order): `around_spot` (the put and the call at the strike at or below the spot and the one above it); `puts` from the strike `spot * exp(-k * sigma * sqrt(T))` (`put_k`, k = 1.4) up to around the spot; `calls` (held names only) from around the spot up to `spot * exp(+k * sigma * sqrt(T))` (`call_k`, k = 1.4); sigma is the prior close's implied vol of the underlying, from `option_eod` / the IV history (the reader `optioncandidates` uses); if the prior close has none, the last known value; if there is none at all, 30 percent. Owner decision 2026-11-10, 15:33Z: the owner's intent is a put delta of 0.08 and more; k = 1.4 is that delta 0.08 written as a band (about |delta| 0.08 at 30 days), and k = 1.75 below is the delta 0.04. This is a band, not a price: the plan computes no option value, no IV and no Greek of its own (plan v2.5 section 1 and ADR 0001: IV and Greeks only from the IBKR model values), and the real delta that comes with the pull from IBKR is only a page filter. The plan row records which of the three sigma sources it used (`sigma_source`: `prior_close`, `last_known`, `default`). Every listed strike inside the band, with two guards (`PlanParams`): at least 6 strikes per expiry on the put side when the band is narrow (the nearest listed strikes below the spot are added), and at most 25 strikes per expiry on names with a 1 dollar strike grid (for SPY, QQQ and IWM, beyond 3 percent out of the money only the 5 dollar strikes). When a cap binds, the far strikes drop first: on a name with a 0.50 grid (more strikes inside the band than on a 1 dollar grid) the cap of 60 per stock drops the puts farthest from the spot, then the far held calls, across expiries, by distance from the spot; `around_spot` is never dropped. The minimum of 6 puts per expiry wins over the per-expiry cap of 25 and over the cap of 60 per stock; only the class ceilings of the run can defer it, and then last. The real delta is a page filter (the pages show puts of delta -0.05 to -0.35), never a pull rule; the band above is the pull rule. The strike band and the calls scope are one named parameter set in the plan params, `PlanParams` (`job_plan.toml` table `[params]`), an **owner decision 2026-11-10** ("follow option-trader", final): default `put_k = 1.4` for all names, `call_k = 1.4`, `store_k = 1.75`, `store_drop = 0.25` and `calls = "held"` (calls only for names with a held position); the alternative `calls = "all"` is a value, not a code change (not chosen). Tiers are not used (option-trader's production sets one tier for all names), so no per-name class decides. Option-trader's per-name flags: `deep_puts` (put bound lowered by 0.15 * spot) is for the names of the owner's spread list, a list that optdesk does not hold, so the flag exists in the plan function's input and is false for every name until a list exists (`## Left out`); `no_option_names` (names with no options: underlying only) is a `no_option` list in the JP `job_plan_jp.toml` (Decision 21). Spot and the open: at 08:45 the spot is the last stored close; the evening resolve resolves a band wide enough for a gap (the resolved contracts are `master.instrument` rows and, with their expiry, strike, right and trading class, `master.option_contract` rows written by the resolve job, read back by `ListOptions` of `## Interface` (Store); nothing else stores the band, `PlanFunc` recomputes it from the stored close): for puts down to `spot * exp(-1.75 * sigma * sqrt(T))` (`store_k`, about |delta| 0.04) or to `spot * (1 - 0.25)` (`store_drop`), whichever is nearer the spot, and for held calls up to `spot * exp(+1.75 * sigma * sqrt(T))` or `spot * 1.25`, whichever is nearer, computed on the stored close; the plan lists the resolved options of the stock through `openquote.OptionContractStore` and keeps the candidates inside that band, and the pull core takes the first underlying snapshot of the day as the spot for choosing strikes: it runs the same `PlanFunc` (pure, so core.go may call it) over the stored candidates with the open spot, recomputes the band at the open spot (the same k and sigma), quotes the puts inside it and the held calls up to `call_k` and writes the others `deferred` with `outside_band` set (Decision 12). A name with no resolved chain gets `NoValue` ("no resolved chain") in the plan job and no guess is made.
   - every held option contract (put or call, any expiry) is always included, outside every ceiling. This is an optdesk addition: option-trader does not take held positions as an input (it quotes a held contract only if the name is on its watch list).
   - ceilings per run, option-trader's shape with optdesk numbers for about 45 US names: `around_spot` 350, `puts` 1400, `calls` 1200 (option-trader runs 1000 / 3000 / 3000 for hundreds of names), at most 60 per stock; counted without held contracts. Overflow is not dropped silently: the plan stores it with the reason `deferred` and the pull writes final status `deferred` (Decision 8); the underlying itself is never deferred (its price is always read). Order (owner decision 2026-11-10, 15:33Z): there are no rounds and the number of days to expiry does not split the order; the key is the class (`around_spot`, then `puts`, then `calls`) and inside a class the names take turns, each name's next strike nearest the spot first (the expiries of a name interleave by distance from the spot), and the starting name rotates by the day number, so a budget cut drops far strikes and far calls, not whole names.
   - only listed contracts: the chain comes from `ListChains` (reqSecDefOptParams); because its strikes are a union over expiries (option-trader #793: 8,170 contracts not listed), the contract is resolved before the slot: the 08:45 plan job builds the plan from stored con_ids only (`master.option_contract`, which holds the instrument id of each resolved contract) and never resolves; a candidate with no stored con_id is not in the plan and is counted as `unresolved` in the run's gap report. The resolve is a job of its own, `option_open_resolve` (manifest `job_resolve.toml`, `anchor = "session_close"`, `offset = "60m"`, key one stock, scheduled, so it runs while `ot scheduler` runs and needs no `ot run-once`; the nightly `option_eod` fills `master.instrument` only, and the resolve job finds its contracts there and puts them into `master.option_contract`; the gap pass is the same code with the manifest `job_gap.toml` and a gap-only filter) which resolves the candidates of the plan function and applies Decision 5 (never at the open: option-trader advice 2026-11-10).
4. Plan rows go to a new dataset `plan.option_open_item` (Decision 7), written by the plan job before any pull request of the pull job. One row per planned contract: day, plan id, underlying id, instrument id, class (`around_spot`, `puts`, `calls`, `held`: the same four values as the ceilings and the order of Decision 3), a `deferred` flag (a contract over a ceiling keeps its class and is flagged), rank, planned spot, sigma and `sigma_source` (Decision 3). The plan job has a budget of 40 minutes (the lease of a run is 10 minutes and nothing renews it, so the key is one stock, not the whole plan), ends before the slot, and a stock not finished by then is reported as a gap of the job, not silently thinner.

### Listed check, remembered with a validity period (owner addition 2026-11-10)

5. What is stored, where, how long:
   - Table `master.option_not_listed` (store module, migration; Postgres next to `master.instrument`, not a file of the job). Columns: underlying id, expiry, strike, right, trading class, `checked_at`, `retry_at`, error code, error text. One row per contract that IBKR answered "none" for.
   - Validity: `retry_at = checked_at + 7 days`, plus a jitter drawn per row, uniform in minus 2 to plus 2 days, so the re-asks spread over days. These are option-trader's values after #793 (first 1 day, 8,000 contracts re-asked daily cost 23 minutes of gateway in a 30-minute job; owner decision there 2026-10-17). They are values of `job_resolve.toml`. The resolve job does not ask a contract before its `retry_at`; the plan job asks nothing (Decision 3).
   - The key of a mark is the full contract identity (underlying, currency, exchange, trading class, multiplier, expiry, strike text, right), as option-trader's `listed_absent`; a listed contract has no TTL (its con_id is fixed; `master.instrument` already holds it).
   - Early end of a mark, four triggers as option-trader (advisor 2026-11-10): (a) `retry_at` has passed; (b) the same strike is seen listed at another expiry; (c) a later `ListChains` shows the strike now listed (the chain gained it after `checked_at`); (d) the stored spot of the stock moved 5 percent or more since `checked_at` (strikes may be listed near the new price): the marks of that stock are asked again. Adopted as they are: optdesk's shape (a daily plan of a few hundred contracts, one store) gives no reason to differ, and a seven-day mark with a one-day mark would only cost gateway time (#793: 23 of 30 minutes).
   - The refresh button and the pull never ask a not-listed contract and never write a mark: they only skip a contract that has a mark (option-trader's on-demand rule trusts a mark 1 day; here the plan already filtered).
6. Which answers count as "not listed" and which never do. A mark is written only for a final answer of IBKR about the contract itself: `ResolveContract` returns an empty list, or error 200 whose text is "no security definition" for one fully specified contract with exactly one request in flight; any other error 200 is `ambiguous`. The resolve asks the strikes of each expiry from its own chain entry, never the union over expiries (option-trader #793). Never marked, the contract is asked again at the next run: a timeout, a disconnect or session loss (10197, 1100 to 1102, "not connected"), a pacing or line error (101, 100, 162), a missing subscription (354, 10089 to 10091), a deadline or a stop of the run (two consecutive timeouts of the resolve job's connection stop its resolves for the run, option-trader #757, and the rest are reported unsent, not marked), an answer that arrived after the run stopped, an ambiguous answer (error 200 with several results or a result that differs from the request: option-trader counts it `ambiguous`, not `not_listed`), and any unknown error. A test pins this table (issue 6). Sending a contract to the pull that the plan marked listed and that answers 200 at 09:45 gives status `not_listed` on that row only; the next run of `option_open_resolve` turns it into a mark when the answer was a clean 200 of one request (it reads those rows; the resolve job is the only writer of the table, and the plan job writes no mark). Marks of contracts past their expiry are removed at the start of each resolve run, and each run logs one line with the counts `asked`, `found`, `not_listed`, `ambiguous` and `timeout`.

### Where rows go

7. A new dataset `obs.option_open` r1 (contracts, store migration), not `option_eod` with a slot column and not `quote_snapshot`. Reasons: the `option_eod` description says "frozen after the close" and the candidates job picks "the newest capture" by a random uuid (see above); the IV rank and the history read that table; adding a second capture per day changes both silently. `quote_snapshot` lacks IV and Greeks. The new table has the columns of `option_eod` that make sense at the open (instrument, underlying, generation, bid, ask, sizes, last, volume, underlying price and its time, the four IV columns, delta, gamma, theta, vega), without `open_interest` (stale intraday, the page joins the last `option_eod` value and prints its date), and adds: `slot` text (`0945`; the overlay of Decision 13 sets `refresh` on a row of the button, the only marker of a refresh row), `skew` bool and `outside_band` bool (written by the pull core, Decisions 8 and 12), `plan_id`, `market_data_type` (the type of the tick, Decision 9), `requested_at`, `sent_at`, `received_at`, `event_ts`, `connection_generation`, `status` and `error_code`. Primary key `(session_day, capture_id, slot, instrument_id)`; insert is `ON CONFLICT DO NOTHING`. Timescale hypertable on `session_day` like `option_eod`. `ot_ro_pages` reads through the view `rd.option_open_r1` (and `rd.option_open_item_r1` for the plan table), never the base table; the views and their grants are part of the migrations.
8. Final status per item, exactly one row per planned item, written at the end of the run (a crash writes nothing and the runner retries the key): 1 `ok` (bid, ask and model IV), 2 `partial` (bid and ask without the model IV, or any other part of them, kept), 3 `no_data` (nothing came), 4 `not_listed`, 5 `no_subscription`, 6 `deadline`, 7 `deferred` (over a ceiling or a line budget, or outside the band chosen at the open spot: not asked, `outside_band` set, Decisions 3 and 12), 8 `error`, 9 `disconnected`. Statuses 6, 7, 8 and 9 are retried by nothing the same morning: a later pull is the owner's button. Order of `ok` rows: grouped by stock, then expiry, so that the spot of the stock sampled at the start and at the end of a group bounds the time skew (option-trader: a slow group or a spot move is flagged incoherent): the row carries `underlying_price` and `underlying_event_ts` of the group's end; a spot that moved 1 percent within a group sets the `skew` column of the group's rows, which the page prints ("skew"). `outside_band` is set by the pull core on a stored candidate that the band at the open spot leaves out; that row is not asked and has status `deferred` (Decision 12). Run summary: at the end of each run the pull core logs and returns one line, items, `ok`, `partial` and the seconds from the first `requested_at` to the last `received_at` (derived from the rows, no table), so the first pull measures itself. A `partial` that ended at the timeout is retried once with the classes of Decision 10, a `no_data` is not retried.

### Market data type and the request shape

9. Live ticks (type 1) at the open, and each row records the type that came with its own tick; the pull asks for no type. Settled by a probe of 2026-11-10 at the US open (read-only, through the deployed pyside socket `run/ibkr-main.sock`, the gateway named `main`, with the existing `QUOTE_KIND_OPTION_EOD`; the connection type of a gateway is 2, frozen, unless its entry says otherwise): puts of SPY and AAPL, 21 to 45 days (the plan now takes 20 to 45), came back `OK` with `market_data_type` live (1) and bid, ask, last, volume, open interest, IV, the four Greeks and the underlying price, 2 to 3 puts per call in 2.0 to 2.7 s; some strikes near 0.95 times the spot did not resolve (the not-listed case of Decision 6). The existing `option_eod` job and every Go job dial `run/ibkr.sock`, the socket of the gateway the pyside file names `default` (`cmd/ot/runonce.go:95`, `docs/deploy/pyside.md`); that file is deployed outside the repo, so the repo cannot say whether `default` is `main`. Rule for wave 1: the pull job dials `ibkr.sock` like `option_eod`, and the window confirms once, before the first run, that `default` is `main` (the deployed gateways file, or the same probe on `ibkr.sock`); if the two differ, the wiring (issue 15) dials `ibkr-main.sock` through a profile value instead, and nothing else changes. So no second gateway, no second client id and no change of the connection type: type 2 returns live ticks while the market is open (and the last close after it, which is why the type is stored per row, as option-trader does after #1811). The row's `market_data_type` is the type of the tick (`_quote` in `ibgateway.py` reads `ticker.marketDataType`). Wave 1 sends the existing `OPTION_EOD` kind (ticks "100,101", 20 s timeout, the 5 s open-interest grace); the model IV and Greeks come from the default option computation ticks that IBKR sends with any option subscription, and the generic tick 106 is skipped on purpose (no second IV source), so an `ok` row needs the model IV present; no code of this design requests the frozen type 2 or any type: the type of a row is the one its tick carried. The kind `OPTION_OPEN` (15 s, no grace, issues 1, 8, 23, 12, 18 and 19) is a wave-2 refinement on the same default gateway.
10. Request shape. One streaming `reqMktData` per contract, never `snapshot=True` (error 414 with generic ticks, option-trader). Ticks "100,101" as `OPTION_EOD`, release on bid, ask and the model values; no open-interest grace at the open once `OPTION_OPEN` exists (wave 1 uses `OPTION_EOD` with its 20 s timeout and 5 s grace). Pull job: item timeout 15 s (20 s in wave 1), one retry on a timeout for `around_spot`, `puts` and `held` items and none for `calls` (`retry_classes = ["around_spot", "puts", "held"]` in `job_pull.toml`; a call that times out is `deadline`), key budget 8 minutes (the lease), whole job window 25 minutes. Line budget: the existing `LineBudget` (70 lines) and the in-flight cap `snapshots` (50, `OT_IBKR_SNAPSHOTS`) both apply, so at most 50 quotes run at once (`## Capacity`); error 101 shrinks the lines (existing, tested); at most 40 message starts a second, a cancel counting as a start (`pacing.py`). The line is cancelled in a `finally` and the ticker removed (ib_async keeps one ticker per conId). Reconnect on 10197: the gateway's session is re-opened by pyside's `supervise` and the key is retried by the runner (issue 21 marks the loss in wave 1; wave 2, issue 13, adds the retry policy); the rows written so far stay. No TWS or phone session may be logged in while the gateway is up (10197 kills the session): a note for the owner, not code.
11. Slot and early close: the schedule values are `anchor = "session_open"`, `offset = "15m"` (and `-45m` for the plan); the Japan slots are Decision 21, so the calendar moves both on an early-open day. The pull ends before 10:10 ET.
12. A gap at the open: the plan is made on the last close, but the stored band reaches k = 1.75 or 25 percent below the close, whichever is nearer (Decision 3), and the pull recomputes the band at the open spot and chooses inside it, so a stock that gaps down by up to about (1.75 - 1.4) * sigma * sqrt(T), 3.5 percent at sigma 0.35 and 30 days (more for a higher sigma), keeps its whole band; the puts are stored only up to around the close, so a gap up quotes the strikes the stored band holds and the open's strikes above it are outside it. A stock that gapped beyond that is quoted on what the band holds; the page shows "outside the planned band" for a contract whose row has `outside_band` (not asked, status `deferred`). The button is the owner's way to a better set; it uses the stored plan only (Decision 14). A replan after the open is left out.

21. Japan (owner 2026-11-10: add). What is quoted: the Nikkei 225 monthly index options of OSE (class 225, the `option_eod_jp` manifest) and the JP stocks of the watch list (chain, class and multiplier as the JP section of the `optioneod` manifest names them). Calendar `XTKS`, zone `Asia/Tokyo`. Slots come from the calendar: plan job `option_open_plan_jp` at `session_open` minus 45 minutes (08:15 JST when the TSE opens at 09:00), pull job `option_open_jp` at `session_open` plus 5 minutes (09:05 JST; option-trader's `jp-open-snapshot` runs at open + 5 minutes with a 20-minute bound; owner 2026-11-10, "ask option-trader"). Plan: the same function (around_spot, puts, calls; order, k = 1.4 and deferral as Decision 3; owner decision 15:33Z) with DTE 14 to 90 as option-trader's `plan_jp_v1` (its owner decision of 2026-10-16, #749), no deep puts; the chain of a stock: exchange `OSE.JPN`, multiplier 100, trading class = the stock code (the `optioneod` JP manifest names these); at most 60 per name and 80 for the index (class 225); names in the `no_option` list of `job_plan_jp.toml` are quoted as underlying only (option-trader's `no_option_names`, the owner's JP exclusion #1662; seeded from the JP names `option-capture-jp-stocks.md` found without options). The session date of a JP run is the date in Asia/Tokyo, named explicitly in the key (not the New York date). During the lunch break 11:30 to 12:30 JST the refresh asks nothing and answers "lunch break; stored quotes of <time>", as for a closed market (Decision 15); the break is the value `lunch_break = ["1130", "1230"]` of `job_pull_jp.toml`, exposed by `optionopen.JPLunchBreak()` (issue 17) and read by the session check of issue 10; the calendar knows only open and close. Option-trader's JP details have not arrived and the owner said to ask nothing more: the values above are `job_plan_jp.toml` and `job_pull_jp.toml` values and change without a design.

### Scheduler checks

22. Postcondition, progress and start (option-trader #1026, #1677, #1808, #1782, #1275). (a) At the end of the pull run, and by 10:00 ET at the latest, the plan rows of the session day exist and at least N rows are `ok`, N being `min_ok_share` (0.5, a value of `job_pull.toml`) of the planned items that are not `deferred`; a run that misses it is a failed run and a gap, not a quiet success. The pull starts no new key after 10:00 ET. (b) The run summary of Decision 8 also lists progress per stock (items done, time of the last row) and the pull writes a heartbeat line every 30 seconds, so a stuck run shows while it runs. (c) No replacement run and no per-chunk row write in this cut (option-trader #1782 and #1809, `## Left out`): a crash writes nothing and the runner retries the key. (d) A missing gateway socket or key (DSN) is seen at the start of the run, not at 09:45 (option-trader #1275): the families are left out with one named line and the day shows a gap, and the other jobs run (`docs/design/scheduler.md` Decision 8); the start path of the scheduler is not changed.

### The refresh button

13. Path: the web button posts to `ot serve`, which asks pyside, directly, for the plan contracts of the symbols on the page and answers with the new rows; no database write. `POST /options/refresh` with a body `{"symbols": ["AAPL", ...]}`; the page JSON then is fetched again by the web and the builder reads the live rows from an overlay reader in `cmd/ot` that puts the in-memory rows over the stored `obs.option_open` rows. Rows of a refresh are not stored: a refresh is not an observation for the history, the 09:45 slot and the close are. (Storing them would need a writer role in `ot serve`; Decision 17.)
14. Scope of one call: the contracts of the plan of today for those symbols, at most 8 symbols and at most 40 contracts in all (held first, then by the rank of the page: the card contract of each symbol, then the chain rows near the spot). `/options` refreshes the symbols of its cards; `/options/stock/<key>` refreshes that stock. No plan for the day (the plan job has not run or failed): the answer is the notice "no plan today", and nothing is asked. Live ticks over the one gateway connection (Decision 9); no per-item timeout of its own (pyside's is 20 s, 15 s after `OPTION_OPEN`) and no retry: the call is cancelled at 15 s and rows not yet received are dropped; rows that did not complete keep their stored values and the notice names how many ("27 of 31 quotes fresh, 4 from 09:45").
15. Freshness rule (option-trader: reuse under 60 s): a symbol whose newest in-memory refresh is younger than 60 s is not asked again; the answer says "reused, 41 s old". A call that finds another call running waits for it up to 3 s: for the same symbols it then reuses that call's rows, for other symbols it answers the notice "another refresh is running, try again" and asks nothing (one call at a time per process, Decision 17). Outside the regular session of the clock (not between open and close of the calendar, early close included) the endpoint asks nothing and answers "market closed; stored quotes of <time>". No lock and no refusal between the button and the scheduled pull: they share the one line budget and the one in-flight cap of the gateway in pyside, and the clients partition it by request size. The pull sends its contracts in chunks of 30 (one chunk in flight), a refresh call in chunks of 20 (one in flight); 30 + 20 = 50 is the in-flight cap and is under the 70 lines, so neither starves the other (`LineBudget` wakes all waiters with no order, so the design does not rely on a queue). Two refresh calls never overlap (Decision 17).
16. Failure and fallback: pyside not reachable, the gateway not connected, or the deadline: the answer is HTTP 200 with the notice and the stored rows (never an error page, and never a cached "not listed"). A refresh row of status other than `ok` or `partial` is dropped, not shown.
17. The permission this adds, said exactly. Today `ot serve` has the pages role of the database and no network to the broker; the only thing it does besides reading is `POST /owner-settings` under `--owner-edit` on a loopback address. This design adds: `ot serve` (under a new flag `--live-quotes`, off by default, loopback address only, like `--owner-edit`) holds a `broker.Broker` client to the pyside socket (`ibkr.sock`, Decision 9) and may call `Snapshot` for contracts of today's plan: with the kind `KindOptionEod` in wave 1 (the one the pull sends) and `KindOptionOpen` after issue 19; the button always sends the kind the pull job sends. It cannot place an order (the broker port has no such method), cannot write the database (no new DSN), cannot read accounts, and the contracts it may ask are only those of the plan table. What changes is who may act on the gateway: a browser tab on the owner's machine, through a POST, can make the gateway spend lines and a 15 s of its pacing; an open page left on a refresh loop could starve the 09:45 job of lines. Priority of the 09:45 job: a call of the button that starts inside the pull job's window (09:44 to 10:10 ET) asks at most 10 contracts and in one chunk of 10, so the job's chunk of 30 always finds its lines; outside the window the chunk is 20. Limits: one call at a time per process, 60 s reuse, 40 contracts, and a count of at most 30 calls an hour. **Second opinion: a change of who may act; the owner waived the separate review, the advisor answers it (2026-11-10) and the owner gives the merge word.** Alternative that avoids it, not chosen: a control socket of the scheduler process; it does not exist in code, would give the web a way to start jobs, and so adds more power (`## Left out`).
18. Pages show (puts filtered to delta -0.05 to -0.35 by the builder's copy of the stored delta, a display filter, Decision 3): next to every bid, ask, IV and Greek of a contract the quote time (exchange-local `HH:MM:SS`, "09:45:12"), the data type as a word (live, frozen, delayed) and its source ("open pull", "refresh", "close archive"); older than 15 minutes grey, a type other than live in red words; a contract with no open or refresh row shows its `option_eod` value with the label "close archive, 11 Nov"; the open interest shows its own date. The builder only copies these fields; the web renders them. No yield or score is recomputed by the web, and none by the builder either: the page shows no yield at the new bid (the card's yield stays the stored value of the candidates run, labelled with its own time; `## Left out`). The schema change is Decision 19.

## Capacity

Can pyside carry this? From the code (`pyside/src/optdesk/ibkr/`), not from a guess:

- How it serves quotes today. `transport.py` `Snapshot` runs one `IbGateway.quotes` task per request and streams each row when it completes. `quotes` starts one task per contract at once; each takes a snapshot lease (`DEFAULT_SNAPSHOTS` 50, `OT_IBKR_SNAPSHOTS`), then a line lease (`DEFAULT_LINES` 70), then one message start from the `MessagePacer` (40 starts a second, a cancel counts as a start). So quotes are concurrent, at most 50 in flight, not one at a time. Each item is one streaming `reqMktData`, released when its fields are complete or at `timeout_s` 20 (the 5 s open-interest grace applies to `OPTION_EOD` only). One IB connection per `[[gateway]]` entry, one client id each (default 33); error 101 shrinks the line limit to the lines in use less one. The in-flight cap (50) is the effective limit, below the 70 lines; the account's own limit is 100 lines (option-trader), and an open TWS window eats from those 100, which is why 70 is the budget and 50 is what runs.
- What is not there. The session type is set once per connection (`ibgateway.py` `open_session`); a kind has no type of its own (Decision 9). `LineBudget` wakes all waiters with no order. `ResolveContract` goes through the `DetailsLane`: 2 in flight, rising to 5 when ten answers average under a second, halving over 3 s, and one request that runs 20 s drops it to 1 and pauses 30 s. There is no `Snapshot` batch size limit beyond the leases.
- The size of the open plan, an estimate to be checked by the first plan run. Per expiry with sigma 0.35 and 30 days, `sigma * sqrt(T)` is 0.10 and k = 1.4 puts the lowest put at 0.869 times the spot, a band of 13.1 percent, against 14 percent for the former k = 1.5: about 7 percent fewer strikes at equal days to expiry (the same for every name at equal sigma and days). With a strike step of 2.5 on a stock of 150 that is about 8 put strikes and 2 around the spot, about 10 contracts per expiry for puts and around_spot; 20 to 45 days holds 3 to 4 expiries (weeklies) or 1 (monthly only), and every one is pulled: about 33 per name on average. The owner's list is about 45 US names, so about 1,500 contracts for puts and around_spot, plus held calls (up to k = 1.4, about 8 strikes per expiry, say 10 held names: about 280), about 1,800 in all by default; with `calls = "all"` about 2,900. The ceilings (350 + 1400 + 1200 = 2,950) hold both; the far strikes are what is deferred when a run is larger. The count is an estimate to be checked by the first plan run, which writes the count per class. Option-trader's first run, 44,188 items, is the warning of how this grows.
- Wall time of the pull at the upper size (`calls = "all"`; about 2,900 contracts, taken as 2,700 for the arithmetic below; the default of about 1,800 is smaller). A quote holds its line from request to completion, typically 1 to 3 s at the open and up to 15 s when nothing comes; far out-of-the-money calls are the slow ones, so assume 20 percent of the calls and 10 percent of the others wait the full timeout. Wave 1 (`OPTION_EOD`: 20 s timeout) retries a timed-out put once and a call never (`retry_classes` of `job_pull.toml`), so a slow call costs 20 s and a slow put 40 s: 240 slow calls * 20 s + 150 slow puts * 40 s = 10,800 line-seconds over 30 in flight = 6 minutes. The pull keeps 30 in flight (Decision 15); the pacer allows 20 items a second (two starts per item) and the probe measured 5 to 6 a second (option-trader #299 measured 10.9 at 70 lines), so the base time is the measured one: 2,700 contracts take 8 to 9 minutes (7.5 to 9 at 5 to 6 a second) and the default of about 1,800 take 5 to 6 minutes. The 30-in-flight line-seconds figure (6 minutes) is the bound for the timeout tail on top of the base, not a replacement for it: about 14 to 15 minutes at worst for 2,700 in wave 1 and about 12 once `OPTION_OPEN` (15 s) is in, and about 10 to 11 minutes at worst for the default. The pull key is a batch of stocks of up to 120 contracts (2 to 3 stocks, about 23 keys), because a key of one stock never fills 30 in flight and 45 keys in sequence would cost 45 times the slowest item; each `Run` sends chunks of 30 one after another and stays inside the 10-minute lease. Does the 50-in-flight cap still finish inside the slot budget of 25 minutes? Yes: 6 to 15 minutes in wave 1, a margin of about 1.7 times at worst for 2,700 and about 4 times for the default at its base time; the margin is thin at the upper size, so the stop rule matters: the job starts no new key after 15 minutes (10:00 ET, Decision 22) and the rest of the plan is written `deadline` (the order puts the far calls last). If the first pull (its `requested_at` and `received_at` columns) shows more than 20 percent slow, the retry of puts is dropped as well (a `job_pull.toml` value). The refresh button's share: 20 in flight (10 inside the window 09:44 to 10:10); 30 + 20 = 50, so the button never takes the job's lines. A refresh of 40 contracts in chunks of 20 takes two waves, 2 to 6 s typically, and may end partial inside 15 s (the notice says how many).
- Advisor's estimate (2026-11-10, at 5.5 contracts a second): about 2,500 contracts take 7.5 minutes; with the per-name cap about 1,600 take 5 minutes. The 30-in-flight arithmetic above is a bound; this throughput is the planning figure, and conservative: option-trader #299 measured 10.9 items a second at 70 lines.
- Measured by the load probe of 2026-11-10 (option-trader, live ticks): quotes about 5 to 6 contracts a second, a resolve 0.16 s, 37 percent of the strikes not listed, bid and ask on 100 percent, IV and delta on 98.6 percent, all type live. At 5 to 6 a second the default plan (puts to k = 1.4, calls for held names only, about 1,800 contracts) takes about 5 to 6 minutes and 2,700 contracts (`calls = "all"`) about 8 minutes, inside the estimates above, which are upper bounds; the resolve numbers below are the pessimistic option-trader ones and the first resolve run measures its own.
- Cost of the listed checks. `ResolveContract` is the slow call: option-trader measures about 5 s per (underlying, expiry), serialised, and its first run on 148 expiries overloaded the gateway (#776) and once stopped it answering (#757). Here the lane starts at 2 in flight, so a first day with no cache needs 500 to 700 resolves at 1 to 5 s over 2 to 5 lanes, about 5 to 30 minutes, possibly more; a day with the cache (`master.instrument` holds every con_id, `master.option_not_listed` every mark) resolves only the new strikes, a few dozen. The first day with about 1,300 uncached contracts needs 1,300 resolves at 1 to 5 s over 2 to 5 lanes, 5 to 55 minutes. Therefore the resolve stage caps new resolves per run at 300 (a `job_resolve.toml` value; a hand run by the window takes a larger value, 1500, since the resolve key is one stock and each key is a minute or two inside the lease) and stops its resolves after two consecutive timeouts; what is left is `deferred` and reported. The resolve job runs every evening on its own slot; for the first day the window runs it by hand after issue 15 has merged and been deployed (before that no hand path exists: both `ot run-once` and `ot backfill` run registered jobs only): `ot run-once` with the scheduler stopped, or `ot backfill` of the key once its window has closed; the order is issue 15, deploy, the hand resolve, then the 08:45 plan; run again if some stocks were deferred; after that only new strikes and expiries need resolves, a few dozen, and the nightly `option_eod` already resolves its contracts into the same cache.
- What must change in pyside: for the first pull only issue 21 (the read-only probe and the session-loss codes, `## Gateway safety`) and no new kind (the probe of Decision 9: the existing `OPTION_EOD` kind on the `main` gateway returned live ticks at the open, and the pull dials the gateway of `ibkr.sock`, which is `main` when the deployed `default` is `main`; the concurrent, line-budgeted quote path and the 40-per-second window exist and are tested; the design only fixes how the pull and the button split the in-flight cap, Decision 15). Wave 2: a kind `OPTION_OPEN` with its own spec (15 s, no grace), and the rest of the session codes of `## Gateway safety` (issue 13). Anything under 500 contracts and 40 messages a second is within what the code already does; the real latency of 2,700 items and the resolve time are measured by the first pull itself (every row has `requested_at`, `sent_at` and `received_at`).

## Gateway safety

Learned from option-trader's gateway checks (its advisor, 2026-11-10), set against what `pyside/src/optdesk/ibkr/` has. Five points.

1. Read-only proof. Option-trader: after every handshake a short second connection with client id 0 sends one `reqOpenOrders` and passes only on the rejection "Read-Only mode" (error 321) within 5 s; no rejection means `GatewayNotReadOnly`, an alert and a stop that the starter does not restart; neither answer fails the connection. Optdesk has: the send guard of `transport.py` (`install_guard`, installed on every client before it connects; `ORDER_IDS` 3, 4, 21, 58 refused first, then an allowlist of ids 1, 2, 7, 9, 20, 25, 49, 59, 71, 78 and 61 to 64, everything else refused: stricter than option-trader's deny list, since reqOpenOrders 5, reqPnL 92 and 94 and the others are not on it) and the "Read-Only API" setting of IB Gateway as the second layer (`pyside-gateways-health.md` decision 5). It has no proof that the second layer is on. What the open pull needs: the guard already covers it (`gateway_factory` installs it on every gateway), and the open pull uses only ids already allowed (1, 2, 9, 59, 78). There is one connection to the gateway (Decision 9), so one probe per gateway process is enough. Wave 1 (issue 21): a new file `readonly_probe.py` holds the probe with its own narrow send guard (only message id 5, `reqOpenOrders`; every other id refused, the order ids first), and `ibgateway.py` runs it after every handshake and before the session is marked connected: a short connection with client id 0, one `reqOpenOrders`, passing only on error 321 ("Read-Only mode") within 5 s; anything else raises, the gateway stays not connected, and `Snapshot` already answers `UNAVAILABLE` ("the gateway is not connected", `transport.py`), so a run fails before its first request. No edit of `transport.py` is needed. Wave 2, issue 16 (owner merge): only the `allowed` parameter of `install_guard` (point 3). Source: option-trader #757, #786, #794 and its ADR 0004.
2. Health and session codes. Option-trader: a monitor of 1100/2110 (lost), 10197 (competing session), 1101/1102 (ready: a new connection generation, old subscriptions re-requested after 1101), 2103/2105/2157 (degraded); a check every 5 minutes. Optdesk has: `apiEnd` marks the session lost and wakes the jobs; `supervise` reconnects with a capped backoff and a new generation; `_on_error` ignores the codes 2100 to 2199 as informational (this swallows 2110 and 2103) and sees 1100 to 1102 and 10197 with no con id, so a 10197 (another login of the same user took the market data; the socket stays up) shows as silence: every item times out and the run ends `deadline`. The open pull cannot tell that from a thin market. Policy for the open pull, as option-trader: on 10197 keep the quotes already received, cancel the subscriptions, probe one underlying and one option at growing intervals (5, 10, 20 s), retry the unfinished items when the probe answers, and close the run partial at its deadline; the unfinished rows are written status 9 (`disconnected`), never `no_data` and never a not-listed mark (Decision 6). Wave 1 (issue 21): 10197 and 1100 mark the session lost (the path of `apiEnd`), so open items end `disconnected`, never `deadline`. Gap for wave 2: the monitor of 2110, the new generation after 1101 and the retry policy: issue 13. `pyside-gateways-health.md` (`/health` of the gateways) stays and reports a `competing_session` state in its text only if that file's contract allows it; otherwise it stays true/false.
3. Client ids. Option-trader: fixed distinct constants per role, a check that rejects duplicates and 0, no retry on error 326 (id in use), a message allowlist per role, a pacer key per gateway. Optdesk has: a `client_id` per `[[gateway]]` entry (default 33) and a check that rejects a duplicate (host, port, client id) (`gateways.py` `_check`). The open pull adds no connection and no client id (Decision 9), so nothing is needed for the first pull. Not there, for wave 2: 0 is not rejected (0 is reserved for the probe), there is one allowlist for all gateways, and a connect that fails with 326 is retried with backoff (in wave 1, issue 21, it stops and fails). The per-role allowlist is a `install_guard` parameter in the owner-merge issue 16; the rejection of 0 is in issue 13. Client ids are fixed constants, never 0 and never shared: the job connection keeps 33; the button reaches the same connection through pyside and adds none in wave 1, and a connection added later for the button takes its own fixed id; the line cap of 100 is per gateway login, so a second id would share the 70-line budget and not add one (option-trader ADR 0012).
4. Order guard in code. Covered: the guard is installed on every client by `gateway_factory`, and the open pull uses only ids already allowed (1, 2, 9, 59, 78). The Go side adds no order method (Decision 17; `broker.Broker` has none). Nothing in this design adds a message id.
5. Pitfalls and the pacer. Option-trader's lessons: one pacer per gateway (#757: the gateway stopped answering in a chain refresh; #786), fully specified contracts (we send con_ids), the same login elsewhere kicks the session (10197: the owner's note, Decision 10), no TWS while the gateway is up. Optdesk has one `MessagePacer` and one `LineBudget` per `IbGateway`; with a single connection to the gateway (Decision 9) that is one pacer per gateway, the rule of option-trader, and the pull and the button share it by sharing the connection. Port 4001 of IB Gateway is for probes only, never for the jobs (they go through pyside); each quote line is cancelled after its tick and the simultaneous lines stay under the account's 100 (Decision 10: 70 budget, 50 in flight); rows carry the pull time (`requested_at`, `received_at`) and the refresh re-pulls one name at a time. No change is needed: there is one connection, so no shared pacing is built (`## Left out`).
