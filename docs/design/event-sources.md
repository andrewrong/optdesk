2. Dividends: IBKR tick 456 through `pyside`, as the old system and plan v2.5 row W5-6 have it; no new account. The tick is four comma-separated values (past 12 months, next 12 months, next ex-date `YYYYMMDD`, next amount). IBKR does not say declared or projected, so the guard treats every ex-date as projected.
3. Earnings: Alpha Vantage `EARNINGS_CALENDAR` (`horizon=3month`), ported from the old source (header found by name; a notice body for a wrong key or used-up quota is an error, never `absent`; fewer than 500 rows is refused). Confirmed by the owner 2026-11-09; it is the only source the old system had; IBKR gives no earnings date through `pyside`. A new outside service for optdesk: `second-opinion case: new outside service`. The key `ALPHA_VANTAGE_API_KEY` is read by the `.env` loader and passed in; it never enters an error, log or row.
4. What a gate may do with these rows (the gates are the next design; this is the contract they get). A vendor earnings date is never a company confirmation. Until a design ports the SEC estimated window, a `listed` date can only refuse or mark a candidate, never clear it; the date is `unconfirmed` unless its `time_of_day` is `pre-market` or `post-market` and the row is at most 2 days old (the old rule's two tests, without the window). `absent`, `unsupported` and `error` all mean unknown, never "no results before expiry", and an unknown or missing date gates as blocked (the candidate waits; it is not cleared); with `horizon=3month` an expiry beyond three months cannot be judged either.
5. Japan, earnings: Alpha Vantage does not list Japanese companies. The JP route is J-Quants `GET https://api.jquants.com/v2/fins/earnings-date` (JPX's own API, all listed companies with the date history, fields `PubDate` and `SchDate`, see the probe under Decision 12; the `/v2/equities/earnings-calendar` endpoint lists only March and September fiscal year companies, so it is not used). Owner 2026-11-09: "a, 我应该有账户，我之前注册过" (an account exists). Auth of the current V2 API is one header `x-api-key` and nothing else (V2 refuses `x-api-key` with `Authorization`; the V1 mail, password and refresh token flow is gone). The env key is `JQUANTS_API_KEY`, read by the `.env` loader and passed in, never in an error, log or row; the owner puts the value from the J-Quants dashboard in the service `.env`. option-trader never used J-Quants (no match in its code), so no earlier key name exists to reuse. The entry's `symbol` is the 4-digit securities code of a JP stock, sent to the vendor as the 5-digit code (the 4 digits plus "0") in `code`, and matched back after the vendor's 5-digit `Code` is cut to 4. The endpoint takes exactly one of `code`, `date`, `scheduled_date`, so the source makes one call per JP watch symbol (Decision 12). Rows have `source` `jquants`; no pagination was seen, and a body that carries a `pagination_key` is `error` `unexpected_pagination`, not a silent truncation; an empty `SchDate` (undecided) is `absent`. A new outside service: `second-opinion case: new outside service; owner's word 2026-11-09 given`. The JPX 決算発表予定日 Excel is left out, not a fallback: it is the same JPX data a day behind the API, its terms for automated download were not found, and it adds a second source, an xlsx dependency and a layout that changes per period for a case the gate already covers (a failed or missing J-Quants answer writes `error` or `absent`, which gates as blocked per Decision 4, never as cleared). The J-Quants account is the free plan (owner 2026-11-09: "免费版，所以要省着调用"), so calls are budgeted (Decision 12), and the plan's data delay (about 12 weeks, observed) means most JP dates for the next report are absent: a JP company without a date gets `absent`, and the gate sees unknown, so blocked. For an issuer with an override the job writes only the owner row that day and no vendor row (the vendor's answer for that issuer is dropped), so one issuer has one row per day and the key never collides; the once-a-day rule of Decision 12 ignores rows with `source` `owner`. 12. Call budget (owner 2026-11-09: the J-Quants account is the FREE plan, "免费版，所以要省着调用"; the Alpha Vantage key is the free tier, about 25 calls a day). The rule, the same for both earnings sources:
   - At most one `Fetch` per source per job run. `earnings_refresh` makes one `Fetch` per source: one Alpha Vantage call (the one `EARNINGS_CALENDAR` csv covers all US issuers) and one J-Quants call per JP watch entry.
   - At most one run per day: the job is keyed by the `XNYS` session day and makes no call for a source that already has a row of the day with any status, `error` included (an `unsupported` row has source `none` and an owner row has source `owner`; neither belongs to a vendor source, so neither stops a call, and neither is written a second time, see the second run below); a manual `run-once` on the same day does not call again either.
   - A second run of the day (the scheduler or `run-once`): the job reads the rows of the day through `EarningsDateReader` and writes no row for an entry that already has a row of the day, of any status and source; so a second run adds no row, the owner and `unsupported` rows included. It returns the same Permanent error as the first run when a row of the day it read has status `error` (so the runner does not loop on it), and success otherwise. `EarningsDateWriter` is also idempotent on the key: an insert whose key exists is left as it is (ON CONFLICT DO NOTHING), no error, as a backstop for two runs at once. An entry added to `watch.toml` after the first run has no row until the next day.
   - No automatic retry loop, inside a run or across runs of a day. A failure is recorded as an `error` row (attempt 1) and gates as blocked (Decision 4) until the next day's run. A 429 or any limit answer (J-Quants 429, the Alpha Vantage notice body) is recorded as `error` with `error_code` `rate_limited` and is not retried; a J-Quants failure on one code stops the remaining calls of that `Fetch` and every JP entry gets the `error` row.
   - J-Quants, one call per JP watch symbol: `GET /v2/fins/earnings-date?code=<4 digits>0`, sent with the header `x-api-key`; the budget is the number of JP watch entries per day, once a day, never a bulk request (the endpoint refuses one, see the probe) and no `refetch_days` or `max_calls` key. The source takes the JP symbols in `EarningsConfig.Symbols` (Alpha Vantage ignores it). Pagination was not seen; the source keeps no page cap and treats a `pagination_key` in a body as `error` `unexpected_pagination`. No worker chooses a request shape: it is this one.
   - Free plan delay: the probe shows the free plan serves this endpoint about 12 weeks behind on `PubDate`, so the next report's date, published 4 to 6 weeks before it, is mostly absent. The design fixes `delay_days` 84 (approximate, observed) as the free-plan figure; no code reads it. The gate rule: a J-Quants date is `unconfirmed` (Decision 4) and never clears a candidate, and a JP company with no date is `absent`, which gates as blocked. The job stores the date as listed and leaves that judgement to the gate (`source` `jquants` is the signal). Only a paid plan (Open question 3) could change the figure, by a revision of this design.

## What the owner gets

- You keep one short file, `watch.toml`, of the companies you watch, US and Japanese, with an optional `buy_price` and `sale_price` per company that the option-candidates work reads. The valuation work reads the same file. This design is the file's one owner.
- Once a day, for each US company, the system stores the next results date the vendor lists, or "not listed", with the vendor's time text; a Japanese company's date comes from J-Quants (JPX's own API, one call per company a day); on the free plan the data is about 12 weeks behind, so most Japanese dates are "not listed" and hold the candidate back. A date is a vendor's word, not the company's: it can make a candidate wait or carry a mark, never approve it.
- After one command, `ot probe dividends`, run on your gateway machine, you know whether IBKR gives ex-dividend dates for US and for Japanese stocks. Only a market that passes gets a dividend schedule. Then per stock and day the next ex-date and amount per share are stored; the guard for short calls reads them as projected, never as declared.
- Dates you type in `watch.toml` as `report_date_override` win over any vendor. Before the jobs run you do two things: add `OT_PG_DSN_EVENTS`, `ALPHA_VANTAGE_API_KEY` and `JQUANTS_API_KEY` (the key from your J-Quants dashboard) to `.env`, and run `ot migrate` and `ot setup pg`. You write no J-Quants file. No Telegram text, no order touched.
