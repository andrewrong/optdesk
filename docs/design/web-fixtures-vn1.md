## Scope

The pass is cut to what has a consumer: `market_summary` and `options_summary`, whose v2 cards landed (#132, #133) and so froze v2
under the version rule. Everything else of the list waits for a consumer (`## Left out`); a schema written before its card would be
unproven (its tags would never have met `json-schema-to-typescript`) and may be amended in place before its first consumer
(`checks.yml` accepts `<id> vN amended before first consumer`).

## Decisions

1. Tagged unions. A slot that holds a value or a reason is `oneOf` of branches that each have a required `kind` with a distinct
   `const`: `value` for every figure def, `gap` for `Gap`. The variable part is never `null`; an absent optional string, number or array
   is an omitted property. `kind` is the one tag name (no existing property has that name, see above).
2. New vN only. `page.market_summary.v3.json` and `page.options_summary.v3.json` refer to `common.v2.json`. Nothing existing is edited:
   `common.v1.json`, every `page.*.json` and `carryover.sha256` stay.
3. A `unit` const is lower snake case (`^[a-z][a-z0-9_]*$`); of the common figures only `UsdFigure` changes (`USD` to `usd`). The local
   figures of the two pages already comply. Other pages are not touched.
4. Staleness without the browser clock. A v3 page requires a top-level `stale_after` (`Timestamp`). `StaleLabel` of `common.v2` is
   `{data_time, text, is_stale}`; the label has no `stale_after` of its own. The browser shows the text, marks the card from `is_stale`
   and has no `Date.now`, timer or clock-skew alert. This is stated plainly as a lock-in: `is_stale` is a boolean that Go sets once when
   it builds the view-model, so a page left open does not turn stale, and no Go code emits it until the follow-up of `## Left out`; a
   different behaviour needs a later version. The fixtures are the only producers until then.
5. Fixtures: `web/fixtures/v3/<dir>/{ok,gap,stale,bad-version}.json` plus a README, validated in Go by a new test with its own table; the old
   directories stay. The manifest lists path strings, as today.
6. Types: the web script `generate:types` writes the two v3 files; the top-level `title` of a v3 file is `<PascalName>V3`. `web/src/generated/index.ts`
   is not changed (it is the interface entry of row `contracts`, so this design does not touch it): the two cards import the v3
   types from `@/generated/market_summary.v3` and `@/generated/options_summary.v3`.
7. Cross-module license. The schemas, the Go tests, the script, the generated outputs, the v3 fixtures with their manifest lines and the
   shared `StaleNotice` component land in one issue, so that each card is built from the interface issue alone. Reasons, as in
   `docs/design/web-v2-types.md` (Decision 4, points i and iv): AGENTS.md says a change to code generated from `contracts/` carries the
   source and the output together, and `generate:types` is the source of the outputs; the fixtures need the schemas and the test of the
   same issue, and the manifest is one file; the cards' tests read the fixtures and render `StaleNotice`, so a sibling issue for either
   would put a card behind an unmerged sibling. `web/package.json`, `web/fixtures/**` and `web/src/pages/home/StaleNotice.tsx` with its test
   (row `web`) join the contracts files in that one issue; nothing else in the cut edits two modules. No new dependency
   (`json-schema-to-typescript` 16.0.0 is a devDependency already).
8. Offline check of the generated types: a Go test reads each v3 schema and its committed `.ts` and asserts that every property name,
   `const` and `enum` value of the schema appears in the file, that `null` does not, and that the banner and the top-level name are
   there. It does not regenerate (no node, no network). Drift of the other direction is the owner's CI step (`## Left out`).
