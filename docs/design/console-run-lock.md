# Console run lock: two runs of one job never overlap, in memory; a console run takes no database lease

Author: the optdesk window (draft)
Owner approved: (pending)
Date: 2026-11-12
Source: owner 2026-11-12 09:48Z: every job of the scheduler can be re-run by hand; two runs of the same job must not run at the same time; the whole-process lock only prevents another process and does not control re-runs between tasks; no queueing.

## Goal

Today a console run is refused `lease_held` whenever `ops.run_lease` is held under another owner: `BackfillWith` takes it under a random owner `backfill:<hex>` (`internal/runner/reconcile/backfill_force.go`, `holdLease`), the scheduler tick under `runner` (`reconcile.go`), and a console run killed by a deploy leaves its owner holding the lease for `leaseTTL`. The console turn also runs on the one worker of `internal/runner/sched/ticker.go` (`runTurn`), and a request is held while a slot start is near (`SlotHold`, `slot_near`): the console waits for a tick and for a slot, which is a queue. `Reconcile` also walks the keys of all jobs one after another, so a long job makes the others miss their slot (owner 09:55Z: "queuing makes jobs miss their time; jobs are independent"). After this design a console run takes no lease, scheduled runs of different jobs run in parallel, a run is refused only by a run of the same job, and nothing waits.

## Modules

- runner (`internal/runner/**`): `reconcile` (the per-job lock, a goroutine per job in `Reconcile`, no lease in `BackfillWith`), `sched` (the console loop off the tick worker).
- jobs (`internal/jobs/**`): five jobs declare their upstream (Decision 6).
- ot (`cmd/**`): the console host claims requests and returns them as funcs, stops setting `Hold`, and maps the new reason.
- pages (`internal/pages/**`): the text of the new reason.

## Interface

One interface file changes, `internal/runner/api.go`: a new optional method of a job, beside `Scheduled` and `Bounded` (the places where a job gives the scheduler its schedule and run bound today; `job.toml` is read by each job package with no shared schema, so a toml key would need a parse in every package):

    type Dependent interface { After() []string } // ids of the jobs of the same day that this job reads

A second addition, the one owner of the console request goroutines (Decision 4) and the contract between `sched` and `cmd/ot`:

    type ConsoleRun func(ctx context.Context) // one claimed request, run to its end under ctx
    type ConsoleClaimer interface { ClaimConsole(ctx context.Context) ([]ConsoleRun, error) }

`ClaimConsole` reads the queue, claims requests and returns one `ConsoleRun` per claimed request; it starts no goroutine. The ticker owns every goroutine: it calls `ClaimConsole` on a console goroutine of its own (not the loop goroutine, not the worker), one call at a time, and runs each `ConsoleRun` in a goroutine of its own under a console context it drains and cancels (Decision 4). `ConsoleTurner` stays in `api.go` and keeps working: the ticker uses `ConsoleClaimer` when the reconciler has it, else `ConsoleTurner` as today; its doc comment gains "Deprecated: replaced by ConsoleClaimer; it runs on the worker and never overlaps a Reconcile". A later design deletes it. `Prober` and the `New` comment of `ticker.go` keep describing the worker's ledger calls, which stay true for the worker; the console goroutine's own calls are stated in Decision 4. Each of the issues for `sched` and `cmd/ot` is built and checked against these declarations alone, with a fake on the other side. `BackfillOptions.Hold` and `SlotHold` stay in `api.go` unused by the console (a later design may delete them). The refusal is a `KeyRun` of group `GroupLeaseHeld` with `ReasonCode` `job_running`, a free string. The interface issue lands before the issues that use it.

## Decisions

1. `BackfillWith` takes no lease. The process exclusion of serve is the scheduler fence (`ticker.watchFence`), the exclusion between runs is Decision 2, and the live-run check of a key (`closeExpired`) stays. `Reconcile` keeps `holdLease` under the owner `runner` as today, and `Backfill` (the bare call of `ot backfill`) keeps its own `backfill:<hex>` lease, so `ot run-once` and the backfill command behave as before. `ops.run_lease` is not shared and not counted: no change to `Acquire`, `Release` or the renewal.
2. One in-memory try-lock per job id, held in the `reconcile` package around every job run: `bareRun` (forced re-run, no run row), `runMissingKey` (console run of a missing key) and the key run of `Reconcile`. A busy job is not run and not waited for. `BackfillWith` writes a `lease_held` line with `ReasonCode` `job_running`; `Reconcile` leaves the key for the next tick. Per job, not per job and key: "two runs of the same job". The lock set is created once in `cmd/ot/scheduler.go` beside `host`, outside `build` (which makes a new reconciler and backfiller on every swap, `preflight.go`), and is passed to every reconciler and backfiller through a constructor option of the `reconcile` package (not `api.go`), so Reconcile, `BackfillWith` and a swapped reconciler all share one set and a run that started before a swap still holds its job.
3. The slot hold is removed from the console path: `cmd/ot` stops setting `BackfillOptions.Hold` and the request is no longer held for a slot (`turn` no longer calls `h.q.Hold`; `slot_near` is no longer produced). The per-job lock replaces it.
4. The console runs off the tick worker, and the ticker owns its goroutines (Interface, `ConsoleClaimer`). The trigger is the ticker loop's console turn: the loop only signals a console goroutine (a non-blocking send; one claim at a time, a signal during a claim is kept as one pending signal), so the loop makes no ledger call and `TestTickerCallsNoLedgerOnLoopGoroutine` holds. The console goroutine calls `ClaimConsole` under the console context below, so a stop or a lost fence cancels and drains it with the requests (its store calls are bounded by `startPhase`, 1 minute, which is no loop's concern) and runs each returned `ConsoleRun` in a goroutine of its own. Those goroutines run under a console context made from the context that outlives `runCtx` (as `workCtx` does): `Run` waits for them `drainGrace`, then cancels it and waits `killGrace`, and a lost fence cancels it at once, so no job runs after the fence is lost. A `ConsoleRun` calls nothing owned by the worker: not `refresh`, not the `disabled` map. Different jobs run at once; the same job is refused by Decision 2.
5. Scheduled runs are parallel too. `Reconcile` keeps its walk over days in order; inside one day, `reconcileOn` plans all jobs and writes the expected keys and windows as today, then runs the keys of each due job in a goroutine of its own, one per job (the keys of one job in order), and waits for all of them before it computes the result of that day and sets the cursor from the result over all keys, as today; the next day starts after that. The only guard is Decision 2: a job that is already running (a console run, or the previous tick that has not ended) is skipped for this tick and the key stays missing, so the day is not complete and the cursor holds, and the next tick retries it. `Reconcile` keeps `holdLease` once for the whole call under the owner `runner`, not per job, and its renewal runs until every job goroutine has returned.
6. A dependency is order, and the scheduler computes it; nothing waits. A job gives its upstream jobs by `After() []string` (`runner.Dependent`), next to its `Schedule()` method. One rule for every job that implements it: a dependent runs for day D at max(its own slot instant on D, the moment its upstream ends for D); never before its own slot, and a failed upstream never leaves it unrun (fallback, not cascade).
   - At the dependent's slot turn, `reconcile` finds for each id in `After()` the state of the upstream for D: it maps the id to its keys through the plan of the day and reads the run ledger (`ledger.Runs`, which carry a key, not a job id). Upstream ok (for a multi-key upstream, the keys of day D all ok): the dependent runs. Upstream still running: the turn leaves the dependent's keys as they are and returns, with no wait and no hold. An upstream that is due in this same call and has not ended (a restart or a late start with both slots due): the dependent is left to the trigger of the upstream's end, so a dependent never beats its upstream. Upstream failed, already ended without ok, or not due in this call and with no ok run for D: the dependent runs now anyway, on what is stored, and its key line carries `ReasonCode` `upstream_missing` (as for a console run below).
   - When a run of an upstream for D ends, ok or failed (a `done` or failed run, or a forced re-run that returned), `reconcile` starts each dependent of that job whose slot instant on D has passed and that has not run for D, in a goroutine of its own under the per-job lock of Decision 2 (a running dependent is skipped); a dependent whose slot has not passed is left to its slot turn. An ok upstream gives a plain run, a failed one a run marked `upstream_missing`. A dependent's own dependents follow the same way when it ends.
   - Every dependent started this way runs under the context of the call that triggered it, and that call waits for it before it returns: `Reconcile` (under its lease and drain, Decision 5) or the `ConsoleRun` of the request (under the console drain, Decision 4); none outlives its trigger, its lease or the fence.
   - A forced bare re-run of an upstream writes no run row (`bareRun`), so it never counts as an ok run, though it triggers dependents when it returns without error. The day of an upstream in another calendar (`option_eod_jp` on XTKS before `compute_figures` on XNYS) is the latest session day of the upstream's calendar that is not after D.
   - A run of a dependent alone from the console never starts its upstream (owner 09:59Z) and is not held by the order: it runs on what is stored and its key line carries `ReasonCode` `upstream_missing` when an upstream is not ok (set only when the run left that code empty; the outcome and the group are unchanged), with the upstream ids in the `upstream` attribute of the run log. The mark is written wherever a dependent's key is run: `bareRun`, `runMissingKey`, the key run of `Reconcile` and every triggered run, stored as the `ReasonCode` of the run row given to `RunKey` when that would otherwise be empty (for `bareRun`, which writes no row, on the key line only). Only an upstream's completion triggers dependents, never the reverse.
   The pairs, from the slots in each `job.toml` and the jobs' own reads: `option_open_plan` -> `option_open`; `option_open_plan_jp` -> `option_open_jp` (each has its slot at the session open, so it runs at the open, after the plan); `option_eod`, `option_eod_jp`, `quote_snapshot` -> `compute_figures` -> `option_candidates`; `account_capture` -> `position_marks` (the manifest of `position_marks` says it is placed after the account job). Other pairs are added the same way by a later issue; none is guessed here.
7. `cmd/ot` `classify`: a result with no `ran` or `rerun` line and at least one `lease_held` line of reason `job_running` ends the request `refused` `job_running`. Any other `lease_held` end stays as it is.
8. The page shows `job_running` as "this job is already running; press Run again when it ends".

## Left out

- A queue of waiting runs, a wait, a retry: the owner said none. A dependency is a trigger by completion, never a queue.
- The page text of `upstream_missing` on a `ran` or `rerun` line: the mark is in the stored line and the log; a page issue follows when the owner wants it shown.
- A guessed dependency: only the pairs of Decision 6 are declared; others (for example `option_list_preopen` and `option_open_resolve_gap` before the plan) are a later issue after a check of what each job reads.
- A lock per job and key, or per dataset: the owner's rule is about a job, and a finer lock would let two runs of one job overlap.
- A change of `ops.run_lease`, its owners or its renewal: `Reconcile`, `ot backfill` and `ot run-once` keep it.
- Deleting `BackfillOptions.Hold`, `SlotHold` and `ConsoleTurner`: an interface change for a later design.
- Stopping a running job from the page.
- `ot run-once` is a separate process with only the runner lease, so it and a console run may run one job together; run-once is being retired in favour of the console.
- Accepted for development mode: several broker jobs running at once on the pyside gateway may hit IBKR pacing limits. No limit on concurrent jobs is added; a pacing failure is a job error as today.

## Adversarial

Answered from `console-lock-adversarial.md`.

- Gap, the lock misses `bareRun` (blocking): adopted; Decision 2 puts the lock in the reconcile package around `bareRun`, `runMissingKey` and Reconcile's key run, not in `runkey.go` alone.
- Gap, the slot hold is a wait (blocking): adopted; Decision 3 removes it from the console path and leaves the field in `api.go` so there is no interface change.
- Gap, no trigger for the console turn off the worker: adopted; Decision 4 names the loop's own console turn and the goroutine per claimed request.
- Risk, a shared owner `runner` lets `ot run-once` in and its release deletes serve's row (blocking): adopted by dropping the shared lease. `BackfillWith` takes none; `Reconcile` is unchanged, so the owners are as today. The holder count, the shared renewal and the release race do not arise.
- Simpler way, no lease in `BackfillWith`: adopted, Decision 1. Moving the console off the worker is kept, because a request must start while a tick runs.
- False claims (run-once is refused by `Acquire`; the key runner path covers `bareRun`): both removed from the design.
- Files missing (`jobconsole_sched.go`, `jobconsole_scheduler_test.go`, `jobconsole_turn_test.go`, reconcile `fakes_test.go` and the backfill tests, `ticker_console_test.go`): adopted, in issues 2, 3 and 5.
- Owner 09:55Z, scheduled runs parallel too: adopted as Decision 5, guarded only by the per-job lock.
- Owner 09:59Z, a downstream run alone must not re-run the upstream: adopted in Decision 6 (a basic check of the ledger, a mark, no refusal).
- Owner 09:57Z, "with a dependency the scheduler runs the upstream first, then the next job; unrelated jobs never queue": adopted as Decision 6, refined by the owner at 12:00Z to order (a dependent runs at max(its slot, the end of its upstream), never before its slot; a failed upstream runs it marked, never leaves it unrun); the declaration is one new optional method, `Dependent.After`, next to `Schedule()`, which makes `api.go` an interface change with its own first issue.
- Console goroutine not drained or cancelled on fence loss; `disabled` map race: adopted, Decision 4.
- Lock-in of deleting the hold: avoided by leaving `Hold` in `api.go`.
