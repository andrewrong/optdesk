## Goal

On `/job-console` of `ot serve --owner-edit` the page lists every job. Four jobs can be run from the page, because their `Run` uses the day it is given; for each of the other twenty the page says why it cannot (it answers only in its own slot, or it reads the state of now whatever the day). For a runnable job the owner chooses a day and force yes or no, presses `Run`, and the page shows the request as `queued` (with the reason when it is held), `running`, then `done`, `refused`, `failed`, `interrupted` or `withdrawn`, with one line per key: what that run produced, whether the key is present now, and a reason code. A queued request can be withdrawn from the page. After a reload the last requests and their per-key lines are still there. The run is done by the scheduler process, which holds the service env and the run lease, as one turn of the ticker's own worker; `ot serve` only writes request rows and reads results. No terminal step.

Idempotent means, here and in `## Idempotency of the jobs`: a second run of a job for a day adds no duplicate row; a row is changed only by the job's own revision or upsert rule on changed content. Three jobs key a row by an attempt counter, so a forced second run adds one row under the next attempt: that is the job's own key, not a duplicate of the same attempt. The table names the rule of each job and says which lines were read; the page does not claim more (Doubt 6).

## Decisions

1. **The page writes a request; the scheduler's worker runs it.** `ot serve` inserts one row into `settings.job_request` (job id, day, force). The scheduler process takes a waiting request as one turn of the ticker's worker (Decision 8), runs `BackfillWith` for that day and the job's keys (`jobDatasets`, `cmd/ot/backfill.go:124-165`, resolves a job to its datasets), and stores the result in the same row. Why not `serve` shelling out to `ot backfill`: `serve` would need the runner DSN, the vendor keys and a gateway, which it holds none of; a page that can start a process is a larger authority than a page that can write one row. Why not a goroutine beside the ticker (revision 2): a second consumer shares the lease with the ticker's Reconcile, outlives the ticker's drain and needs its own yield, bound, cap and expiry rules; the worker is already serial and awaited at a stop.
2. **Two tables, a unique index that holds force.** `settings.job_request`: `id` (identity), `job_id`, `session_day`, `force`, `requested_at` (default `now()`), and the columns of the scheduler: `state` (`queued` default, `running`, `done`, `refused`, `failed`, `interrupted`, `withdrawn`), `started_at`, `finished_at`, `reason` (a code), `hold_job` and `hold_at` (why a queued request waits, Decision 8), `keys jsonb` (the object `{"v":1,"lines":[...]}`, one line per key with the fields of `KeyRun`: `dataset`, `subject`, `group`, `status`, `error_code`, `reason_code`, `returned`, `usable`, `attempt`, `present`). A partial unique index `(job_id, session_day, force) WHERE state IN ('queued','running')` makes a double press of the same kind one request (the insert is `ON CONFLICT DO NOTHING` followed by a read of the open row) and lets a press of the other force value make its own request; both run, one after the other. There is no 409 and no silent drop of the owner's force. `settings.job_request_withdraw` (`request_id` primary key referencing the request, `withdrawn_at` default `now()`) holds the withdrawals: the web role can insert there and cannot update a request. There is no cap on open requests and no floor on the day (revision 2 had both): the owner is one person, and each request is one serial turn. No role can delete a row; the page lists the newest 20 and the tables have no retention (Doubt 9). The page reads the view `rd.job_request_r1` (every column named, with `withdrawn_at` joined in) with `OT_PG_DSN_PAGES`.
3. **Who may act, said plainly.** Today the page token of `/owner-settings` lets whoever holds it change the owner's rules and names. After this design the same token also lets him queue a run of the four runnable jobs for any day not after today, which spends vendor quota (Alpha Vantage 25 a day for the fundamentals source), broker pacing and the worker's time, and with force appends rows; it can withdraw a queued request and can never delete or edit a row (the web role cannot). The token binds no route (`Check` has no route argument, `settings.go:243-260`), so one token works for the three posts for 15 minutes. Reach is local: the remote address must be loopback, the Host a loopback name with the listen port, a cross-origin post is refused, and `serve` refuses `--owner-edit` on another address (`serve.go:52-54`). The web role is the existing `ot_w_settings` and the line `OT_PG_DSN_SETTINGS`, with `INSERT, SELECT` on the two new tables in a schema it already holds. Schema `settings` is insert-only for every role but the owner today; this design makes `ot_runner` the first non-owner role to hold `USAGE` on it and an `UPDATE` in it: on seven named columns of `job_request` (`state`, `started_at`, `finished_at`, `reason`, `keys`, `hold_job`, `hold_at`) and nothing else, with `SELECT` on both tables and no grant in `ops`. `0033_underlying.sql` uses a narrow role of its own for a similar need; roles `ot_w_jobrequest` and `ot_w_jobrequest_run` would narrow the two sides at the cost of a change of `internal/store/setup`, an `.env` line and an owner step each (Doubt 4). No new role, no new `.env` line, no `ot setup pg` change here. The owner's merge of this design is his word for the widened authority.
4. **Force is "run a present key again", and a console run is invisible to the scheduler's own accounting.** `ForceBackfiller.BackfillWith(ctx, day, datasets, BackfillOptions{Force, RunInWindow, Job})` does not skip a `present` key: it runs it as an extra attempt (`seq = runs+1`, `backfill.go:81`). `Backfill` keeps its reason `backfill`; `BackfillWith` starts its runs with the reason `console` (`runner.ReasonConsole`). The tag is a free-text column read by five places, and each is named:
   - `RunKey` with the reason `console` writes the mark `present` when the verdict is present and writes no mark otherwise: no `no_value` from the console for any job, a `present` mark is never overwritten, a key never tried stays unmarked. The tag is kept where the code overwrites it: the cut branch writes `abandoned_stop` only for another reason (`runkey.go:86-88`), the verdict writes `empty_before_close` only for another reason (`runkey.go:192-194`), and `markCrashed` keeps `console` and sets only the error code (`reconcile.go:423-429`). A console run that was cut, empty or died is therefore no crash and does not count toward `crashBrake`. Both causes of a cut (the key's own deadline at the job's run bound and the request's bound, Decision 8) leave the same tag and show as `cut`.
   - `nextAttempt` and `expireIfClosed` look at the runs of a key without the runs tagged `console` (a helper `withoutConsole`, applied after the `running` checks, so a live console run still blocks a start and a lapsed one is still closed). `expireIfClosed` returns at once when the filtered list is empty, before `closeRow`, so `closeRow` row 3 never indexes `runs[len(runs)-1]` of an empty slice (`reconcile.go:388,403`). A key that only a console run has touched is run by its own slot as if the console had not run, and a retryable console run never makes the scheduler write `no_value` at the close.
   - `dayState` in `backfill.go` keeps all runs on purpose: the attempt number is `len(runs)+1` over all runs so run ids stay unique (`runkey.go:53`), and a live lease of any run is a live lease.
   - `lastRuns` in `cmd/ot/runoutcome.go` skips console runs, so `run-once` does not print the rows or the reason of a console run as the key's own outcome (entry 10).
   Nothing is deleted and nothing is cleared. The ask said "clear the mark, then run"; clearing opens a window in which a present key looks missing to the gap syncer.
5. **A call selects keys by job, and the outcome of a key is what that attempt produced.** `BackfillOptions.Job` is a job id: with it set, `BackfillWith` keeps from the keys of the listed datasets only those whose job (`p.job[k].ID()`) is that id, so pressing `option_open` never runs the keys of `option_open_jp` that share its dataset. `BackfillResult` gains `Keys []KeyRun`: key, `Group` (what this call did with the key: `already_present`, `ran`, `in_window`, `lease_held`, `not_reached`), and for a key that ran the `Status`, `ErrorCode`, `ReasonCode`, `Returned`, `Usable`, `Attempt` of its own new run row, and `Present`, the mark after the call (read as `backfillKey` reads it, `backfill.go:295-311`). The outcome of a line comes from the run row; `Present` is shown beside it and is never the outcome. The six old lists stay and are filled as before for a call without options. The reason is always a code, never the text of a job error (`safeErrText`, `runkey.go:121-135`, exists for logs only); what the job itself says for "nothing" (`after session`, `missed slot`) is in the log only (Left out).
6. **What can be run from the page is a table, and the page lists every job.** `cmd/ot` holds one table of the 24 job ids with a kind: `any_day` (the four of "What main holds"), `slot_only` (nine; reason `answers_only_in_its_slot`: the scheduler runs it in its slot) and `reads_now` (eleven; reason `reads_the_state_of_now`: the day is a label). The page shows every job; a runnable one has the form, any other shows its reason text and no form. The post refuses a job that is not `any_day` (422). A drift test asserts that the ids of the table are the same set as the jobs the wiring builds. `ot backfill` is unchanged by this design: the runner refuses nothing (revision 3's `LiveOnly` and its refusal are gone), so `ot backfill --day <past>` still marks a `slot_only` key `no_value` as it does on main (Doubt 5).
7. **A console run does not wait for its window.** `Backfill` lists a key inside its window as `InWindow` and does not run it (`backfill.go:66-71`), so "Run today" during the session would do nothing. The turn sets `BackfillOptions.RunInWindow`. An answer that is empty before the close leaves the key unmarked (Decision 4), and its own slot still runs it.
8. **A console request is one turn of the ticker's worker; it is held while a slot is near; the bound is the job's own.** `runner.ConsoleTurner` is an optional interface of the Reconciler, found by a type assertion like `Prober`: `ConsoleTurn(ctx, hold SlotHold) (took bool, err error)`, where `SlotHold` is `func(bound time.Duration) (jobID string, at time.Time, held bool)`. The ticker does the rest:
   - the loop submits a turn with `console` set only when it submits no reconcile turn: a due slot or tick is submitted before a waiting request, and a request waits at most until the next wake of the loop (at most 30 s, `ceiling`) when the worker is idle; one request per turn; the poll is one indexed `SELECT` on the refresh turn the loop submits anyway;
   - `hold(bound)` answers from the schedule the worker has published (`t.starts`): the first start of any enabled job in `(now, now+bound]` of the injected clock, `held` true; a schedule not yet published answers `("", zero, true)`, and a schedule that failed to refresh keeps the last published one (`ticker.go:358-362`);
   - `ConsoleTurn` (entry 7) reads the waiting requests, oldest first, takes the first whose job is not held (`bound` = that job's `RunBound`, `runner.Bounded`; a job without it gets the runner's default bound of 30 minutes, `defaultRunBound` in `runkey.go`), and for each request it passes over writes `hold_job` and `hold_at` on the row, so the page shows "held for <job> at HH:MM UTC" or "held: the schedule is not read yet"; a request that is taken clears them. There is no expiry: a held request waits as long as it must, and the owner can withdraw it;
   - the turn's context is cancelled with the cause `context.DeadlineExceeded` after the job's `RunBound` of the injected clock (`clk.AfterFunc`, in the host): the one number of the design is the job's own. The cause is how `ConsoleTurn` tells `cut` from a cancel by a stop or deploy (`context.Canceled`). A request of several keys has the one bound for the whole turn: the keys not reached when it fires are `not_reached` and the request ends `failed` `cut`; a job with many keys may need more than one request [unverified: how many keys `compute_figures` has on a day];
   - because a request starts only when no start of a slot lies within its bound and is cut at the bound, **a console turn never delays a slot**. A tick (a Reconcile that retries keys, not a slot) that comes due during a turn finds the worker busy, is not marked covered and runs when the turn ends, at most the bound and `busyRetry` late (`ticker.go:236-247`); a tick's retries are never lost to a held lease, because the worker is never in two places;
   - a stop or an executable change during a turn: the worker gets `drainGrace`, then its context is cancelled (`ticker.go:116-148`); the turn ends `interrupted` and is not run again by itself.
   `BackfillWith` stops at the cancel: before each key it checks `ctx.Err()`, and the keys not reached get the group `not_reached` and no run row (so the abandoned rows and the crash brake of the dead context are gone; entry 3). A job that ignores its context holds the worker as a job in `Reconcile` does today (the same two-hour `reconcileTimeout` exposure, `ticker.go:41`), and the lease heartbeat keeps the lease; the console adds no new kind of hang.
9. **The turn follows one order.** In `ConsoleTurn`: read the waiting requests; for each that carries a withdrawal, `Finish` it `withdrawn`; take the first not held and `Claim` it (`UPDATE ... SET state='running' WHERE id=$1 AND state='queued'`, one row or none); resolve the job among the jobs of the reconciler now in use (the host keeps the job set and the `Backfiller` of the last `build`, so a job a probe brought back is there; a job in the table but not in that set ends `refused` `left_out`, an id not in the table or not `any_day` ends `refused` `not_runnable`); `jobDatasets` (a job with no key on the day ends `refused` `no_key`); `BackfillWith` with `Job`, `RunInWindow` and the request's `Force`. **The end state, in this precedence:** (1) if `Plan` or `BackfillWith` returned with the context done, `context.Cause(ctx)` decides: `DeadlineExceeded` is `failed` `cut`, `Canceled` is `interrupted`, whatever error text came with it; (2) a call that returned with no key `not_reached` and no error is `done`, even when the bound fired at that instant; (3) `RefusedNoPlan` is `refused` `no_plan`; (4) `Retryable` from the lease (a `run-once` or `ot backfill` of the owner holds it) is `failed` `lease_held`; (5) a `Plan` error is `failed` `plan_failed`; (6) any other error is `failed` `error`. A cut or interrupted request keeps the lines of the keys done and marks the others `not_reached`. `Finish` is written with a context that is not cancelled. After `Finish`, `KeyGapSyncer.SyncKeys(day)` runs as `ot backfill` does (`cmd/ot/backfill.go:68`) under a 2-minute timeout, except for `interrupted`, whose gaps the next Reconcile turn syncs. A withdrawal of a request that is `running` is ignored: it ends by itself. **At start, the host's `Start` sets every `running` row `failed` with the code `restart`** (the fence makes this process the only consumer; the scheduler calls `Start` before the ticker runs, entry 10), so a row left by a kill, a frozen loop or a turn that missed the 5 s grace cannot hold the unique index for good. A request is never run again by itself. A panic in a job is the panic a `Reconcile` would have: no `recover` is added, the process ends, the row stays `running` and the next start fails it `restart`.
10. **The job table is static, checked by a test, and the page makes no claim about the scheduler.** The scheduler does not publish a capability table (Left out), so the page cannot show beforehand that the scheduler holds a job out: the request ends `refused` `left_out`. A `queued` request shows the time it was queued, its hold if it has one, "withdrawal pending" if it has a withdrawal, and otherwise the sentence "waits for the scheduler's worker; a running reconcile or console run goes first".

## Doubts (least sure)

1. A held request can wait for ever. `option_eod`-style slot clusters from 15:30 to 17:00 ET put a start inside a 10-minute bound for most of that window, and a job with a 45-minute bound (none of the four runnable jobs has one) would be held across several slots. The request shows why, can be withdrawn, and has no expiry by choice.
2. A job that ignores its context holds the worker and the lease until it returns (same as `Reconcile`, `reconcileTimeout` two hours), and a turn that loses the 5 s kill race leaves the row `running` until the next start of the scheduler turns it `failed` `restart`; for that time the unique index blocks the same job, day and force.
3. The poll rides the refresh turn of the loop, at most every 30 seconds; the page reloads every 5 seconds, so a request can wait up to 30 seconds behind an idle worker, and behind a reconcile turn of up to two hours. The page makes no claim about the scheduler.
4. The token is also a settings and underlyings token for 15 minutes, and the reverse (`Check` binds no route); a holder can queue runs of four jobs for any day, one turn each, with no cap, and spend vendor quota (Alpha Vantage 25 a day). The web role is `ot_w_settings` and the runner role `ot_runner` with a column-level `UPDATE`, the first non-owner update in schema `settings`; two narrower roles are cleaner and cost an owner step each.
5. A key of a lost day that is a gap stays a gap for good unless the owner runs `ot backfill` (it marks `no_value`); a day with no stored plan cannot be run from the page (`no_plan`); a console run writes no `no_value` for any job, so a past-day key that truly has nothing at the source stays `missing`, and the page shows `nothing_found`.
6. "Idempotent" is stated per job from reading; the writers of `iv_history` and `underlying_resolve` are inferred and nothing was run twice. A forced run of a `DO NOTHING` job reports `returned` and `usable` and cannot say that nothing new was stored; the page says "returned N rows" and never "stored".
7. The classification of `bars_refresh`, `fx_refresh` and `iv_history` as "reads the state of now" is conservative: their history query ends now and the day only bounds the stored comparison; if the owner wants them runnable for a past day it needs a reading of what the broker returns for a past end date [unverified]. `fx_refresh` was also read to stamp its rows with the clock.
8. How many keys `compute_figures` has on a day is not known; one request holds one turn bound, so a job with many keys may need more than one request. `fundamentals` is limited by its source's quota rather than the bound.
9. The page lists 20 requests; an older one is reachable only by `?request=<id>`, and the tables have no retention and no role that deletes.
10. The job table in `cmd/ot` is a second list of job ids and kinds; the drift test is the only guard and a new job is invisible on the page until the table gets a line. The wiring adds a `deps` field and a default line to `wire.go` (799 of 800 lines); if main moves so that this passes 800, the entry reports it and does not split the file.
11. A crash after `BackfillWith` and before `Finish` leaves a `running` row that the next start turns `failed` `restart`; the keys stored by that run are present, the per-key lines are lost.
12. A withdrawal is a request the runner processes on its next turn, so "withdrawal pending" can show for up to 30 seconds, and a request taken by the worker at that moment runs to its end.
