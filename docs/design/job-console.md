## Goal

On `/job-console` of `ot serve --owner-edit` the page lists the jobs, and for each says whether it runs for any day or for today only. The owner chooses a job, a day and force yes or no, presses `Run`, and the page shows the request as `queued`, `running`, then `done`, `refused`, `failed` or `interrupted`, with one line per key: what happened (present, already present, nothing found, unconfirmed, partial, failed, refused, waiting, skipped, not run) and a reason code. After a reload the last requests and their per-key lines are still there. The run is done by the scheduler process, which holds the service env and the run lease, as one turn of the ticker's own worker; `ot serve` only writes one request row and reads results. No terminal step.

Idempotent means, here and in `## Idempotency of the jobs`: a second run of a job for a day adds no duplicate row; a row is changed only by the job's own revision or upsert rule on changed content. Three jobs key a row by an attempt counter, so a forced second run adds one row under the next attempt: that is the job's own key, not a duplicate of the same attempt. The table names the rule of each job and says which lines were read; the page does not claim more (Doubt 7).

## Decisions

1. **The page writes a request; the scheduler's worker runs it.** `ot serve` inserts one row into `settings.job_request` (job id, day, force). The scheduler process takes the oldest queued request as one turn of the ticker's worker (Decision 8), runs `BackfillWith` for that day and the job's datasets (`jobDatasets`, `cmd/ot/backfill.go:124-165`), and stores the result in the same row. Why not `serve` shelling out to `ot backfill`: `serve` would need the runner DSN, the vendor keys and a gateway, which it holds none of; a page that can start a process is a larger authority than a page that can write one row. Why not a goroutine beside the ticker (revision 2): a second consumer shares the lease with the ticker's Reconcile, outlives the ticker's drain and needs its own yield, bound, cap and expiry rules; the worker is already serial, awaited at a stop and kept off a held lease by construction.
2. **One table, a unique index, no cap.** `settings.job_request`: `id` (identity), `job_id`, `session_day`, `force`, `requested_at` (default `now()`), and the columns of the consumer: `state` (`queued` default, `running`, `done`, `refused`, `failed`, `interrupted`), `started_at`, `finished_at`, `reason` (a code), `keys jsonb` (the object `{"v":1,"lines":[...]}`, one line per key with the fields of `KeyRun`: `dataset`, `subject`, `group`, `status`, `error_code`, `reason_code`, `returned`, `usable`, `attempt`, `present`). A partial unique index `(job_id, session_day) WHERE state IN ('queued','running')` makes a double press one request: the insert is `ON CONFLICT DO NOTHING` followed by a read of the open row. **Force is not in the index, and a silent drop is refused:** when the open row's `force` differs from the post's, the post answers 409 with a fixed text and the page shows that request; the owner presses again after it ends. A cap on open requests and a floor on the day are dropped (revision 2 had both): the owner is one person, the index bounds the rows per job and day, and each request is one serial turn. No role can delete a row; the page lists the newest 20 and the table has no retention (Doubt 9). The page reads the view `rd.job_request_r1` (every column named) with `OT_PG_DSN_PAGES`.
3. **Who may act, said plainly.** Today the page token of `/owner-settings` lets whoever holds it change the owner's rules and names. After this design the same token also lets him queue a run of any job for any day, which spends vendor quota (Alpha Vantage 25 a day), broker pacing and the worker's time, and with force appends rows; it can never delete or edit a row (the web role cannot). The token binds no route (`Check` has no route argument, `settings.go:243-260`), so one token works for the three posts for 15 minutes. Reach is local: the remote address must be loopback, the Host a loopback name with the listen port, a cross-origin post is refused, and `serve` refuses `--owner-edit` on another address (`serve.go:52-54`). The web role is the existing `ot_w_settings` and the line `OT_PG_DSN_SETTINGS`, with `INSERT, SELECT` on one new table in a schema it already holds. The runner role `ot_runner` is new to schema `settings`, which is a break of its insert-only habit: it gets `USAGE` on the schema, `SELECT` on the table and a column-level `UPDATE (state, started_at, finished_at, reason, keys)` on it, nothing else in `settings`, nothing in `ops`. `0033_underlying.sql` uses a narrow role of its own for a similar need; a role `ot_w_jobrequest_run` would narrow the runner side, and `ot_w_jobrequest` the web side, at the cost of a change of `internal/store/setup`, an `.env` line and an owner step each (Doubt 4). No new role, no new `.env` line, no `ot setup pg` change here. The owner's merge of this design is his word for the widened authority.
4. **Force is "run a present key again", and a console run is invisible to the scheduler's own accounting.** `ForceBackfiller.BackfillWith(ctx, day, datasets, BackfillOptions{Force, RunInWindow})` does not skip a `present` key: it runs it as an extra attempt (`seq = runs+1`, `backfill.go:81`). The run is started with the reason code `console`. Three rules follow, each one conditional in one named place:
   - `RunKey` with the reason `console` writes the mark `present` when the verdict is present and writes no mark otherwise: no `no_value` from the console for any job, a `present` mark is never overwritten, a key never tried stays unmarked; a run cut under `console` keeps the reason `console` (it is not rewritten to `abandoned_stop`), so it is no crash and does not count toward `crashBrake` (`runkey.go:86-88`). A run whose process died is closed `crashed` as before (`markCrashed`), and that one crash does count: it was one.
   - `nextAttempt` and `expireIfClosed` look at the runs of a key without the runs whose reason is `console` (a helper `withoutConsole`, applied after the `running` checks, so a live console run still blocks a start and a lapsed one is still closed). A console run therefore does not count as the scheduler's run, `closeRow` never picks it to rewrite, and a key that only a console run has touched is run by its own slot as if the console had not run (`reconcile.go:333-421`).
   - The attempt number is still `len(runs)+1` over all runs, so run ids stay unique (`runkey.go:53`).
   Nothing is deleted and nothing is cleared. The ask said "clear the mark, then run"; clearing opens a window in which a present key looks missing to the gap syncer.
5. **The outcome of a key is read from the run row of the attempt and the mark after it, not from the old lists.** `BackfillResult` gains `Keys []KeyRun`: key, `Group` (what this call did with the key: `already_present`, `ran`, `in_window`, `lease_held`, `refused`, `not_reached`), and for a key that ran the `Status`, `ErrorCode`, `ReasonCode`, `Returned`, `Usable`, `Attempt` of its new run row and `Present`, the mark after the call (read as `backfillKey` reads it, `backfill.go:295-311`). The six old lists stay and are filled as before for a call without options. The builder derives one outcome per line in Go (Decision 12). The reason is always a code, never the text of a job error (`safeErrText`, `runkey.go:121-135`, exists for logs only). What the job itself says for "nothing" (`after session`, `missed slot`) is in the log only and is not on the page (Left out).
6. **"Today only" is a capability of the job, and the job names the day.** `runner.LiveOnly` has one method, `LiveDay(now time.Time) contracts.Day`: the day the job answers for at the instant `now`, which is the expression of the job's own guard (`now.In(loc)` formatted as a day). Eleven ids implement it: the nine of "What main holds" and the two plan ids. `BackfillWith` and `Backfill` refuse a key of a `LiveOnly` job when `day` differs from `LiveDay(clock.Now())` at the call, with the group `refused` and the code `live_only_past_day`; the key is not run and not marked. So `ot backfill --day <past>` no longer marks these keys `no_value`: it prints `refused live_only_past_day`. A live-only job on today after its slot or stop still returns its own `NoValue`; with Decision 4 the console shows it as nothing found and marks nothing. The jobs keep their own check as the second guard. There is no zone derived from `Scheduled.Schedule()` anywhere. A `_jp` job answers for the Tokyo day: at 08:30 JST the Tokyo day is one ahead of the New York date, and `LiveDay` says so.
7. **A console run does not wait for its window.** `Backfill` lists a key inside its window as `InWindow` and does not run it (`backfill.go:66-71`), so "Run today" during the session would do nothing. The console turn sets `BackfillOptions.RunInWindow`. An answer that is empty before the close leaves the key unmarked (Decision 4), and its own slot still runs it (Decision 4, second rule). `in_window` is reported only by a call without the option.
8. **A console request is one turn of the ticker's worker, with one bound.** `runner.ConsoleTurner` is an optional interface of the Reconciler, found by a type assertion like `Prober`: `ConsoleTurn(ctx) (took bool, err error)`, which takes the oldest queued request if there is one, runs it and stores the result. The ticker does the rest:
   - the loop submits a turn with `console` set only when it submits no reconcile turn: a due slot or tick is submitted before a waiting request, and a request waits at most until the next wake of the loop (at most 30 s, `ceiling`) when the worker is idle;
   - one request per turn; `Next` is one indexed `SELECT` on the refresh turn the loop submits anyway;
   - the turn's context is cancelled with the cause `context.DeadlineExceeded` after `consoleBound` (10 minutes of the injected clock, `clk.AfterFunc`): the one number of the design. The cause is how `ConsoleTurn` tells `cut` (the bound) from a cancel by a stop or deploy (`context.Canceled`);
   - a slot or tick that comes due while a console turn runs finds the worker busy, is not marked covered and runs when the turn ends, at most `consoleBound` and `busyRetry` late (`ticker.go:236-247`); a tick's retries are never lost to a held lease, because the worker is never in two places;
   - a stop or an executable change during a turn: the worker gets `drainGrace`, then its context is cancelled (`ticker.go:116-148`); the turn ends `interrupted` and is not run again by itself.
   `BackfillWith` stops at the cancel: before each key it checks `ctx.Err()`, and the keys not reached get the group `not_reached` and no run row (so the abandoned rows and the crash brake of the dead context are gone; entry 3). A job that ignores its context holds the worker as a job in `Reconcile` does today (the same two-hour `reconcileTimeout` exposure, `ticker.go:41`); the console adds no new kind of hang. The bound is not measured (Doubt 1).
9. **The turn follows one order.** In `ConsoleTurn`: `Next`; `Claim` (`UPDATE ... SET state='running' WHERE id=$1 AND state='queued'`, one row or none); resolve the job among the jobs of the reconciler now in use (the host keeps the job set and the `Backfiller` of the last `build`, so a job a probe brought back is there; a job in `w.jobs` but not in that set ends `refused` with `left_out`, an unknown id `unknown_job`); `jobDatasets` (a job with no key on the day ends `refused` `no_key`; a failed `Plan` ends `failed` `plan_failed`); `BackfillWith` with `RunInWindow` and the request's `Force`; a nil error and `RefusedNoPlan` ends `refused` `no_plan`; every key `refused` ends `refused` with the code of the first; the cause of the context says `failed` `cut` (the bound) or `interrupted` (a cancel) and keeps the lines of the keys done so far, the others `not_reached`; `Retryable` from the lease (a `run-once` or `ot backfill` of the owner holds it) ends `failed` `lease_held`; any other error `failed` `error`; otherwise `done`. `Finish` is written with a context that is not cancelled. After `Finish`, `KeyGapSyncer.SyncKeys(day)` runs as `ot backfill` does (`cmd/ot/backfill.go:68`) under a 2-minute timeout, except for `interrupted`, whose gaps the next Reconcile turn syncs. At start, every `running` row is set `failed` with the code `restart` (the fence makes this process the only consumer); a request is never run again by itself. A panic in a job is the panic a `Reconcile` would have: no `recover` is added, the process ends, the row stays `running` and the next start fails it `restart`.
10. **The job list is static, checked by a test.** `cmd/ot` holds one table of job id, kind (`any_day`, `today_only`) and zone (the zone whose date the post uses: the market zone for US ids, `Asia/Tokyo` for the `_jp` ids). A test over the jobs the wiring builds asserts that the ids are the same set, that exactly the eleven of Decision 6 are `LiveOnly`, and, for each of them, that `LiveDay(t)` equals the table's zone date of `t` at four instants (a New York evening, a Tokyo morning before the New York date turns, just after midnight in each zone, and the day after). The scheduler does not publish a capability table (Left out), so the page cannot show beforehand that the scheduler holds a job out: the request ends `refused` `left_out`. The page makes no claim that the scheduler is up: a `queued` request shows the time it was queued and the sentence "waits for the scheduler's worker; a running reconcile or console run goes first".
11. **A double press, a post and a reload.** `POST /owner-job-console` (fields `job`, `day`, `force`, token) answers 303 to `/job-console?request=<id>`, so a reload never repeats the post. A today-only job has no day field: the post takes today of the table's zone, and the runner re-checks it with `LiveDay` at the turn (a request queued before midnight and run after it ends `refused` `live_only_past_day`, never run under another day). An any-day job takes a `day` that is `YYYY-MM-DD` and not after today of its table zone; any earlier day is accepted (no floor). A day with no stored plan ends `refused` `no_plan`: the page cannot create a plan and says so (Doubt 5).
12. **The page.** `page.job_console.v1`: `title`, `sentence`, `form` (null when the route is off, else `post_path`, `expires`, `mac`), `gaps`, `jobs` (`id`, `kind`, `day` for a today-only job), `requests` (the newest 20: `id`, `job`, `day`, `force`, `state`, `state_text`, `at_text`, `reason`, `keys`), `selected` (the id of `?request=`, shown even when older than the 20; an unknown id gives the gap `no_such_request`) and `refresh_seconds` (5 while a shown request is `queued` or `running`, else 0). A key line has `dataset`, `subject`, `outcome`, `outcome_text` and `reason`, derived in Go from the stored line and nothing else:

   | stored line | outcome | reason |
   |---|---|---|
   | group `refused` | `refused` | the stored `reason_code` (`live_only_past_day`) |
   | group `already_present` | `already_present` | none |
   | group `in_window` | `waiting` | `in_window` |
   | group `lease_held` | `skipped` | `run_in_progress` |
   | group `not_reached` | `not_run` | `cut` or `interrupted` of the request |
   | group `ran`, status `abandoned` | `failed` | `cut` |
   | group `ran`, status `partial` | `partial` | `cut` (the counts are shown) |
   | group `ran`, status `done`, `error_code` set | `failed` | the `error_code`; when `present` is true the text adds "the key stays present from an earlier run" |
   | group `ran`, status `done`, no error, `present` true | `present` | none; the counts are shown and the text does not say "stored" (a forced run of a `DO NOTHING` job cannot say that nothing new was added) |

## Doubts (least sure)

1. `consoleBound` (10 minutes) is chosen, not measured. A slot that comes due during a console turn runs up to 10 minutes and 5 seconds late. Whether 10 minutes is enough for a slow job is not known: a cut request is `failed` `cut`, its lines show what was done, and the owner can ask again.
2. The console poll rides on the refresh turn of the loop, at most every 30 seconds; the page reloads every 5 seconds, so a request can wait up to 30 seconds behind an idle worker. A reconcile turn can take up to `reconcileTimeout` (two hours) and the request waits behind it; the page says so without a claim about the scheduler.
3. The token is also a settings and underlyings token for 15 minutes, and the reverse (`Check` binds no route); a holder can queue runs, one turn each, with no cap (Decision 2). Stated as the change of who may act in Decision 3.
4. The web role is `ot_w_settings` and the runner role `ot_runner` with a column-level `UPDATE`, the first non-owner update in schema `settings`. Two narrower roles are cleaner and cost an owner step each; the design picks fewer steps.
5. A live key of a lost day stays a gap for good (Left out), and a day with no stored plan cannot be run from the page (`no_plan`); the gap line of `ot scheduler status` stays red until the owner decides.
6. A console run writes no `no_value` for any job (Decision 4): a past-day key that genuinely has nothing at the source stays `missing` and its gap stays open, where `ot backfill` would have closed it; the page shows `nothing_found` and the owner can run `ot backfill` for that case.
7. "Idempotent" is stated per job from reading and inferred for the writers of `iv_history` and `underlying_resolve`; nothing was run twice. A forced run of a `DO NOTHING` job reports `returned` and `usable` and cannot say that nothing new was stored, and a forced `earnings_refresh` of a present key probably does nothing; the outcome `present` makes no claim about rows.
8. `underlying_resolve` takes a day and ignores it (`job.go:102`): a request for any day does the same work; the page says so. The write rule of its settler was not located.
9. The page lists 20 requests; an older one is reachable only by `?request=<id>`, and the table has no retention and no role that deletes.
10. `jobDatasets` runs `Plan` inside the turn (`cmd/ot/backfill.go:143`); a slow `Plan` that reads the broker holds the worker until the bound, and the plan jobs read stored data only.
11. A crash after `BackfillWith` and before `Finish` leaves a `running` row that the next start turns `failed` `restart`; the keys stored by that run are present, the per-key lines are lost.
12. The job table in `cmd/ot` (Decision 10) is a second list of job ids and zones; the drift test is the only guard, and a new job is invisible on the page until the table gets a line.
13. A run closed `crashed` by `markCrashed` after a process death counts as one crash toward the brake of three, even when it was a console run.
