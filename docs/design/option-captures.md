# option captures, step 8 of the storage plan: a re-run of an option_eod or option_open slot replaces its rows, option_open is compressed, and one row per contract and day is kept for ever

Author: the optdesk designer (draft)
Owner approved: (pending)
Date: 2026-11-14
Revision: 2

Source: owner 2026-11-13 S1 ("every capture can be repaired, overwrite by key, a re-run replaces"), S5 ("options run once a day now, later many times; think about performance first") and the owner's ask for option chains 5 minutes after the open and during the day; storage plan v2 of the advisor, P2, P3 (items 1 to 6), P6 (rows "one contract over days" and "the chain of an underlying now"), section 2a item 5, section 4 step 8 and section 6. The pattern of the earlier steps is copied, not re-argued: `fundamentals-keys.md` (one statement per row with `IS DISTINCT FROM`, optional upserter, column grants, a migration that holds the auto-deploy) and `readings.md`. Revision 2 follows the advisor review r1 and the adversarial answer adversarial.md in the dispatcher's scratchpad (outside the repository, not published); `## Adversarial` answers each point.

Goal: a second run of the same slot on the same day replaces that slot's rows in `obs.option_eod` (today it adds a full set) and in `obs.option_open` (today it is dropped); a replacement never lets a worse answer (a timeout, a no-quote row, a delayed or frozen quote) overwrite a stored good one; `obs.option_open` is compressed like `obs.option_eod`; `obs.option_day` holds the last good quote of every contract and day for ever, written in the same transaction as the capture rows; the console rows of the three `option_eod` jobs can be forced. For the owner: running a capture twice no longer doubles that day's rows, and a re-run of today's slot repairs it. A past day is still not repairable: the broker answers for now (Doubt 3). More slots on the schedule are not added here (Left out). No key is changed, no row is deleted and no compressed chunk is decompressed in this design.

## Decisions

1. No key change (decision of the dispatcher, from the adversarial answer point 3). The primary keys stay: `(session_day, capture_id, instrument_id)` for `option_eod` and `(session_day, capture_id, slot, instrument_id)` for `option_open`. No decompression, no `DELETE` of captured rows, no compression setting change on `option_eod`, no new column on a capture table. The existing doubled `option_eod` rows stay as they are and `pickOptionEod` keeps choosing among them (the readers see no change; by the owner's word of 2026-11-13 "old data is not cared for"). [S] [O]
2. `option_open` write. Its `capture_id` is already deterministic (`day|slot|instrument`), so only the insert changes: `ON CONFLICT (session_day, capture_id, slot, instrument_id) DO UPDATE SET <every non-key column> WHERE <guard of Decision 4>`; a re-run of a slot replaces its row and an equal row is not rewritten. [S]
3. `option_eod` write and capture id. The job's `captureID` becomes `uuid.NewSHA1(OID, day|dataset|subject|slot)`: the run's start instant leaves the formula, the manifest slot enters it, so a re-run of the same slot of the same underlying meets the same capture id and the same keys, and a second slot of a day gets its own ids. The insert becomes `ON CONFLICT (session_day, capture_id, instrument_id) DO UPDATE SET <every non-key column> WHERE <guard of Decision 4>`. Slot is a manifest key only (`slot = "HHMM"`, a label of the run, never read from the clock): `1100` in `job.toml` and `job_index.toml` (09:30 + 90 minutes ET) and `1030` in `job_jp.toml` (09:00 + 90 minutes JST). It is not stored in a column of `obs.option_eod`: the deterministic capture id already separates slots, and no reader or day row needs the slot (the day row of Decision 5 orders by `received_at`). A slot column on `option_eod` would need `ADD COLUMN` on a table with compressed chunks, which this design avoids. The slot enters neither `manifest.canonical` nor the plan hash (`TestUSPlanHashPinned` and `jp_stock_test.go:376` stay as they are). The contract `contracts.OptionEod` and `obs.option_eod.r1.json` are not changed, so `Contracts: unchanged` for every entry. A re-run of a slot whose contract list differs leaves the rows of contracts that left the list in place (same capture id, no row replaces them): accepted. [S, own rule for the label]
4. The guard (advisor B2, order from advisor B1 of r2). The `DO UPDATE` carries one `WHERE` that decides whether the new row replaces the stored one: a new row replaces the stored one only when it is at least as good, by this order, written once as the one `WHERE` of each slot-row statement. `option_eod` ranks a row: 3 = status `1` and `snapshot_kind = 'session'` (good); 2 = status `1` and `off_session` (a delayed quote); 1 = any other status (`2` no quote, `5` error). A new row of a higher rank replaces the stored one; a lower rank never does; of the same rank, a new row replaces the stored one only when it differs in a compared column, and, for rank 3 and 2, only when it has no quote column NULL where the stored row has a non-NULL value (a thinner row never replaces a fuller one). `option_open` ranks status `1` = 2, status `2` = 1, any other status = 0, with the same rule: a higher rank replaces, a lower rank (a `2` over a `1`, a `3` over a `1` or `2`) never does, and of the same rank a new row replaces the stored one only when it differs and, for rank 2 and 1, has no quote column NULL where the stored row has a non-NULL value. So a forced run after the close (not live, `off_session`) never replaces a stored good session row, a timeout (status `5`) or a no-quote row (status `2`) never replaces a stored delayed or good quote, and a partial row never replaces a full one. Compared columns are every column except `capture_id` and `received_at`; quote columns are the compared columns except `status` and `snapshot_kind` (a re-run that returns the same quote is not rewritten, `IS DISTINCT FROM` on the row). One transaction per call; a key twice in one call is applied in order. A `-1`, NaN or infinity is still screened to NULL (`screenSentinel`, `screen`). A forced run is today-only and re-collects the whole slot at the moment of the force: each row carries its own `received_at`, so a slot repaired late holds rows of different moments; that is accepted and is why the console reason `moment_mix` goes (Decision 10). [S] [O]
5. `obs.option_day` (plan P3 item 4; owner S5 "one final row per contract and day"). A plain table, `PRIMARY KEY (instrument_id, session_day)`, foreign keys `instrument_id` and `underlying_id` to `master.instrument` (a plain table may reference a plain table, plan section 6), kept for ever, index `(underlying_id, session_day DESC)` for "the chain of one underlying on a day" (plan P6). Columns: `instrument_id bigint`, `session_day date`, `underlying_id bigint`, `source text` (`option_eod` or `option_open`: where the quote came from), `received_at timestamptz`, `status smallint`, `currency`, `bid, ask, bid_size, ask_size, last, volume, underlying_price, underlying_ccy, iv_bid_decimal, iv_mid_decimal, iv_ask_decimal, iv_decimal, delta, gamma, theta_per_calendar_day, vega_per_vol_point` (same types and checks as the capture tables), `open_interest numeric` and `oi_asof_date date` (null until a capture carries one), `updated_at timestamptz NOT NULL DEFAULT now()`, `written_by text NOT NULL DEFAULT ''`. No slot column: the day row is ordered by `received_at`, so labels of different jobs (`0945` and `1100`) are never compared. View `rd.option_day_r1` names every column; `ot_ro_pages` and `ot_runner` read it. It is derived, never a new broker pull. [S]
6. The day row's rules (plan P3 item 4, with the "a missing value never replaces a present one" rule of `fundamentals-keys.md`). Written in the same transaction as the capture rows, capture rows first, only from a usable capture row. Usable: for `option_eod` status `1` AND `snapshot_kind = 'session'`; for `option_open` status `1` or `2` (the statuses the page shows). A row that is not usable writes no day row, so a contract with no usable capture has no day row. The statement is `INSERT ... ON CONFLICT (instrument_id, session_day) DO UPDATE SET <quote columns> = COALESCE(EXCLUDED.col, option_day.col), received_at, status, source ... WHERE EXCLUDED.received_at >= option_day.received_at AND (stored compared columns) IS DISTINCT FROM (new values)`: a quote column the new row has as NULL keeps the stored value (advisor B2: a usable row that lacks a field does not blank it), a row older than the stored one changes nothing, and `open_interest` and `oi_asof_date` follow the same COALESCE (only `option_eod` carries them, so an `option_open` capture keeps them). With today's schedule the row is the open + 90 minutes value, not a close; it becomes an end-of-day value only when a slot near the close exists (plan P3 item 4). [S]
7. The shared file (decision 7 of the review). The day-row statement is written once, in `internal/store/shared/optionday.go`: `UpsertDaySQL` (the text) and `DayArgCount`; both `internal/store/snapshot` and `internal/store/optionopenpg` import it, which `scripts/arch/main.go:102-105,291` allows by the name `shared` (a sub-package that the other sub-packages of its row may import and that imports no sibling), so `shared` does not import `internal/store/optionday` and each store builds the argument list in the order the statement documents. No row edit of `docs/design/modules.md` is needed for it (the `store` row's glob `internal/store/**` already holds it). [S]
8. Roles (as `fundamentals-keys.md`). `ot_w_option_eod` and `ot_w_option_open` keep table INSERT. On the two compressed hypertables `obs.option_eod` and `obs.option_open` each writer gets table-level `SELECT` and `UPDATE` of its own table (`0047`), because TimescaleDB 2.19 copies a column-level grant to the compressed twin, which lacks the user columns (SQLSTATE 42703; #2384). On `obs.option_day` they get INSERT, UPDATE of the non-key columns (`0047`) and table-level `SELECT` (`0049`), because the upsert reads `written_by` through `EXCLUDED` (#2420). No DELETE, no TRUNCATE. `ot_runner` and `ot_ro_pages` read the three views as before. The migrations grant; `internal/store/setup` is not edited. [S]

The old methods and the readers. `InsertOptionEod` and `InsertOptionOpen` keep their names and signatures and now upsert (their doc comments in the frozen `internal/store/api.go` and `internal/store/openquote/api.go` still say "a retry adds no row"; `docs/contracts/store.md` states the new meaning, as `fundamentals-keys.md` did). `OptionEod` and `OptionOpen` keep their shape and their winner pick as a guard (it also hides the legacy doubled rows); no caller moves to `obs.option_day` in this step (Left out); a declarations-only reader for it lands now so those issues can follow (Interface). [S]
10. Console (plan section 2a item 5). The reason `moment_mix` goes for `option_eod`, `option_eod_jp` and `option_eod_index`: they stay today-only and gain Force (a forced run replaces the slot's rows, Decision 4). `quote_snapshot` keeps `moment_mix`. `option_open` stays listed-only (Doubt 4). [S]
11. Guarantee that a re-run is of today only (advisor decision 4). The upsert never meets a compressed chunk because a re-run cannot name a past day: the job returns Permanent for a day that is not the clock's date (`TestPastDayRefuses`, `internal/jobs/optioneod/run_test.go:389`) and the console answers 422 for a day other than today (`TestPostTodayOnlyTokyoZone`, `cmd/ot/jobconsole_post_test.go:210-221`); today's chunk is not compressed (Today, compression policy 7 days, `0006:74`). `ON CONFLICT DO UPDATE` on a compressed chunk is therefore not needed and not designed; what Timescale 2.30.2 does there (it allows an upsert into compressed chunks from 2.11 on by decompressing the batch: unverified) is recorded by one new test, not relied on. [S] [O]
12. Deploy order (advisor B1). Each step works with the deployed code of the others: (a) the job entry first: the new capture id with the deployed store, which ends `ON CONFLICT DO NOTHING`, drops the second run of a slot instead of doubling it and every first run inserts as before. From the deploy of entry 2 until the deploy of entry 4 a same-slot retry is dropped by the old `DO NOTHING`, so a retry cannot repair a status `5` row in that window; entries 2 and 4 therefore merge in one sitting (entry 4 right after the window ran `0047`); (b) the migration (`0047`) only adds: grants, a table, a view and compression of `option_open`; the deployed binaries use none of them, so it breaks nothing and holds the auto-deploy as the plan asks; (c) the two store entries, which name the new grants and `obs.option_day`, merge only after the window ran `0047`: a store binary on the old schema would fail on the missing table and the missing grants. The store entries cannot tolerate the old schema (the day row and the grants are the point of them), so the safety of (c) is the `Order: after 3` line of each of the two entries, the hold of the auto-deploy while the migration is unmerged or unrun, and the issue gate that opens entries 4 and 5 only after entry 3 is merged and run (Doubt 5). The window runs rebuild `ot`, `ot setup pg`, migrate, `ot setup pg` again. [S]
13. Migration lock handling (adversarial point 2). `0047` sets `lock_timeout` (a `SET LOCAL` first line in the Up transaction) before any statement that takes a lock on a hypertable (`ALTER TABLE obs.option_open SET (timescaledb.compress ...)`, `add_compression_policy`, the `GRANT`s on `obs.option_eod` and `obs.option_open`), so a long reader makes the migration fail and roll back instead of queueing every later reader behind it. The migration touches no row of `obs.option_eod`, changes no setting of it and builds no index on it. Enabling compression on `obs.option_open` (never compressed, one month chunks) is a metadata change; `segmentby underlying_id`, `orderby session_day DESC, capture_id, slot, instrument_id` (the whole key, so a unique check on a compressed chunk finds its columns), policy 7 days. The window runs it outside the 11:00 ET capture, as the owner decided for migrations. [S] [trial]
14. No old value is kept (owner S1): a replaced quote is gone; a wrong forced overwrite is repaired only by another run while the broker still answers (today). No `void` mark (step 9). Retention of intraday rows and a 7-day chunk interval start when runs exceed about ten a day (plan P3 items 2 and 5); both are settings, not migrations, and not done here. [S]

## Doubts

1. Timescale facts not read: the compression-policy timing for a one-month chunk (Today), `ON CONFLICT DO UPDATE` on a compressed chunk (Decision 11), enabling compression on a never-compressed hypertable with a primary key whose columns are all in `orderby` (Decision 13). Written from memory of the docs and marked unverified; the pg tests (`TestOptionEodConflictOnCompressedChunk`, the migration on a fresh database) are the check for the first and the last, and nothing depends on the second.
2. The `option_eod` day-row slot order: with no slot column the day row follows `received_at`, so a forced run after the close that returns good session data replaces the 11:00 value, which is wanted; a forced run with delayed data does not (`off_session` is not usable).
3. A same-day re-run of a past slot repairs it only while the broker has quotes for that slot's moment (it does not: it answers with the current quote). So "re-run replaces the slot" is correct for storage and weak as a repair; the owner's word "a re-run repairs" is met for a failed or partial run of today, not for history. Worth saying to the owner in one line in the pull request body.
4. `option_open` stays unforceable from the console (`no_lower_time_bound`: a forced run has no lower time bound and could quote outside the session). With the upsert a forced run would be safe for storage, but the reason is a job-guard question, not a storage one; not decided here.
5. `0047` can move its number; entries 4 and 5 carry the line `Order: after 3`, and the issue gate opens them only after entry 3 is merged; that the window has also run `0047` is not something the gate reads. Decision 12 makes the cost of a store merged before the window ran the migration one failed deploy of the store binary (the insert names a missing table or grant), not a silent loss; the window runs the migration first.
6. A forced run replaces a slot's rows at the moment of the force (Decision 4): a slot repaired late holds rows of several moments. Accepted; each row carries `received_at`.
7. Plan P3's row counts are derivations, not measures; nothing here depends on them.
