Goal. The seller needs the real contracts, with con_ids, of every watched US stock stored before the open, without depending on the day before (owner, 12:36Z: "必须有兜底方案"). Today the per-strike resolve guesses strikes and asks IBKR one by one. One `reqContractDetails` per (underlying, class, expiry) with no strike returns the real list, calls and puts together (`probes-5-6.txt`). This design adds that call and two new jobs that use it. It changes no existing job, no page and no plan; main's per-strike path keeps running beside it as the fallback. Design B consumes the stored lists. The indexes SPX, NDX and RUT are not in this design (`## Left out`).

## What main holds today

- `ContractsService` has `ListChains` and `ResolveContract` only. `broker.Broker` has no list call; `ReferenceClient` and `HistoryClient` are separate interfaces beside it.
- The details lane (`pacing.py`): timeout 20 s, then a 30 s pause, so a timeout costs 50 s; shared with dividends and bars. `parallel.txt`: 8 and 16 parallel calls finish in exact 5.0 s steps, so list calls do not overlap. **Every number below is 5.0 s per request.**
- The runner gives `Run` one key per call (`runkey.go:76`); `reconcileOn` runs the keys of a plan one after the other. Main's resolve jobs plan one key per stock, so each stock has its own budget clock and there is no order across stocks. Without `Bounded` a run bound is 30 minutes, and the deadline is max(window close, now) + bound (`runkey.go:253`). `verdict()` (`internal/runner/reconcile/runkey.go:172-196`): a run with `Err` of kind `NoValue` is `no_value`; any other `Err` is a failed run (Retryable before the close is not counted and is retried each turn; after the close it expires); with `Err` nil, a job that implements `runner.Postcondition` (`internal/runner/api.go`, `Postcondition(ctx, day, datasetID, subjectKey string) (bool, error)`) marks the key present exactly when it answers true, and a false answer is a done run without a mark, which counts and is not run again (`nextAttempt`, `internal/runner/reconcile/reconcile.go:333-365`); without a Postcondition the mark needs `Usable > 0` and an empty answer before the close is `empty_before_close`, retried each turn. A run cut with `Returned > 0` is `partial` and runs again the same day; a crashed lease is re-run (`reconcile.go` `nextAttempt`).
- `runner.Scheduled`, `runner.Windowed` and `runner.Bounded` are optional methods with plain values on a job (`internal/runner/api.go:92-113`; `resolveJob` has them, `listed.go:97-104`), so a job package needs no edit of `internal/jobs/api.go`. A window is the session close plus a non-negative offset (`window.go`), so it closes at 16:00 at the earliest. `parseManifest` needs `budget_minutes` above 0, `[params]` and an `after_close` window (`manifest.go:80-100`). `stocks()` keeps US stocks only (`inputs.go:76`). `jobs.WatchEntry` carries `BuyPrice` (`internal/jobs/api.go:25`) in `Stored.Watch`. Since #1709 `Stored.Watch` is not the watch.toml list: `cmd/ot` builds each options-group job with `jc.f.listed(groupOptions, build)` (`wire_underlying.go:123`), a `listedJob` (`cmd/ot/listedjob.go`) that at each `Plan` reads the stored underlying list and the held names, builds the inner job from the entries of the group (each with `BuyPrice`) and keeps that inner job for the `Run` of the keys it planned; `listed` forwards `Postcondition`, `Window`, `Schedule` and `RunBound` of the inner job, and an empty underlying list is a Permanent `Plan` error.
- `option_open_resolve` runs at close+60m (17:00 ET), `option_open_resolve_gap` at open-90m (08:00 ET), `option_eod` at close (16:00, `run_bound` 16m, so cut near 16:16), `fundamentals` at 08:00 ET, `option_ledger` at close+60m (no window), the JP plan at open-45m (18:15 ET in winter); one worker (`ticker.go`), `reconcileTimeout` 2 h.
- `store()` writes the broker's strike text (`req.Strike`, listed.go:419), which is the broker's canonical decimal text; `strikeKey` (`inputs.go:129`, `RatString`) is for matching only: "12.5" becomes "25/2". `putOptionSQL` sets `resolved_at = now()` on every upsert and nothing reads it.
- `transport.py` (owner-only; 771 lines) registers `ContractsServicer` in `build_server`, so a new rpc is a method on that class. `ibgateway.py` has 799 lines; the ratchet fails a file over 800 not in `ratchet.json`, which is owner-only. `transport.py` imports generated types only through `pyside/src/optdesk/contracts/api.py`; the generated servicer's methods are abstract for mypy, so every subclass (`ContractsServicer`, `_FakeContracts` in `tests/contracts/test_contracts_api.py`) gains the method in the same change. gRPC has its default 4 MB message limit (no option on main); the largest answer probed is 516 contracts, about 50 KB.
- pyside deploy is the owner's (`docs/deploy/pyside.md`).

## Decisions

1. **The rpc.** `ContractsService.ListContracts(underlying, expiry, right, trading_class) -> ListContractsResponse{ repeated ContractSpec }`: one `reqContractDetails` with no strike; an empty `right` means both rights in one answer (Decision 7); con_id, right, strike, multiplier, class per contract. Read only. A timeout, disconnect or gateway error is a gRPC error, never a partial list (IB returns the whole detail list or an error). `list_contracts` joins the log `WORDS`, and `ListContracts` the live `ALLOWED_RPCS` (rpc names, checked against the stubs by `test_guard.py`), as a read.
2. **Where the pyside code lives.** New file `pyside/src/optdesk/ibkr/lister.py`: `ListingGateway(IbGateway)` adds `list_contracts` through the details lane (`DetailsLane.run`: its 20 s timeout and 30 s pause apply, as for `resolve`), formatting every strike with the existing `_decimal_text` (the table's CHECK at `migrations/0032_option_contract.sql:18` is `^[0-9]+(\.[0-9]+)?$` on `strike` text, and the key has `strike` as text, so "12.5" and "12.50" would be two rows); `ibgateway.py` is not edited. **In flight 1:** the lane is used, its width is not (the 2 to 5 lane of single-contract `resolve` would let list calls overlap). `ListingGateway` takes its own one-slot lock (an `asyncio.Lock` in `lister.py`) before `lane.run`, so the wait for the lock is outside the lane's 20 s timeout, and the lock is released from inside the wrapped request, when the request itself ends (answer, error or cancel), not when `lane.run` returns. The lane does not cancel a timed-out request (`pacing.py` `_on_timeout`, `_late_answer`: it stays in flight at the gateway), and because the request releases the lock, the abandoned request still holds the slot and the next call waits: the peak stays 1 after a timeout, with the lane's 30 s pause on top. A waiting call is bounded by its caller's deadline: the Go call timeout is 25 s (`internal/broker/grpcbroker/dial.go:23`, `defaultCallTimeout`), so a call queued behind another client's call counts its wait toward the 25 s and may end as a timeout (two in a row stop the pass, `stopAfterTimeouts`); with the one Go worker only a second client can do this, and it is named here, not prevented. So two `ListContracts` rpcs, from a re-run overlapping a pass or from any second client, queue and never overlap. Evidence: option-trader ADR 0003:83 and #241 (calls per (underlying, expiry) with strike and right open are safe when serialised, about 5 s each) and #776/#757 (148 issued concurrently made the gateway stop answering). The Go side is serial too: `Run` makes one call at a time (Decision 4, no goroutine), and the scheduler has one worker goroutine (`internal/runner/sched/ticker.go:52-56`), so the evening, pre-open and option-open jobs never overlap on main; dividends and bars share the details lane but are not under the list lock (the jobs are serial, so only a non-Go client could overlap them), so the lock is the second guard, on the side that every list caller shares. New file `list_rpc.py` (under 200 lines): validation, the answer, the proto conversion. A protocol `ListerGateway` in `model.py`, as `AccountGateway` and `ExecutionsGateway`, not a method of `Gateway`, so no fake of `Gateway` breaks. `server.py`'s default `build` is `ListingGateway`. **The edit of `transport.py` is the delegating method and nothing else**: an import, the method on `ContractsServicer` (UNIMPLEMENTED when the gateway has no `list_contracts`; else `self._shared.call("list_contracts", context, list_rpc.answer(...))`) and the word in `WORDS`; at most 15 lines, 771 to at most 786 before `ruff format`; the pull request states the count after formatting, and the entry fails if it is over 800 (`transport.py` is not in `ratchet.json`, which holds only `internal/compute/api.go` at 840, so 800 is its limit; the lock needs no other edit of `transport.py`).
3. **Go side.** `broker.ContractLister` (`ListContracts(ctx, underlying Contract, expiry Day, right, tradingClass string) ([]Contract, error)`, `right` empty for both) beside `Broker`; `Dial` still returns `Broker`; the concrete client implements both. UNIMPLEMENTED from an old service is `broker.ErrNotServed`, declared in `api.go` as a typed constant error (a string type `notServedError` with a one-line `Error` method, and the constant), not a `var`, so the interface file holds a type and a constant and no runtime value; the client returns it inside a Permanent error and `errors.Is` finds it (a comparable constant). The client keeps only contracts of the requested class and returns each contract's multiplier; **the multiplier filter is applied by the job (entry 5)**, which drops a contract whose multiplier differs from the chain's from `ListChains`, because `ListContracts` takes no multiplier. Strike text is the form main already stores: the Python side formats the float strike of a contract detail with `_decimal_text` (`ibgateway.py:143`: "660", "12.5", no trailing zeros), as it does for `ListChains` strikes that `ResolveContract` echoes.
4. **Two new jobs, one runner key each, their own parser and values.**
   - *Jobs.* `option_list_evening` (close+30m, 16:30 ET, order 115: after `option_candidates` 110, before `option_open_resolve` 120) and `option_list_preopen` (open-120m, 07:30 ET, order 185: before the gap's 190). `Plan` returns **one** key: dataset `master.option_list`, subject `evening` or `preopen`. `Run` gets all names in one call (`runkey.go:76`), builds every group, sorts the calls once and stops at one clock: held names, then **priority names** (a `Stored.Watch` entry with a non-empty `BuyPrice`, the owner's price), then the rest; inside a class, nearest expiry, then symbol; a name whose `ListChains` expiry set differs from the stored lists goes first in its class. Priority is bounded by the budget only; held is guaranteed (Decision 9). The jobs are built in entry 6 with `jc.f.listed(groupOptions, build)` like the other options-group jobs (#1709, `What main holds today`): `Plan` reads the stored underlying list at each Plan and the inner job gets its entries as `Stored.Watch` (with `BuyPrice`); `Run` calls `stocks()` on that `Stored.Watch`, so the names of a run are those of the Plan it came from and are not read again at its start; `Plan` returns the one key whatever the names. The verdict sees their `Postcondition`, `Window`, `Schedule` and `RunBound` through the forwards of `listed`.
   - *Parser, window, bound.* `list.go` has its own parser and its own `Schedule()`, `Window()` and `RunBound()`. Evening: window `after_close`, `lateness_hours` 5 (as the resolve), `RunBound` 92 minutes. Pre-open: window `after_close`, lateness 0 (closes 16:00), `RunBound` 31 minutes. A bound is the budget plus 50 s plus slack. The evening bound never binds: the deadline is the window close (21:00) plus the bound, and the 90-minute budget cuts first. The pre-open bound (16:00 + 31 minutes for a 07:30 start) never cuts a normal run either; it matters only for a start after the close. The job's own budget and `stop_time` are the cuts. Without `RunBound` the default 30 minutes would apply.
   - *Budget and stop time.* `list_budget_minutes` 90 (evening) and 30 (pre-open: 07:30 to 08:00). The pre-open job also has `stop_time` = 08:30 ET (initial value), a clock time in code: a window cannot end before the plan at 08:45; the stop time bites only on a late start (a down gateway at 07:30, a long earlier turn).
   - *Postcondition and the end states.* **Session.** A list serves the open of one trading day. `option_list_preopen` of key day D writes session D; `option_list_evening` of key day D writes `Calendar.NextSession(ctx, calendarID, D)` (`clock.Calendar`, `internal/clock/api.go:31`), the day whose open it serves, so the pre-open of D+1 finds the evening's groups listed for D+1 and lists only what is left. Run rows carry the same session. `Postcondition(ctx, day, datasetID, subjectKey)` maps to it: preopen reads session `day`, evening reads `NextSession(day)`. **Definitions.** `listed` of a run row is the number of groups with `listed_session` equal to the session and `listed_pass` equal to this pass, recounted from `master.option_list` (never from a counter, so a crash between the `option_list` row and the run row loses nothing). `expected` is the groups of that name not yet listed for the session when the pass's first run computed them from `ListChains`: set once, never recomputed by a re-run, `null` (unknown) until that name's `ListChains` answers; expected 0 gives reason `none` (every group of the name is already listed for the session) or `no_expiry_in_window`. **`no_expiry_in_window` has one definition, used everywhere in this file: `ListChains` answered with at least one expiry for the name and `ChooseExpiries` kept none of them.** An empty `ListChains` answer (no expiry at all) is not that: it is reason `listchains_failed` with `expected` unknown, because a name with no expiry at all is stale or wrong chain data, not a name with nothing in the window. **The job implements `runner.Postcondition`**: true when, in the run rows of that session and pass (`OptionListStore.ListRuns`, entry 3), some name has `listed` above 0, or some row has reason `none` and every row has reason `none` or `no_expiry_in_window` (the pass had nothing left to list because the evening listed it). **A pass whose every row is `no_expiry_in_window` is false**: nothing was stored for the session by anyone, so the key is not marked present. This agrees with `verdict()` (`runkey.go:175-185`: with `Err` nil and a Postcondition, `Usable` is ignored and the mark is the Postcondition's answer, true meaning the data exists, not that this run wrote it). `Usable` is set to the groups listed, for the log only. **The job computes `Listed`**: after each name it counts the `option_list` rows of the session and pass (`Lists(underlyingID)`) and writes through `PutListRuns` the larger of the stored value and that count, so a stored `Listed` is never lowered (the evening of D overwrites an `option_list` row with session D+1, which would lower a recount of the pre-open of D made after 16:30). **One rule: when this pass has listed nothing and either some name has `expected` above 0 or unknown, or every row has reason `no_expiry_in_window` (the guard), the run ends Retryable for every reason except `stop_time` and `unserved`** (`timeouts`, `listchains_failed` (an empty `ListChains` answer included), `broker_down`, `budget`, `list_max_new`, `all_short`: every group ended `short` or `error`, and the guard case: every name `no_expiry_in_window`); **`unserved` ends Err nil and expires `no_value` on purpose** (main's per-strike path covers the day, and the run rows and the log name it); in every other case `Err` is nil (a pass that listed something, then ended on `budget`, `list_max_new` or two timeouts, except the pre-open case of the next sentence; a pass with a `none` row and every other row `none` or `no_expiry_in_window`; a late start). **Pre-open leftovers: the second Retryable case.** A pre-open run that ends on `budget` or `list_max_new` while some group of its `expected` is still unlisted for the session ends Retryable when the job's clock (`ListDeps` carries the clock; a fake in tests) reads before `stop_time` at the end of the run, and ends Err nil at or after `stop_time`. Checked against `verdict()` and `nextAttempt` (`internal/runner/reconcile`): a run with `Err` set gives no mark whatever the Postcondition says, so the key is not present; `nextAttempt` does not count a Retryable run before the window close (the pre-open window closes at 16:00) and starts the key again on the next turn; the re-run reads its rows first and asks only the groups with no listed row for the session, so the groups the first run listed are not asked again. After `stop_time` the run ends Err nil with the rows as they are (reason `budget` or `list_max_new`, `listed` below `expected`), the Postcondition is true because something was listed, and the day is partial for those groups: design B reads the run rows, not the mark, and names the groups with `listed` below `expected` as not listed for D (they keep their older contracts). The evening never takes this case: a leftover of an evening continues in the pre-open of the next session. A Retryable run before the window close is not counted and is retried each turn, paying its `ListChains` and first calls again (the cost is in Decision 9: `ListChains` for 45 names at 5.0 s is 3.75 minutes, plus the first calls); after the close it expires, visible. **A run that starts after `stop_time` reads the stored rows only and makes no broker call at all (no `ListChains`, no `ListContracts`)**; the Postcondition answer is read before these rows are written, and the `stop_time` rows have `listed` 0; it writes no new reason over a finished row, and for a name with no row of its pass it writes a row with `expected` unknown and reason `stop_time`; it ends Err nil. With something listed by this pass the Postcondition is true; with no row of its pass it is false, so it is one counted done run without a mark, not retried, and the key expires after the close as missing, visible (the pass did not run that day, intended; a late start after an evening that listed everything also reads missing, by the same rule). **Re-run cost:** a run reads its rows first; if every row is `none`, or `none` and `no_expiry_in_window` (a `no_expiry_in_window` row has `expected` 0, so it has no `ListContracts` call either), it returns without any call; the guard case (every row `no_expiry_in_window`) is the one exception, it calls `ListChains` again for every name and writes the `expected` of a name that now has expiries (an empty `expected` may be replaced, a non-empty one never); for a name whose `expected` is known it lists the remaining groups of that set that have no row listed for the session, without `ListChains`; for a name with `expected` unknown it calls `ListChains` first. "No broker call" below means no `ListContracts` call: a first pre-open run still pays `ListChains` for 45 names (Decision 9). Tests, one per case in entry 5: `TestPassListingNothingIsRetryable` (every call times out and `ListChains` always fails at 07:30: Retryable, key not present); `TestCompletePassThenCrashedRerunIsPresentWithoutCalls` (every row `none`, a re-run: Err nil, zero broker calls, key present); `TestLateStartMakesNoCallAndIsNotPresent` (clock 08:31, no row of the pass: Err nil, zero broker calls, every row `stop_time`, key not present, no second run); `TestPartialPassThenRerunAfterStopTimeIsPresent` (an earlier run listed names, a re-run at 08:31: key present); `TestAllShortIsRetryable` (every group answers short or error, nothing stored: Retryable with reason `all_short`, key not present); `TestPreopenStopsAtStopTime` (fake clock 08:29:55, a request of 10 s, one more group: the second request is not made, reason `stop_time`); `TestListedNeverLowered` (a stored `Listed` of 5 and a recount of 3 after the evening overwrote a row: 5 is written back); `TestPreopenListsThenEveningFailsIsRetryable` (the pre-open of D lists, the evening of D fails every call: its rows are for D+1, listed 0, expected above 0, Retryable, key not present); `TestEveningHalfThenPreopenFailsIsRetryable` (the evening of D-1 lists half the groups for D, the pre-open of D fails every call: its expected is the other half, listed 0, Retryable, key not present); `TestEveningListedAllThenPreopenIsPresentWithoutListContracts` (the evening listed everything for D: the pre-open rows are expected 0, reason `none`, key present, no `ListContracts` call); `TestAllNoExpiryIsRetryable` (every name's `ListChains` answers expiries and none is in the window: Err Retryable, key not present, every row `no_expiry_in_window`, no `ListContracts` call; a re-run asks `ListChains` again for every name); `TestNoExpiryWithOneNoneIsPresent` (one row `none`, the others `no_expiry_in_window`: Err nil, key present, no `ListContracts` call); `TestEmptyListChainsIsListchainsFailed` (`ListChains` answers an empty set for a name: reason `listchains_failed`, `expected` unknown, never `no_expiry_in_window`; `TestEveningWritesNextSession` (the evening of key day D stores `listed_session` NextSession(D) and its run rows carry it; the pre-open of D stores D, so the verdict's own case, an evening and a pre-open with one key day, no longer shares a session); `TestRerunAfterCrashBetweenListRowAndRunRowCountsIt` (the run dies after the `option_list` row of a group and before its run row: the re-run recounts and `listed` equals `expected`).
   - *Reconcile re-runs.* A run cut at `reconcileTimeout`, or a crashed lease, runs again the same day (the runner marks a cut run `partial` when `Returned` is above 0 and `abandoned_stop` otherwise; the job sets `Returned` to the groups it listed in that run, and both are re-run). The re-run reads its rows first (above), asks only the (underlying, class, expiry) groups that have no `option_list` row listed for the session (never a group already listed, never the whole name again), skips groups already listed for the session, and before `stop_time` it continues; after it it is the late-start case; `listed` is recounted from the table and `expected` is never recomputed, so a no-op re-run changes neither. A pass that listed something and ended on its budget ends Err nil and the Postcondition is true, so it is present and is not re-run. **What continues it depends on the pass.** After an evening, the pre-open of the next session continues the same session (it lists the groups not yet listed for it). A pre-open that ends on `budget` or `list_max_new` with groups unlisted before `stop_time` is not present: it ends Retryable and the next turn re-runs it for those groups only (Decision 4, second Retryable case). After `stop_time` it ends Err nil and the day is partial: the next pass is the evening of D, which writes session D+1, so those groups stay on their older contracts for D, and B reads the rows (`budget` or `list_max_new`, `listed` below `expected`), not the mark.
5. **Until pyside is restarted.** The first `ErrNotServed` ends the pass with `Err` nil (not an error kind): every name's run row gets reason `unserved`, the log line says `list_unserved: the pyside service has not been restarted`, the Postcondition is false, so it is one counted done run without a mark and the key expires `no_value` after the close, on purpose: the list passes did not run that day, and main's per-strike jobs, which run at their own slots as today, cover it. The ledger keeps no names and `safeErrText` cuts at 300 bytes, so names live in the run rows and the job's summary line (`Log`). The owner restarts pyside (Rollout).
6. **The writer and the records.**
   - *Writer.* Its own function in `list.go` (`listed.go`'s `store` needs a `keyRun`, `resolveJob` and `candidate`): per contract `Instruments.ResolveInstrument` (instrument from `osiOf`, same package) and `Options.PutOption` (`ListDeps` embeds `Stored`, which has both). **The strike is stored as the broker gave it, unchanged, as `store()` does (`listed.go:419`)**; **matching uses `strikeKey`** (`refKey`, `listed.go:343`), never the stored text. "Already stored" is one `ListOptions` read per name, matched on (right, strike by `strikeKey`, expiry, class); only new contracts are written, and the marks of what it lists are removed.
   - *Bounds.* Writes run inside the budget clock and stop at `list_max_new` = 60000 contracts per run (initial; a re-run has its own count, so a pre-open retry is not blocked by the cap its first run hit): the first pass on an empty store lists about 170 groups of 200 to 500 contracts (both rights), 34 to 85 thousand, each a `ResolveInstrument` and a `PutOption` of unmeasured time, so the cap can bind in the typical case; after an evening the pre-open of the next session continues the same session, and a pre-open is retried before `stop_time` and leaves the rest only after it (Decision 4).
   - *Real list.* A list is real when the call succeeds, both rights are present, it is not empty for an expiry `ListChains` lists, and it holds at least half (`list_min_ratio` 0.5) of the stored contracts of that group; otherwise the group keeps its older contracts and the outcome is `short` or `error`.
   - *Tables* in migration `0034_option_list.sql`. **`master.option_list`**, one row per (underlying, expiry, class) asked: `listed_at`, `listed_session` (the session of Decision 4: the trading day whose open the list serves), `listed_pass` (`evening` or `preopen`, the pass that listed it), `count`, `tried_at`, `outcome` (`listed`, `short`, `error`). **`master.option_list_run`**, one row per (session, pass, underlying): `expected` (the groups left to list when this pass's first run computed them, a list of `expiry|class`, `null` until the name's `ListChains` answers), `listed` (groups with `listed_session` equal to the session and `listed_pass` equal to the pass, recounted from `master.option_list`), `reason` (`not_finished`, `none`, `no_expiry_in_window`, `listchains_failed`, `budget`, `stop_time`, `timeouts`, `unserved`, `broker_down`, `list_max_new`, `all_short`), `updated_at`. Rows are written at pass start with `expected` null and reason `not_finished`, and updated per name as it ends, with writes that survive a cancelled context (`context.WithoutCancel`), so a crash or a cut leaves rows that read not finished; null counts as not none. `expected` is set once: a non-empty `expected` is never replaced, null is replaced by any write, and an empty one only by the guard re-run of Decision 4; `reason` is the latest, but **a re-run writes a reason only when `listed` is below `expected`**, so a no-op re-run never replaces `none` on a complete row; expected 0 is `none`, or `no_expiry_in_window` (the one definition of Decision 4: `ListChains` answered with expiries and none is in the window; an empty answer is `listchains_failed`). **A watched US stock with no row for a session and pass is a gap** (the pass did not reach it or died before writing; the run writes a row for every name of the stocks of its `Stored.Watch`, the names of the Plan it came from, which `stocks()` reads once at the start of `Run`). **What B may rely on:** a contract row is current for an open when `listed_session` equals that open's day; the evening of D-1 and the pre-open of D both write D, and a group listed by either is skipped by the later pass of the same session. B reads both tables.
   - *Order of writes.* Contracts first, then the `option_list` row (with `listed_session` and `listed_pass`), then the run row: a failure between leaves the group listed by this pass and the re-run skips it, and recounts it into `listed` from the table. `short` and `error` update `tried_at` and `outcome` and keep `listed_at`, `listed_session` and `listed_pass`; a second `short` on a later session is accepted. A group "listed for a session" is `listed_session` equal to that session, never `resolved_at`. Age is in trading sessions: `NextSession` is the first session strictly after a day, so age is a loop of at most 5 calls. Role `ot_w_option_open` (INSERT, UPDATE, SELECT on both; no page role); B's migration is numbered after 0034.
7. **Classes and rights; one request per (underlying, class, expiry).** Class per stock: the symbol's own class; adjusted classes (`2SPY`, `2NVDA` in `raw.txt`; multiplier 100, so a multiplier filter would not drop them) are never asked and B names them as left out. **The right is always left empty**: SPY 20261218 unset gave 516 contracts (258 C, 258 P) in 0.84 s, against 4.49 s for the puts alone and 4.98 s for the calls; strike sets equal, con_ids distinct, the unset answer is their union; a contract is matched on (right, con_id). So calls of every name cost nothing extra: both rights are stored, the plan uses puts for non-held names and calls for held ones as today, and there is no per-right key and no carve-out for held calls. It is one sample of the unset case: an answer with only one right for an expiry is `error` and the group keeps its older contracts. A month string (`202612`) returns every expiry of the month (SPY: 5 expiries, 1034 puts, 15.6 s, the sum of five calls), gains nothing and comes near the 20 s timeout: **requests stay per expiry**. Latency is 1 to 7 s whatever the rows (QQQ daily 161 puts 6.5 s, QQQ monthly 352 puts 7.2 s); 5.0 s stays the planning figure.
8. **Expiry choice, `ChooseExpiries`** (a pure function in `list.go`; B applies it in the plan so a list is never taken for an expiry the plan drops). It keeps every expiry that `ListChains` lists for the name whose calendar DTE is in [`dte_min`, `dte_max`] = [21, 45], inclusive, counted in calendar days from the session day the list serves (Decision 4: the evening of D counts from `NextSession(D)`, the pre-open of D from D). Owner decision 2026-11-11 (ask optdesk-2852): the expiries a seller uses are those 20 to 45 days out, as option-trader does. The words "20 to 45" are read as option-trader's rule that the owner named, so the rule built is [21, 45]: an expiry 20 days out is dropped, one 21 days out kept (the table test of entry 5). Its rule for US expiries is DTE 21 to 45 calendar days, ordered nearest to 30 DTE (option-trader `snapshots/params/plan_v4.toml:1-12`, ADR 0003:81, #240). There is no count cap and no monthly rule: a weekly name has about 4 expiries in the window, a monthly-only name 1 or 2, a daily-expiry name (SPY, QQQ, IWM) about 17. The order inside a name is nearest to DTE 30, then the earlier expiry (an order, not a cut); `ChooseExpiries` returns it in that order and a test pins it (entry 5). The call sort of Decision 4 stays by nearest expiry across names; this order is what B uses to rank. **The strike band (k = 1.5 sigma, option-trader `plan.py`) is not applied here:** B applies it when it chooses quotes, so a listing takes every strike of a chosen expiry. **A name with no expiry in the window lists none:** its run row has `expected` 0 and reason `no_expiry_in_window` (the definition of Decision 4: `ListChains` answered with expiries and `ChooseExpiries` kept none; distinct from `none`, a name whose groups are all listed; an empty `ListChains` answer is `listchains_failed`). The Postcondition counts it as `none` only when another row is `none` or has `listed` above 0; a pass where every name is `no_expiry_in_window` is Retryable and not present (the guard of Decision 4). Held contracts of expiries outside the window are not lost (the held path unions them); watched ones are named in B. `dte_min` and `dte_max` are tomls keys (entry 5).
9. **Arithmetic at 5.0 s, per (underlying, class, expiry), with the window of Decision 8.** Inputs are assumptions, none measured: 45 US stocks, 12 held; 5 daily-expiry names (SPY, QQQ, IWM and the like) at **17 expiries each** (the weekdays of a 25-day window); of the other 40, **10 weekly names at 4 expiries and 30 monthly-only names at 1.5 on average**. Typical: 85 + 40 + 45 = **170 requests, 14.2 minutes** at 5.0 s (20.7 minutes at 7.3 s). Worst, all 40 others weekly: 85 + 160 = 245 requests, 20.4 minutes (29.8 at 7.3 s). The 90-minute evening pass holds both with a wide margin. The budget is checked between calls, so a lane timeout (50 s) overshoots it by that much. These are IB calls only; Decision 6 states the writes. Pre-open: `ListChains` for 45 names as 5.0 s calls is 3.75 minutes [unmeasured], leaving 26.25 minutes = **315 requests** inside the 30-minute budget: the typical 170 are listed for the session by 07:48 when the evening listed nothing for it, the worst 245 by 07:54; when the evening listed some, the pre-open pays `ListChains` for all 45 names and lists only the rest. **At 7.3 s the pre-open holds the typical case** (`ListChains` 5.5 minutes plus 20.7 = 26.2 of 30) **but not the worst: 24.5 minutes leave 201 of 245 requests**, so after an evening that listed nothing a worst-case pre-open ends on its budget with 44 of 245 groups unlisted: the run ends Retryable (the clock reads about 08:00, before `stop_time`), the next turn re-runs it, asks only those 44 groups (3.7 minutes at 7.3 s, no `ListChains`) and they are listed for D by about 08:10; only a retry that also ends after 08:30 leaves some of them on their older contracts for D, with the rows saying so (Decision 4). The evening pass is the main one and has the room. Held is guaranteed: if all five daily-expiry names are held with 7 weekly held names, 5 x 17 + 7 x 4 = 113 requests = 9.4 minutes at 5.0 s (the 12 held names at 4 expiries each would be 48 requests, 4 minutes). Priority has no bound but the budget. **The arithmetic assumes serial calls (in flight 1, Decision 2): the times above are sums, never divided by a lane width.** Two consecutive timeouts stop the pass (`stopAfterTimeouts`, `listed.go:35`; reason `timeouts`, Decision 6).
10. **Collisions on the one worker, named.** *Pre-open:* 07:30 to 08:00 by budget, at most 08:01 (one 50 s timeout), so it ends before `fundamentals` and the gap at 08:00 and the plan at 08:45. If the gateway is not up at 07:30 (probe 3 pending) the key is retried each turn and never starts after 08:30 (Decision 4); a pre-open retry before 08:30 and a late run delay `fundamentals` and the gap (budget 40 minutes from their start, unchanged on main), so the gap can end near 09:10 and the plan waits behind it: the cost of a late gateway, bounded by the stop time. *Evening:* `option_eod` is cut near 16:16, so the pass starts at 16:30 and runs to 18:00 at most, ahead of `option_ledger` and `option_open_resolve` (17:00); typically it ends at 16:45 and nothing waits; in the worst case they start up to an hour late and the JP plan at 18:15 ET waits behind them (a delay, not a failure). A turn beyond `reconcileTimeout` (2 h) is cut and the run is `partial`.
11. **Probes pending, and what holds without them.** Probe 3 (gateway at 06:00 to 08:00 ET): default 07:30 with the retry and stop time of Decision 4; nothing claims the gateway answers early. Probe 5 (daily-expiry counts): the arithmetic uses the 17 expiries of the window as an assumption. Probes 6 and the QQQ and SPX parts of 5 are done (Decision 7). An empty answer for an expiry `ListChains` lists is `error`, recorded and named. Probes 7 and 8 belong to B.
