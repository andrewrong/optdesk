# Single runner: only the scheduler runs jobs; restart closes running rows

Author: the optdesk window (draft)
Owner approved: (pending)
Date: 2026-11-12
Source: owner 2026-11-12 15:39Z (optdesk-3414): only the scheduler process runs jobs; `ot run-once` and `ot backfill` only enqueue a console request; on start the scheduler closes every `running` row as failed `restart`. The removal of the database lease inside the runner is a follow-up design (Left out); this design leaves the runner's lease logic unchanged.

## Goal

Today three processes can run a job: the scheduler, `ot run-once` (`reconcileDay`, `Reconcile`) and `ot backfill` (`Backfill`), so `ops.run_lease` (`ledger.go` `acquireSQL`, `reconcile.go` `leaseTTL`, `holdLease`, `backfillOwner`) and the `LeaseUntil` liveness of `ops.capture_run` rows (`runkey.go`, `nextAttempt`, `closeExpired`, `sched/gaps.go`) keep them apart, and a killed run blocks for `leaseTTL`. After this design one process runs jobs and the two commands post a request to the job console queue and may wait for its outcome. The runner keeps its lease logic as it is: `Reconcile` and `Backfill` still hold `ops.run_lease` and a `running` row is still live while its `lease_until` has not passed. A start of the scheduler closes every `running` row of the previous process at once as `crashed` (Decisions 4 and 5), so a killed run no longer waits for its lease to lapse. Same-job overlap stays refused by the in-process per-job try-lock (#1915, `console-run-lock.md` Decision 2).

## Modules

- store (`internal/store/**`): a new small interface `store.RunCloser` (`CloseRunning`), implemented by the ops ledger; the write of a run no longer reopens a closed row or replaces its finish; `ops.capture_run` and `ops.run_lease` keep their shape (no migration).
- runner (`internal/runner/**`): `DayPlanner.PlanDay` (plan only); `reconcile.go`, `backfill.go`, `backfill_force.go`, `runkey.go` and `sched/gaps.go` are unchanged except the new method.
- ot (`cmd/**`): the scheduler closes `running` rows after it holds the fence; the console host plans an unplanned day; `run-once` and `backfill` are enqueue wrappers.
- docs (`docs/**`): the deploy runbook and `contracts/runner.md` text (entry 7); the `cmd/ot` tests that assert the wiring move to test helpers (entry 5).

No row of `docs/design/modules.md` changes.

## Decisions

1. Only `ot scheduler` runs jobs. `ot serve` posts, the scheduler's console claims. `run-once` without `--dry-run` and `backfill` build no wiring, open no ledger and call no `Reconcile` or `Backfill` (grep of `cmd/ot`: `reconcileDay` in `runonce.go` and `backfill` in `backfill.go` are the only non-console callers; `--dry-run` writes nothing, takes no lease and stays: `runDryRun` dials the broker into memory and never calls `withWiring`, so it builds no wiring today and `dryrun_test.go` keeps its calls of `runOnce`, apart from the one `--job` check named in entry 6(l)). The wiring (`withWiring`, `wiring.runnable`, `printOutcomes`) stays for `ot scheduler`; the tests that assert it reach it through the test helpers of entry 5, not through `run-once` or `backfill`.
2. A wrapper posts through `jobrequest.Poster` (the `ot_w_settings` role DSN, as `jobconsole_post.go`): `backfill --day D --job J [--force]` posts `{J, D, Force}` and `backfill --day D` without `--job` posts one request per job of the console job list, as `run-once` does (today it backfills every job of the day, `backfill.go`); `--force` is a new flag of `backfill`, not in `backfill.go` now, and `run-once` has none (`Force` false); `run-once [--day D] [--job J]` posts one request per job of the console job list (`jobconsole_jobs.go`) with kind `any_day` or `today_only` when `--job` is absent; `listed_only` jobs are skipped, and a `today_only` job is skipped when D is not today in its zone (the post would be refused). With `--job` the post is made and the page's own refusal is printed. `--dataset` is removed (a request has no dataset). `--wait` polls `Reader.Get` on the injected clock until the state is not queued or running, prints the key lines and exits non-zero for `failed`, `refused` and `interrupted`; without it the command prints the request id and the `EnqueueOutcome` and exits. `--wait` gives up after `--timeout` (default 120 s on the injected clock), prints `request N is still queued: the console may be off (no consumer is running)` and exits non-zero; the console is off when `openConsoleHost` returns nil, and nothing then claims a request.
3. The lease stays in the runner. `holdLease`, `leaseTTL`, `backfillOwner`, the 30 s renewal and the runner's calls of `Acquire`, `Release`, `RenewLease` are not changed. Only the `cmd/ot` callers go (`run-once` and `backfill` no longer run a job). The in-process try-lock of #1915 stays the per-job exclusion beside the lease. Removing the lease from the runner is a follow-up design (Left out).
4. Liveness of a `running` row is unchanged: it is live while `lease_until` has not passed, and a lapsed one is closed `crashed` by `nextAttempt`, `closeExpired` and `sched/gaps.go` as today. The restart guarantee is `CloseRunning(ctx, now, "crashed")` after the fence is held (Decision 5): it closes every `running` row the previous process left, whatever its `lease_until`, so the new process does not wait for a lease to lapse. Whether the old process's `ops.run_lease` also blocks the new one: it does not. `Reconcile` (the scheduler's only holder in a one-process world) takes the lease under the constant owner `runner` (`reconcile.go` `owner`), and `acquireSQL` takes a lease whose owner is the caller's, so the new process takes over the dead process's `runner` lease at once; the scheduler's console path (`BackfillWith`) takes no lease. The only other owners are `backfill:<hex>` of an `ot backfill` run by an old binary, which expire within `leaseTTL`, are not the scheduler's concern, and are not deleted (deleting would remove the guard against that old binary). So `CloseRunning` touches `ops.capture_run` only.
5. Restart closes at once, as crashed. After the fence is held and before the ticker's first turn, `cmd/ot/scheduler.go` asserts the ops ledger to `store.RunCloser` and calls `CloseRunning(ctx, now, "crashed")` and logs the count. The reason is `crashed`, the one the lapsed-lease path writes, so `isCrash`, `nextAttempt`, `closeRow` and `sched/gaps.go` treat the row as they do now (a crash: not counted toward the two-run cap, a new attempt is planned). A deploy mid-run therefore counts toward `crashBrake` (3) exactly as a lapsed lease does today; nothing is added. If the ledger is not a `RunCloser` or `CloseRunning` returns an error the scheduler does not start ticking: `schedulerCmd` returns the error and exits non-zero (the keeper restarts it).
6. The previous process is gone when the fence is held, with the one exception below. The fence is `pg_try_advisory_lock(fenceKey)` on one dedicated connection (`ops.OpenFence`); a session advisory lock is freed when the backend ends the session: at once when the client process exits (the socket closes and the backend sees EOF), or when the server terminates the backend (`pg_terminate_backend`, server restart, keepalive timeout) with the client still alive. The service is restarted by crew (`docs/deploy/scheduler.md`: the keeper starts the new process after the old one exits; the old one drains on SIGTERM or exits 75), and the repository holds no code that starts a second process before the first has exited, so no grace period is added: a start while the old process still holds its connection does not get the lock: `lockFence` retries every `lockEvery` for `lockWait` (60 s) and then exits with the error, which is the wait for the old process to end. For the exception (backend ended, old client alive for the moment before `fence.Lost()` reaches `watchFence`) the old process may insert a `running` row after the new process ran `CloseRunning`. No guard is put on the insert: that row belongs to no run of the new process and carries the old process's `lease_until`, so the unchanged lease path closes it as crashed once that lease has lapsed (at most `leaseTTL`), as today. The final write of the old run is conditional: `recordRunSQL` ends its `ON CONFLICT ... DO UPDATE` with a guard (entry 3(b)), so a row closed by `CloseRunning` or `markCrashed` is never reopened or given a later finish by the old writer, while the deliberate rewrite of a closed row by `expireIfClosed` (same status, same finish, a new `ReasonCode`) still goes through (entry 3(b)). A file lock, a pid file or an insert guard on `pg_locks` was not chosen: the first two are per host and add a file, the guard needs the backend pid to travel from the fence to the ledger, which `cmd/ot` opens apart.
7. A day nobody planned. A console request is `BackfillWith`, which needs a stored plan and else is refused `no_plan`; `run-once` was `Reconcile`, which plans and also runs every due job and moves the cursor. The console must do only the plan, because its claim covers one job and `Reconcile` runs every due job under the ticker's run lease. So there is a plan-only method, `runner.DayPlanner.PlanDay` (entry 2 declares it, entry 4 implements it: plan, `PutExpected`, windows; no run, no cursor). The console host receives the ops ledger as a new constructor argument: `newConsoleHost(q, syncer, ledger, clk, log)` with `ledger store.OpsLedger`, and `openConsoleHost` (`cmd/ot/jobconsole_sched.go`), which already has `ops`, passes it. The console host (`cmd/ot/jobconsole_turn.go`, entry 6), before it runs a claimed request, reads `OpsLedger.Expected(day)` and, when it is empty and the day is after `OpsLedger.Cursor` (an empty `Cursor.Day`, no cursor yet, counts as before the day, so the console plans it; the case `run-once` accepted; it refused a day at or before the cursor), asserts its `ForceBackfiller` to `runner.DayPlanner` and calls `PlanDay(ctx, day)`; then it runs the one request under the lock of its job. Without a `DayPlanner`, or for a day at or before the cursor, the `no_plan` refusal stands, as `ot backfill` is today. The cursor moves only by the ticker's `Reconcile`.
8. A run in flight when the fence is lost stops by `cancelConsole()` as today; its row stays `running` and is closed by the next start.
9. Deploy order. Code deploys on merge and no migration is added. Entry 5 (the tests keep their wiring through a test helper) has no order and lands before entry 6. Entry 6 (wrappers, plan-only console, close at start) needs entries 1, 3, 4 and 5. #1915 (reconcile files) is ordered before 4, #1918 (`cmd/ot` console files, `scheduler.go`) before 6; #1919 (jobs) does not overlap.
