## Decisions

1. Shape (plan P2, P6; owner S2). The three data tables stay plain tables with a primary key on the data's own identity; no hypertable. Two small by-key tables hold the daily answer of a source (Decision 5). Decimals stay `text`; a pattern check is added where none exists (Decision 7). Every table gets `updated_at timestamptz NOT NULL DEFAULT now()` and `written_by text NOT NULL DEFAULT ''` appended; `received_at` stays the time of the first insert.
2. Earnings key (plan section 3, owner S2). `obs.earnings_date` becomes one row per `(issuer, period_key)`. `period_key date NOT NULL` is the `fiscal_period_end` only when the source is `alphavantage` (it names the quarter), and the `report_date` for every other source (`jquants`, whose `FYE` is the year end and would make four reports of a year one row, and `owner`). Columns kept: `issuer` (the watch-list text `cik:<10 digits>` or `edinet:<code>`), `symbol`, `market`, `report_date NOT NULL`, `fiscal_period_end` (stored as the source gives it), `time_of_day`, `estimate`, `source`, `received_at`; `observed_on`, `attempt`, `status` and `error_code` leave the table (they describe a day's answer, Decision 5). A moved date of an Alpha Vantage quarter replaces the stored one; a moved date of a J-Quants or owner report is a second row and the old one stays (the readers take a listed date before the day as `Previous`). The job still stores only the earliest listing on or after the day per company (Left out).
3. Dividend key (plan section 3). `obs.dividend_expectation` becomes one row per `(instrument_id, ex_date)`: `instrument_id bigint NOT NULL REFERENCES master.instrument` (plan: "instrument_id to bigint with a foreign key"), `ex_date date`, `issuer`, `amount text` (the next amount per share, pattern check), `currency`, `source` (`ibkr_tick_456`), the three bookkeeping columns. Only a `present` projection is a row; a moved ex-date is a second row and the old row stays (no DELETE, Decision 8). `past_12m` and `next_12m` are figures of the capture day, not of an ex-date, and no reader reads them (`git grep Past12M`: only the job and the store); they move to the answer table.
4. Facts (plan section 3: "obs.fundamental_fact (DO UPDATE)"). The key stays the eight columns including `doc_id`: the facts of a filing are replaced by the same filing read again, and a restating filing stays a second row, which `FactsFiledBy` needs for "as filed by that day". `InsertFacts` stays; a new `UpsertFacts` does `INSERT ... ON CONFLICT (the eight columns) DO UPDATE SET currency, value, form, filed, retrieved_at, raw_sha256, updated_at = now(), written_by WHERE (stored currency, value, form, filed, raw_sha256) IS DISTINCT FROM (new)`; `retrieved_at` is not compared, so an equal fact is not rewritten.
5. The answer of a day (needed by `Postcondition`, the gate's row day and the page states, Today). `obs.earnings_check (issuer, observed_on, market, symbol, status, error_code, source, period_key date NULL, received_at, updated_at, written_by)`, key `(issuer, observed_on)`, and `obs.dividend_check (instrument_id bigint, session_day, issuer, status, error_code, source, currency, ex_date date NULL, past_12m, next_12m, received_at, updated_at, written_by)`, key `(instrument_id, session_day)`. Same enums and checks as today (`listed|absent|unsupported|error`, `present|no_value|unsupported|error`; the value status needs its date; `unsupported` needs source `none`), a composite foreign key from `(issuer, period_key)` to the earnings row and from `(instrument_id, ex_date)` to the dividend row (a NULL part passes). `dividend_check.instrument_id` has no foreign key to `master.instrument`: the job keys a `resolve_failed` answer by the con id (`dividendcapture/run.go:190,230`). A re-run of a day overwrites that day's answer (this ends the attempt rows). Rule "a missing value never replaces a present one": rank error 1, absent, no_value and unsupported 2, listed and present 3; an upsert replaces a stored answer only when its rank is not lower and the columns differ, so an `error` never replaces an answer and a later `listed` replaces an `error`. A run for a day before the date of the clock (a replay, Decision 11) never replaces a stored answer: it uses the `Replay` methods of the interface, which upsert the data rows and write an answer only where none is stored for its key, so a forced past day cannot falsify what the gates read as "known on that day". The two check tables are an addition to plan section 3 (which lists only the keys of the three tables as changed); they are the cost of keeping `Postcondition`, the gate's row day and the page states, and the pg tests read both views as `ot_ro_pages`.
6. Views (plan section 3: "every rd view keeps its name and columns"). `rd.earnings_date_r1` and `rd.dividend_expectation_r1` are changed with `CREATE OR REPLACE VIEW`, the same thirteen columns and types each: the check table left joined to the data table on the foreign key, `attempt` the constant 1, `received_at` the check row's `updated_at`, the date columns and amounts from the joined row (NULL when none), `time_of_day` `''` when none. They keep owner `ot_owner` and the grants to `ot_ro_pages` and `ot_w_events`; a drop would lose them. `store.EarningsDateReader`, `dividend.Reader`, every record in `contracts` and every page and gate are unchanged. A listed answer shows the current date of its row: a moved date shows on the answers of earlier days too.
7. Decimals (plan P6 item 3). Pattern checks `^-?[0-9]+(\.[0-9]+)?$` on `amount`, `past_12m`, `next_12m` and `estimate` (NULL passes) and on `fundamental_fact.value` with the exponent form of a JSON number allowed, the last added `NOT VALID` so no stored row blocks the migration. The window counts the stored rows that violate it after the migration (`SELECT count(*) FROM obs.fundamental_fact WHERE value !~ '<the pattern>'`) and a later issue validates the constraint when the count is 0 (Left out); until then a new value outside the pattern is refused as a Permanent error that fails that call of `fundamentals`. Moving them to `numeric` is not done (Left out).
8. Roles. `ot_w_events` keeps table INSERT on `obs.earnings_date` and `obs.dividend_expectation` and gets, on those two and on the two check tables, INSERT, `UPDATE` of the non-key columns and `SELECT` of every column the statements name: the key, the compared columns and the columns read through `EXCLUDED` (no role holds table SELECT, Today; `ON CONFLICT ... DO UPDATE` reading `EXCLUDED.col` needs SELECT on `col`). `ot_w_fundamental` gets the same on `obs.fundamental_fact`: `UPDATE (currency, value, form, filed, retrieved_at, raw_sha256, updated_at, written_by)` and `SELECT` of the eight key columns, those five and `retrieved_at` (14 columns of the table). No DELETE, no TRUNCATE, no UPDATE of a key. `ot_ro_pages` reads the two views and `rd.fundamental_fact_r1` as before.
9. The write (as FX Decision 4). Per row, `INSERT ... ON CONFLICT (key) DO UPDATE SET ..., updated_at = now(), written_by WHERE (stored compared columns) IS DISTINCT FROM (new ones) RETURNING <key>`, one transaction per call, data row before its answer row (the foreign key), a key twice in a call applied in order. A missing value never replaces a present one in the optional columns either: in every `DO UPDATE` of the earnings row `estimate`, `time_of_day` and `fiscal_period_end` are `COALESCE(NULLIF(new, ''), stored)`, and in the answer rows `past_12m`, `next_12m` likewise; the comparison runs on that result, so an Alpha Vantage run without an estimate neither blanks nor rewrites a row. The facts have no optional column. Compared columns: earnings row `symbol, market, report_date, fiscal_period_end, time_of_day, estimate, source`; dividend row `issuer, amount, currency, source`; the answers `status, error_code, source, period_key (ex_date), market, symbol (issuer, currency, past_12m, next_12m)` under the rank rule of Decision 5. Counts: `Written` (a row inserted or replaced) and `Unchanged` per input row; an empty list makes no call. Mapping: `UpsertEarnings(rows []contracts.EarningsDate)`: a `listed` row writes the data row (`period_key` as Decision 2) and its answer; any other status only the answer; `Attempt` is ignored. `UpsertDividends` likewise for `present`.

## Interface

One interface change, entry 1, the new declarations-only package `internal/store/fundkey` (`api.go`, `api_test.go`; additive, nothing in `internal/store/api.go` or `internal/store/dividend` changes):

    // WriteCount is what one upsert call did to the rows it was given: Written rows were inserted or replaced
    // (their data row or their answer row), Unchanged rows were equal to what is stored.
    type WriteCount struct{ Written, Unchanged int }

    // EarningsUpserter stores earnings answers by key: a listed row by (issuer, period key), every row's answer by
    // (issuer, observed day). A differing row replaces the stored one, an equal row changes nothing, an error never
    // replaces an answer, a missing optional value never replaces a present one, Attempt is ignored. writtenBy names
    // the run. Optional method of the value store.OpenEarningsDateStoreFunc returns; the job asserts it at Run.
    type EarningsUpserter interface {
        UpsertEarnings(ctx context.Context, rows []contracts.EarningsDate, writtenBy string) (WriteCount, error)
        // ReplayEarnings is UpsertEarnings for a run of a past day: the data rows are upserted, an answer row is
        // written only where none is stored for its key.
        ReplayEarnings(ctx context.Context, rows []contracts.EarningsDate, writtenBy string) (WriteCount, error)
    }

    // DividendUpserter stores dividend answers: a present row by (instrument, ex-date), every row's answer by
    // (instrument, session day), under the same rules, with the same replay method. Optional method of the value
    // dividend.OpenFunc returns.
    type DividendUpserter interface {
        UpsertDividends(ctx context.Context, rows []contracts.DividendExpectation, writtenBy string) (WriteCount, error)
        ReplayDividends(ctx context.Context, rows []contracts.DividendExpectation, writtenBy string) (WriteCount, error)
    }

    // FactUpserter stores filed facts by their key: a fact read differently replaces the stored one. Optional method
    // of the value store.OpenFactStoreFunc returns.
    type FactUpserter interface {
        UpsertFacts(ctx context.Context, rows []contracts.FundamentalFact, writtenBy string) (WriteCount, error)
    }

## Doubts

1. Issuer text or issuer id: decided in Decision 16 (text). The owner or advisor may still want the id; then entry 2 gains the column and a join and every entry is ordered after the interface entry of `instrument-company.md`.
2. The two check tables are an addition to plan section 3 (Decision 5). The alternative, a `seen_on` column that moves on every run on the data row, breaks "an equal row is kept"; a design without answers breaks the runner's postcondition.
3. A source that stops listing a report leaves its row in place (a missing value never replaces a present one); a company that reports and is not yet listed for the next period shows the old date as past, which the readers already treat as such (`Previous`, `published`). An Alpha Vantage quarter whose `fiscalDateEnding` the vendor sometimes omits flips between two keys, so it is two rows.
4. A past-day run of `earnings_refresh` or `dividend_capture` stores the vendor's current answer: the data rows (by period and ex-date) are repaired, and an answer row is written only where the day has none (replay); it cannot recover what a vendor said on that day. This is the "dev mode, any job runs when triggered" rule, not a claim of history.
5. `fundamental_fact.value` pattern: SEC's own number literals (`e.Val.String()` at `internal/sources/sec/mapping.go:126`) were not checked for forms outside plain integers, decimals and exponents; the check is `NOT VALID` and a Permanent refusal of a new odd value fails the job's call (visible, not silent).
6. No database was available: foreign keys on the new columns, the composite key with a NULL part, grants for `ON CONFLICT ... DO UPDATE` and the view replacement are written from the PostgreSQL rules; the `pg` tests are the check.
7. `0046` assumes `0043`, `0044` and `0045` land first; another migration that lands first moves the number and the test lists of entries 3 and 4. The Order lines are prose; nothing the merge gate reads stops a store entry of 3 to 9 from merging before the window ran `0046`.
8. `fundamentals` carried the force reason "quota" although it fetches from SEC; removing it is intended; whether SEC needs a pacing guard on forced runs is not checked.
9.
