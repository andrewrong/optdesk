# Scheduler per job: a job never waits for another job, one run per job id; a run that goes long is seen

Author: the optdesk window (draft)
Owner approved: (pending)
Date: 2026-11-19
Source: owner ask optdesk-5294 (2026-11-19): "调度器一次只跑一个任务，你确定这样合理吗？？？" Correction the same day: "相同的任务，同一时间跑一个，不是一个调度器一次只能跑一个". Second ask: "对于一个任务跑了很久这样的事情，也需要进行观察，这明显就不是很对啊". Rules kept: dev mode, any job runs when triggered, the only guard is one run per job id (2026-11-12); every job runnable alone and idempotent (2026-11-12).
Status: draft. Read on origin/main only. "[unverified]" marks a claim not checked in code, docs or a probe.

The file keeps its name `scheduler-per-job.md`; there are no lanes. The first draft keyed workers by data source, the owner dropped that: the unit is the job, not the source. Source pacing stays where it is (Decision 9).

## What you see

- A job never waits for another job. A slow `iv_history` repair of an old day does not delay the slot of any other job, today's keys of other jobs, or another repair. Two runs of the same job do not overlap, and the console says so (next lines).
- Guarantee, stated exactly: inside `ot serve`, one run per job id at a time, whoever starts it (scheduler or console). `ot run-once` is outside it: it is kept out by the run fence, which the serve instance holds (`ops.run_lease` is one global row, `migrations/0003_ops_ledger.sql`; `reconcile.go` `holdLease`).
- A console request for a job that is running is never silently queued. Its line says "已在运行，自 14:02 UTC" (English glossed beside: "already running, since 14:02 UTC"); it starts the moment the job is free and can be withdrawn. No expiry (`docs/design/job-console.md` Decision 8).
- The job console lists, above the request form, "Running now": one line per running job: job, "started 14:02 UTC", "keys 12 / 40", the key it is on. `/data-health` shows the same lines above the grid.
- A run that goes well past its usual time is seen three ways, and only seen: the Chinese words "跑了 62 分钟，平常 3 分钟" beside its line; one Telegram notice per run through the existing notifier; one log line `job_run_slow` that the dispatcher patrol reads. Nothing stops, cancels or refuses a slow job (owner rule: dev mode, no time guards). A job with fewer than 5 closed runs shows "没有历史" instead of a usual time.
- What this does not fix: a silent gateway still stalls every job that uses it, because the pyside `DetailsLane` is built once per gateway and shared (Decision 9). The slow notice is how he learns it. This design is not the fix of the 2026-11-19 stall; the 3-keys stop of the bug draft is.
- After a restart a run that was cut shows as before (`ordered_stop` / `partial`, `docs/design/restart-resume.md`); the job-run row that was open is closed `cut`, which counts toward no usual time; the first pass after the start launches the missing keys of every job at once.

The 2026-11-19 stall (about forty `iv_history` keys, each ending after 20 to 30 s with the gateway not answering) may have waited at the gateway, not in the scheduler: `DetailsLane` takes 1 to 5 requests in flight and times one out after 20 s (`pyside/src/optdesk/ibkr/pacing.py`), so forty silent keys fill it for a long time, and the bars repair and the candidate run use the same connection. ## Decisions

1. **The unit is the job id, and the lock is the guard.** Every job may run at the same time as any other. The only guard is the existing in-memory try-lock per job id, one set shared by the scheduled path, the console and a swapped reconciler (`console-run-lock` Decision 2). There is no unique index on open `ops.job_run` rows: a crash or a deploy kill leaves a row open, and an index would then refuse that job for ever. The row only records. At start-up `CloseOpen` closes every open row as `cut` (the start code that already closes `running` runs, `store.RunCloser`, which touches `ops.capture_run` only); a `cut` row counts toward nothing. Test in pg: a row left open is closed `cut` and a new `Start` for the same job succeeds.
2. **A pass is a launch, not a barrier.** The ticker prefers `DetachedReconciler`. `ReconcileDetached` does what `Reconcile` does up to `runJobs`: walk the days, plan, decide the due keys. It then calls `spawn(job, run)` for each due job whose lock is free and returns. The run takes the lock inside the spawn (so a second pass cannot double-start), runs the keys of the job in order, triggers the dependents as `reconcileJob` does, and releases the lock. The pass does not wait; the next pass (at most 30 s later, `ceiling`) re-plans from the ledger. The old `Reconcile` stays for `ot run-once` and the tests.
   - Rule for keys in flight (a key in flight is not re-planned): `ReconcileDetached` does not plan the keys of a job whose lock is held (it asks the `runner.JobLockHolder` before planning that job), so a pass never sees keys that a run has in hand as due. The run marks each key `Present` or closes it before it releases the lock (the unlock is the last deferred call, after the last mark), so no pass can find a finished-but-unmarked key while the lock is free. Tests: `TestDetachedSkipsKeysOfHeldJob`, `TestRunMarksBeforeUnlock`.
3. **Cursor and completeness come from the ledger.** A day is "done" when every expected key is marked present (`Present`), so a pass that launched runs sets no cursor; a later pass that finds the marks sets it. This keeps every pass idempotent and a restart safe: nothing lives only in memory except the lock, and a lost lock is a restart, which re-plans. Two code paths (`Reconcile` for run-once and tests, `ReconcileDetached` for serve) use the same planning function and the same cursor rule; `TestDetachedAndReconcileSameCursor` runs one fake day through both and compares the cursor.
4. **Lease, fence, drain, yield, bound, cap, expiry, point by point (revision 2 of `job-console.md`).**
   - Shared lease: `ops.run_lease` (owner `runner`) is held by the pass only while it plans and launches (seconds, renewed as today). A job run holds no database lease. What excludes another process is the instance fence the ticker already watches (`watchFence`); what excludes two runs of one job is the in-memory lock; what tells a crashed run from a live one in the next pass is the key's run row `lease_until` and heartbeat (`reconcile.go` `nextAttempt`), unchanged.
   - Drain at stop: all spawned runs and console runs belong to one job group with one context that is not cancelled by `runCtx`, like `consoleCtx` today. At a stop the group has `drainGrace` (30 s) in total, not per run; then the group is cancelled with the ordered-stop cause (`shared.ErrOrderedStop`) when the stop is an interrupt or a replaced executable, with a plain cancel otherwise, and `killGrace` (5 s) follows; `Run` returns only after the group's wait. A lost fence cancels the group at once.
   - Yield: nothing yields. No run holds a worker that another needs. One job's run does not make another job wait. Inside one job, today's key and an old day's key are the same job and run in order: a long old-day repair of J delays today's J. That is the owner's guard (one per job), named openly here and not hidden under "never wait"; it is seen by the slow notice (Decision 7) and bounded by the 3-keys stop of the bug draft.
   - Bound: each spawned run gets the context timeout `reconcileTimeout` (2 h, the number the turn had); each key keeps its own `RunBound` (`runBound`, default 30 min). A run that hits the timeout ends `cut` and leaves its keys for the next pass. This timeout is the existing one moved from the turn to the run, not a new time guard.
   - Cap: one running run per job id, from the lock, for scheduled and console runs together. Requests beyond that are rows in the queue, not goroutines.
   - Expiry: a waiting console request has none; it waits as long as the job runs, and the owner can withdraw it. A scheduled key that waits is left to the pass and closed by the window rules (`closeRow`) as today.
5. **A console request picks its job, and waits for its job, visibly.** `ClaimConsole` skips a queued request whose job id is locked (`Holder(jobID)` of `runner.JobLockHolder`, asserted on the lock set), writes `hold_job` and `hold_at` on its row (the columns exist: `migrations/0035_job_request.sql`, `jobrequest.Hold`, `internal/store/jobrequest/api.go`), and goes on to the next request, so a request of job B is claimed in the same call after a waiting request of busy job A. The row is claimed when the lock is free. The refusal `job_running` stays only for the race of two claims in one instant; its page text (`internal/pages/job_console/text.go`) is kept for old rows. The page line is "已在运行，自 HH:MM UTC" built from `hold_at`, written into `WaitingFor.line` by the builder (entry 13b); no elapsed time on it, so nothing is computed. Where the lock set is read: the claim is a turn of the scheduler's worker (`consoleHost`, `cmd/ot/jobconsole_host.go`, built by `cmd/ot/scheduler.go`), the same process that builds the one lock set (`shared.NewJobLocks()` in `scheduler.go`). So the claim reads the set directly, in memory, with no cross-process signal: `scheduler.go` hands the set to the host beside `host.set`, and `claimQueued` asks it through `runner.JobLockHolder`. Today `consoleHost` has no lock-set field at all and `claimQueued` never asks for a holder; that field and its wiring are entry 11. `openConsoleHost` runs before the lock set is built and the host may be nil (console off), so the setter tolerates both. What `hold_job` and `hold_at` mean: today `hold_job` is the job whose slot is near and `hold_at` that slot's time (`text.go` `queuedText`: "starts after HH:MM UTC (the slot of X)", pinned by `TestQueuedHeldText` and `TestSlotNearText`). For a request that waits for its own busy job the claim writes `hold_job` = the request's own job and `hold_at` = the start instant of the lock. The page tells the two apart without a new column: it emits `waiting_for` only when `hold_job` equals the request's own job and the job has an open row in `ops.job_run` (the reader of entry 14); then `queuedText` returns the same "已在运行，自 HH:MM UTC" (entry 14 changes `queuedText` by one case placed first), so one request never shows two lines; in every other case the slot-near sentence is unchanged and the two tests stay as they are. `ot serve` never reads the lock set: it shows a waiting request from the row (`hold_job`, `hold_at`) and a running job from `ops.job_run` (entry 5, views of Decision 8), which is how a page in another process knows a job is running. `ot scheduler busy` (a separate command) reads the heartbeat of `ops.capture_run`, not the lock set; it is outside this design.
6. **Every job run is recorded.** `ops.job_run` (entry 5): one row per job run, written by the run when it takes the lock: `Start`, `Progress` after each key (key count and the key in hand), and `Close` with `ok`, `failed` or `cut` (deferred, so every return closes it). Console runs and scheduled runs write the same row, `source` tells which. `ot run-once` runs are not recorded (kept out of serve by the fence). The row has no day: a run that walks old days and then today has no single day, so the page shows job, start, keys and step.
7. **Slow rule, in compute, a notice only.** A run is slow when elapsed > max(3 x usual, 10 minutes), with usual = the median duration of the last 20 closed `ok` runs of the same job id, cut and failed runs excluded, taken only with at least 5 samples; under 5 samples usual is shown as "没有历史" and a run is slow when elapsed > 60 minutes (twice the 30-minute `runBound` of one key, so a job with no history is flagged late, not early). No scaling by source or key count: runs of one job differ in key count and the median is robust to the odd long run; a one-key repair and a forty-key repair differ by more than 2x, which is why the factor is 3 and why the floor is 10 minutes (a 2-minute job that took 7 raises nothing). The rule is `compute.SlowFunc` in `internal/compute/jobrun`; the figures (elapsed minutes, usual minutes, slow) are `compute.FiguresFunc`, called by the notifier and by the page builders, which copy them and compute nothing. What happens once a run is slow: `NotifySlowRuns` (called from the notify turn in `cmd/ot/notify.go`, beside `NotifyAlerts`) sends one text per run through the existing `notify.Sender` (Telegram), marks `slow_notified_at` on the row only after the send is confirmed, and writes one log line `job_run_slow` (`job`, `elapsed_s`, `usual_s`, `keys_done`, `keys_total`, `source`, no key text) that the dispatcher patrol reads; the mark makes it once per run even across restarts. Nothing stops or refuses the job.
8. **What the pages show.** Two views, `rd.job_run_r1` (open runs) and `rd.job_usual_r1` (median and samples per job), feed `/data-health` (one line per running run, above the grid) and the console ("Running now", and per queued request `waiting_for`). The builders call `compute.FiguresFunc` with the generated-at time they already have and copy its figures, and write the text of each line into the `line` field (entry 13b); the front end prints `line` and computes nothing; the readers and the figures function reach a builder through the `Input` fields and `Runs` of the Interface section, wired in entry 12; the Chinese words are in the builders' text files, with the English glossed beside as the owner asked.
9. **Source pacing stays in the source client.** Nothing in the scheduler paces a source. The only pacing found in code is in the IBKR adapter, per connection and shared by every call that connection takes: `MessagePacer` 40 message starts per second (`DEFAULT_STARTS_PER_SECOND`), `LineBudget` 70 market-data lines and 50 snapshots in flight, `DetailsLane` 1 to 5 detail requests in flight with a 20 s timeout (`pyside/src/optdesk/ibkr/pacing.py`, built once per gateway at `ibgateway.py`). IBKR's own message limit is 50 per second; the adapter's 40 is its margin. Other sources keep their own: `internal/sources/fred/pacing.go`, `internal/sources/sec/pacing.go`, `docs/design/jquants-pacing.md`. Concurrent jobs on one gateway therefore queue inside the adapter, not in the scheduler, and a silent gateway stalls them all until the 3-keys stop. This design changes none of them.
10. **Database pools: the default is enough, with numbers; no store entry.** Each store has its own pool of default size max(4, NumCPU) connections; pools open connections on demand (no `MinConns`), and a call holds a connection for the call, in milliseconds, not for the run. Concurrent runs are bounded by the number of job ids, which is at most the 24 jobs of the scheduler [count at the cut from `job.toml` packages], and each run touches a few stores, one call at a time, so at most 24 connections are busy at once, spread over 27 pools; a pool that is full makes a call wait for a free connection, which is queueing of calls for milliseconds, not of runs. The sum of pool maxima can exceed the server's `max_connections`, but only connections that are actually in use exist; the pool may be raised through `pool_max_conns` in the DSN that the service secrets already carry (pgx reads it), which needs no code and is the owner's secrets file, not ours. What is not known: the server's live `max_connections` and NumCPU [unverified]; the acceptance of entry 5 reads the peak of `pg_stat_activity` once with all jobs triggered, read-only, and states it in the PR. If that peak is within 80% of `max_connections`, nothing changes; if not, a store issue sets `MaxConns` in each `Open`.
11. **Smallest cut that unblocks**: entries 7 and 8 (detached pass, group), with the interface entries 2 and the lock holder. The observing entries (1, 3 to 6, 10, 13, 13b to 17) are independent of the group; entry 9 edits `detached.go` of entry 7, and entry 12 wires both tracks.
