## Goal

On the day the owner chooses, the old system (option-trader, a DuckDB file) is stopped for good and the account history it holds (the part IBKR cannot return again) is in the new database, proven by a read-only verify; for N sessions both systems have run side by side and every figure the old system showed is set beside the figure optdesk stored, each difference explained by the owner or fixed; the web is guarded against computing; one runbook says the steps in order. This design stores and reports. It builds no page, no job that computes a figure and no figure.

## Decisions

1. What is imported (owner 2026-11-09: import only data of value; window reading: only what cannot be fetched again from a source optdesk already has). Imported: the old account snapshots with their positions and summary values, the last snapshot of each session day (`account_snapshot`, `account_position`, `account_summary` of the old store), because IBKR cannot return a past snapshot; and the Flex trade rows older than what a Flex query returns, through the existing `tools/ot-flex-export/` and `ot ledger-import` (`option-ledger.md` Decision 7), which this design does not touch. Not imported, and why: daily bars and daily FX (re-fetchable: optdesk backfills them from IBKR, `docs/design/market-bars.md`; so `ot bar-import` does not exist); old readings and derived figures (derived: optdesk recomputes them, and the parallel run is the check, Decision 7); working orders, fallback marks and earlier snapshots of a day (`account_order`, `account_fallback_mark`, `account_price`, no value once the day is over); the old FRED, event, benchmark, quote, chain and calendar tables (re-fetchable from the sources optdesk already has). Owner-entered data: the old store has directories for owner inputs, plans and settings (`owner_inputs`, `owner_plans`, `owner_settings`, `follow_member` in the option-trader source); this design has not read them and imports none; whether any of it cannot be entered again is asked of the owner (Left out). A dev-only exporter `tools/ot-history-export/` (its own uv project with a committed `uv.lock`, not run in CI, imported by nothing at run time, as AGENTS.md allows; the mainstream, MIT `duckdb` package, as `tools/ot-flex-export/` does) reads a copy of option-trader's DuckDB file, read-only, and writes `account.jsonl` (one line per alias and session day) and, from saved pages, `figure.jsonl` (Decision 2). It refuses a table whose columns differ from the ones it was written for, and refuses a file in which a value of an alias column looks like an IBKR account id (letters then digits): only aliases leave the old system.
2. Where the old figures live (read in the option-trader source, 2026-11-09). The finding is mixed. Stored: the table `reading` (`src/option_trader/readings/store.py`, `_SCHEMA`: name, version, subject_kind, subject, day, rev, value, unit, state) has the same key as `readings.reading` of optdesk, and the scheduler writes some figures into it (`scheduler/record_levels.py`, `scheduler/flex_readings.py`: `household.monthly_premium_received`, the market levels, the macro readings). Computed at page build: the figures of the pages are made by the view-model builders (`viewmodels/options_figures.py`, `viewmodels/household_page_builder.py` and the other `viewmodels/*_page_builder.py`), which the register names in `implemented_by` (for example `option_trader.viewmodels.options_figures._series`) and which read the stored inputs, not a stored figure. So there is no stored baseline for most page figures. The baseline is what the old system shows: for the N sessions of the parallel run (Decision 7) the owner saves the page JSON of the old serve each session day to a directory, and the exporter turns it into `figure.jsonl` by reading each register entry's `pages` path in it (for example `options_summary.card.premium_series_6m.premium`), and adds the rows of the stored `reading` table for the same days. A `pages` path the exporter cannot find in a saved page is counted `path_not_found` in its printed counts and the figure is `unchecked` with that reason; it is never written as zero. `figure.jsonl` has its own day bound: the exporter takes `--figures-from DAY` and `--figures-to DAY`, the first and the last session day of the parallel run, and writes no figure line outside them; it is run a second time, after the parallel run (Decision 10). `figure.jsonl` lines carry name, version, subject kind, subject, day, the value as decimal text, the places of the old display, and `from` (`reading` or `page`).
3. One command, no framework (window decision 3, the pattern of `option-ledger.md` Decision 7). `ot account-import DIR [--map from=to ...] --through DAY [--verify] [--report FILE]` reads `DIR/account.jsonl` and writes each line as one `store.Capture` through `store.AccountWriter.WriteCapture`, with the capture id `<alias>:<session_day>:import` (the id rule of `store.Capture`, run key `import`). It is insert-only and idempotent: a second run counts `Same`. Counts only are printed: no row, no value, no account number. The alias map is as in the ledger: the default is the same label; when at least one `--map` is given, an alias that no `--map` names refuses the whole file before any write.
4. Complete days only. `--through DAY` is the last complete session day of the old system, and the exporter refuses any line of `account.jsonl` after it and the importer refuses any such line (`figure.jsonl` has its own bound, Decision 2): the day of the export and the day the old collectors were stopped are never imported, so the files of a later export agree with the files of an earlier one on every day they share. The new scheduler starts on a later session day, so an import capture and a live capture never share a day.
5. kind='import' (window decision 4: kept only if still needed). It is not needed. The plan note asks that imported rows can be told from live ones and merged; the capture id already ends in `:import` for an imported capture, the ledger rows already carry `source = ot_import`, and by Decision 4 no day holds both kinds, so there is nothing to merge. The generated `kind` column, the `rd.account_*_r2` views and the reader change of the first draft are dropped; they are named in Left out with what would bring them back.
6. `--verify` (read-only, two rehearsals). `--verify` writes nothing: it reads the same file, asks the reader whether each line is stored with the same content (the SHA-256 of the canonical line against the same hash of the stored rows rebuilt through `store.AccountReader.Positions` and `Values`) and reports per dataset `Missing` (no stored row of the key) and `Different` (a stored row of the key with another hash, for example a day the old system later restated, or a stale import capture from an earlier export: insert-only keeps the old row, so an import reports it as `Conflict` and a verify as `Different`). It exits 0 only when both are zero. `--report FILE` writes counts, the SHA-256 of the input file and `ok`, no row. A rehearsal is an import and a verify on a fresh scratch database each time (window default — owner may change): the scratch database is a new database from `ot setup`, named by the environment file of the profile used, so a second rehearsal on a later export has no stale capture to conflict with. Rehearsal 1 and rehearsal 2 use two exports; the final import is the same command on the live database. Three reports with `ok` are the evidence (Decision 10).
7. The parallel run, and no replay tool (window decision 2). Both systems run side by side for N session days (window default — owner may change: N is 10) after the first import into the live database, the old system on its own, optdesk running its scheduler. Each session day the owner saves the old serve's page JSON. After the parallel run the exporter writes `figure.jsonl` for those days (Decision 2), and `ot compare-figures` (entry 6) reads it and reads optdesk's readings back with `store.ReadingReader.LatestReadings`, once for each distinct `(name, subject_kind, subject)` of the old file over the range of its days (the subject list comes from the old file, because `LatestReadings` needs it). A replay of past sessions with `ot backfill --day` is not part of this design: `cmd/ot/backfill.go` refuses a day with no stored plan (`runner.RefusedNoPlan`) and a day ahead of the cursor, and a fresh scratch database has neither, so the command would be refused (Left out).
8. Replayable and live-only figures (window default — owner may change the table). The 54 figures of the register, 23 replayable, 21 live-only and 10 new. Replayable from the imported account and Flex history and the bars and rates optdesk backfills (these could be computed from stored inputs, once a job computes them; until then the compare says `not_computed_yet`): `home.options_summary` (2), `home.household` (5), `household.*` (13), `option.tracking` (1), `market.spx_close` (1) and `market.sp500_vs_200d` version 1 (1). Live-only (they need quotes, chains, IV or Greeks of the day, which nothing stored holds; they are checked by the parallel run only): `home.options` (4), `structure.*` (10), `companies.volatility` (2), `option.candidates` (4) and `market.index_iv` (1). New, made in optdesk with no old value (their `agreed_in` is not `carried over from option-trader`): `market.sp500_vs_200d` version 2, `market.vix_pctile_3y`, `market.vxn_pctile_3y`, `market.rvx_pctile_3y`, `market.sp500_pctile_3y`, `market.iv30_own`, `market.ivp_own`, `market.ivr_own`, `market.vix_term_ratio` and `macro.ease` (10). 23 + 21 + 10 = 54. The table is data in `docs/deploy/cut-over-figures.toml`: `[[class]]` entries with `prefix` or `id`, an optional `version`, and `class` = `replayable`, `live_only` or `new`. The matching rule: an entry with `id` and `version` matches that figure exactly and wins; else an entry with `id` matches that id; else the longest `prefix` that equals the id or is followed by a dot in the id (so `home.options` matches `home.options.x` and not `home.options_summary.x`). An id that matches no entry makes `CompareFigures` return an error that names the ids and no report: the compare is not run on an incomplete table.
9. Compare, every figure. `ot compare-figures --old FILE --register FILE --classes FILE --explained FILE` sets, for every `[[figure]]` of the register (go-toml/v2), the old rows beside optdesk's readings and gives it one status: `checked` (every row equal), `explained` (a row differs or is missing and the owner's `[[explained]]` entry has `id`, `reason` and `date`), `unexplained`, `new` (class `new`, nothing to compare), `unchecked` (no old row; the reason is printed: `path_not_found`, `no_old_value`, or `not_computed_yet` when optdesk has no reading because no job makes the figure). It exits 0 only when `unexplained` is 0 (an unclassified id is an error, Decision 8, and exits non-zero without a report); `unchecked` is printed, each with its reason, for the owner to read, and the closure record (Decision 10) states their count. Equality is exact on the decimal text after both sides are rounded half-even to the old `places` with `math/big` (window default — owner may change: no tolerance). It checks values, not pixels: the look of a page against its design is the owner's comparison of screenshots (Left out).
10. Stop-the-world, runbook and closure (window default — owner may change: the restore drill). The old serve is not restarted and the collection gap between the last complete day and the first new capture is accepted (alignment index; plan line 25). `docs/deploy/cut-over.md` lists, in order: (1) back up the new database and restore the backup into a scratch database, comparing row counts (the restore drill the alignment index defers to this design); (2) copy the old DuckDB file (a copy, never the live file); (3) export `account.jsonl`; (4) rehearsal 1 and (5) rehearsal 2 (Decision 6); (6) stop the old collectors (owner); (7) copy and export again with the last complete day as `--through`; (8) the final import; (9) its verify; (10) start the new scheduler (owner); (11) the parallel run of N sessions, saving the old page JSON each day; (12) export `figure.jsonl` with `--figures-from` and `--figures-to`; (13) `ot compare-figures`; (14) close. `docs/deploy/cut-over-record.md` is the owner's record of the closure: three verify report hashes, the dates, the exit code of the compare, its count of `unchecked` and the reason of each, and the check that `web/no-compute-allow.txt` has no line. The cut-over is closed when the owner fills the record and merges it.
11. The web test (Decision 9b of the first draft, the part this design can finish). `web/no-compute-allow.txt` is empty on main but no test reads it. A vitest reads it, fails when it holds a line, and fails when a file under `web/src/` outside `web/src/generated/` holds `toFixed`, `toLocale`, `Intl.` or `Math.`. This is the enforce mode of the web half. `web/deps-allowlist.txt` is a dependency list and stays. The register half, 44 `pending-recompute` hashes to zero and the test that refuses the word, needs `compute-stage2` and is in Left out.
12. Library or own code. JSON Lines reading, the canonical hash and the comparison by key are own code on the standard library (`encoding/json`, `bufio`, `crypto/sha256`, `math/big`): no mainstream library does an import keyed by dataset with a per-line content hash, and a diff library would not know the keys; own implementation, because of that. It sits behind three function types in `internal/jobs/api.go` (Interface), so a library can replace each. The register is read with go-toml/v2, mainstream and MIT, already in `go.mod`. Python uses `duckdb` (MIT). No new direct dependency.
13. Tests. No test touches option-trader's database, a live broker or service data: the exporter's test builds a small DuckDB file in a temporary directory with invented rows; every Go test reads fixture lines with invented aliases and values; PostgreSQL tests carry the build tag `pg`. Tests run in parallel (`t.Parallel()`, `t.TempDir()`), none sleeps, time comes from `clock.Clock`. No source file reaches 600 lines.
14. Nothing here goes to Telegram. Commands print counts and statuses to the terminal and to report files only; the margin cushion and the assignment cash appear in no report.
